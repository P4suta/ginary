# E23 — the Windows launcher had never launched anything

Date: 2026-09-06 · Status: GREEN complete

## Housekeeping

E23 has one subject and two halves that meet in the same place: **the `windows` job of
`.github/workflows/ci.yml` did not run a packaged application, and the documents did not say what
the `macos` job had been proving for weeks.**

`main` is green. Every job of `ci.yml` passes on every push, `macos-15-intel` and `macos-14`
included. The only open pull request is release-please's own
[#7](https://github.com/P4suta/ginary/pull/7), which is red for exactly the reason
`docs/RELEASE.md` step 1 says it will be until a maintainer makes the changelog edit — the design
rather than a defect, and untouched by this milestone.

What that green does not cover is the thing a Windows user depends on. The `windows` job built
both flavors, ran `cargo test` natively and probed a bare `erl.exe` for `halt(3)`. It never ran
`ginary build`, and it never started a packaged artifact. So `launch_windows::run` — the spawn,
the job object and the console control handler, the three mechanisms
[ADR 0015](../../adr/0015-windows-launcher-stays-resident.md) rests its `#[allow(unsafe_code)]` on
— had **never executed anywhere**, on any machine, in any run. Seven targets were offered and one
of them had a launcher nothing had started.

The tree said so itself.
`tests/regressions/e15_the_adr_credited_the_windows_job_with_a_spawn_that_never_ran.rs` was
written in E15 to fail the day that stopped being true and to point at the sentence to rewrite. It
did exactly that, on the first workflow edit of this milestone. E23 is the milestone that file was
waiting for.

**Nothing is committed, tagged, pushed, merged or released as this record is written.**

## 2 — what the two jobs did, side by side

The `macos` job has, since E9 made it green, done the whole thing: build the darwin stub natively
into a target directory of its own, package `hello_ffi` against the runner's own OTP,
`codesign --verify --strict` the artifact, run it, assert its arguments and its exit code, and
verify the signature *again* afterwards to prove that extracting a payload did not rewrite the
file the signature covers.

The `windows` job did four steps: two `cargo build`s, one `cargo test`, and a `pwsh` probe that
ran `erl -noshell -eval "halt(3)"` and checked `$LASTEXITCODE`. That probe proves a **platform**
fact — the emulator leaves 3 behind for its parent — and it is the fact `launch_windows::run`
rests on. It is not the fact that `run` carries that code across the spawn it owns, because
nothing ran `run`.

Two smaller things came out of reading the job beside its sibling:

- **The stub was built over the command line tool.** Both flavors are one Cargo target and share
  `target/release/ginary.exe`, and the job ran `cargo build --no-default-features --release`
  first and `cargo build --release` second. Nothing consumed either, so nothing failed — but the
  moment a step wants to run `ginary build`, the stub has to be somewhere else. That is precisely
  the defect `tests/regressions/e5_the_macos_job_ran_the_stub_as_the_command_line_tool.rs` records
  against the macOS job, whose scanner splits a command on `target/release/ginary` and reads the
  next word: on Windows that word is `.exe`, so the existing guard could not have seen the
  Windows version of its own bug. The stub now goes to `--target-dir target/stub`, which makes
  the ordering irrelevant rather than load-bearing.
- **The job name understated it.** `Windows build and exit-code propagation` became
  `Windows build, launch and exit-code propagation`, matching `macOS build, launch and signature`.
  No branch protection depends on it: the required context is the `Required CI` fan-in.

## 3 — RED

Three files, in this order, each failing on an assertion rather than on a compile error.

`tests/ci_matrix.rs` gained three rules, all of which look the `windows` job up by what it does
rather than by a step name:

```text
test the_windows_job_packages_and_runs_an_artifact ... FAILED
test the_windows_artifact_run_asserts_the_code_the_launcher_carried ... FAILED
test the_windows_job_keeps_the_bare_runtime_probe_beside_the_artifact_run ... FAILED

the `windows` job has to keep the step that runs `ginary build --target windows-x86_64`: it is
the only execution `launch_windows::run` — the spawn, the job object and the console control
handler — has anywhere
```

The third of those is a rule about keeping *both* probes. The bare `erl` proves the platform
fact; the artifact proves ginary's. With only the second, a red job says "3 did not arrive" and
cannot say whether the emulator lost it or the launcher did.

Then, on the workflow change, the E15 tripwire fired as designed:

```text
the `windows` job starts a packaged artifact now — [...] — which is the end-to-end run
docs/adr/0015-windows-launcher-stays-resident.md says that milestone still owes. Both statements
in the ADR change together
```

## 4 — the job, and why each part of it is there

The new step is the macOS one with the platform changed and nothing else, so that what the two
runners prove differs in the operating system rather than in the thoroughness of the check.

- **The runtime is named as a `dir:` source in the fixture's own `gleam.toml`,** appended to the
  *copy*, never to the committed fixture. `ginary build` has no `--erts` flag and never had one;
  assuming it did killed the macOS job at argument parsing on two consecutive runs
  (`e6_the_macos_job_passed_a_flag_the_cli_does_not_have.rs`).
- **The path is written as a TOML literal string,** in single quotes. This is the one place where
  the Windows job cannot copy its sibling, and it is a user-facing fact rather than a CI detail:
  `\U`, `\t` and `\x` are escape sequences inside a TOML *basic* string, so
  `erts = "dir:C:\Users\you\otp"` is not the path it looks like and is usually not valid TOML at
  all. Writing it the way a Windows user has to write it means the job proves the documented
  spelling instead of sidestepping it with forward slashes.
- **Four runs, not one, and the cache emptied between the first two.** `GINARY_CMD=selftest`
  first, because it reports extraction, preflight and a no-op runtime start as `PASS`/`FAIL` per
  phase, and a failure there names the phase rather than leaving a number. Then
  `GINARY_CMD=uninstall`, which throws the entry away again: the selftest fills the cache, so
  without it the run labelled "cold" is a warm one and the job never exercises a launch that has
  to extract before it can spawn — the first thing a user's machine does. Then the cold run,
  whose stdout is asserted for `args=0 hello world`, the `priv/greeting.txt` contents and a
  `cwd=` line; then a warm-cache run, which is a spawn against a runtime this launcher did not
  unpack; then `halt(3)`. `ginary inspect` runs over the artifact first and its exit code is
  asserted too — `$ErrorActionPreference` does not apply to a native program's status, so an
  unchecked one would be a silent one.
- **Diagnostics that are sentences.** A failed build lists the `beam.smp.dll` and `erl.exe` it
  found under the runtime root, so a layout that is not what `otp.rs` assumes is a path rather
  than an exit code. A failed run repeats itself under `GINARY_DEBUG=1`, which is the launcher's
  own phase log and the only view of a launch this repository can get off a runner it does not
  own.

## 5 — the documents, and the second half of the subject

Removing the Windows sentence meant reading the surrounding claims, and the macOS ones were worse.

`README.md` said macOS support "has never been run on a Mac" and "nothing built for macOS has run
anywhere". `docs/dev/v1-readiness.md` — the **fail-closed checklist that decides whether ginary is
v1** — carried the macOS launch as `CI-gated`, a status it defines as "never marked done and never
hand-waved". Both had been false since the `macos` job first went green: two runners had been
packaging an artifact, launching it and verifying ginary's own code signature on every push.

That is a defect of the same kind as the one the checklist exists to prevent, pointing the other
way. An item marked done without evidence overstates the project; an item left deferred after its
evidence exists understates it, in the document written to stop hand-waving, and it costs a reader
the platform they were evaluating. So the rule is now stated in both directions, in the sweep's own
introduction and in
`tests/regressions/e23_the_documents_said_the_launches_had_never_happened.rs`, which derives the
answer from the workflow rather than trusting the prose: a job that goes back to building without
launching puts the old sentences back.

Writing that scanner turned up a defect in the scanner itself, worth recording because it is the
same class as the `.exe` blind spot in §2. `WorkflowStep::commands` joins a backslash continuation
by replacing `\` + newline with one space, and the continuation line arrives with its own
indentation still attached. So the macOS job's

```text
"$GITHUB_WORKSPACE/target/release/ginary" build \
  --target "${{ matrix.target }}"
```

reads as `build   --target` with three spaces, and the first version of the rule — a
`contains("build --target ")` — answered that the one job which had packaged and launched an
artifact since E1 had never packaged anything. Both scanners now read a command as its **words**.
A rule that matches one particular wrapping is a rule about formatting.

The remaining stale claims went with them: `docs/adr/0016`'s "CI on a `macos-15-intel`/`macos-14`
runner is the GitHub Actions milestone that closes it", the two `#[cfg(windows)]` regression files
that described themselves as running nowhere when the native `cargo test` on the runner executes
them, and `tests/windows_build.rs`'s module doc, which called the `otp_win64_<version>.zip` layout
an open question. It is now read off a real tree on every push: a name this repository's fixture
has wrong is a build that fails there.

## 6 — one thing that is not fixed, and is written down instead

`a_windows_runtime_path_survives_a_toml_literal_string` in `tests/config.rs` was written to prove
the README's new advice and found something beside it. The literal string works — every backslash
reaches the build unchanged — but "is this path absolute?" is answered by `Path::is_absolute`,
which answers for the **build machine**. `C:\Users\you\otp` is not absolute to a Linux one, so a
drive-lettered path in a manifest built on Linux is joined onto the project root like any other
relative path.

It is not fixed here, and the reason is scope rather than convenience: teaching the config reader
a target-specific notion of absoluteness is a rule with its own edge cases (`C:foo` is a real and
genuinely relative Windows spelling), and it does not reach the mainline case, where a Windows
runtime tree unpacked on a Linux build machine is named by that machine's own path. The failure is
also diagnosable rather than silent — the build prints the joined path when it cannot find the
runtime. Both halves are asserted in that test and stated in the README, because a sharp edge
nobody wrote down is one the next person finds at the worst moment.

`docs/dev/v1-readiness.md` gained the related boundary in the same spirit: there is **no Windows
runtime in the catalog**, so cross-building *to* Windows from Linux or macOS is not something v1
does. `otp repack` takes tarballs and a Windows runtime ships as `otp_win64_<version>.zip`, a
different shape and a milestone of its own. A Windows artifact is built on Windows, where a Gleam
developer already has Erlang because `gleam` needs it, and the build refuses by name rather than
producing an artifact with the wrong runtime in it.

## 8 — the run

Every job of run [34015391532](https://github.com/P4suta/ginary/actions/runs/34015391532) is
green, first time, `Required CI` included. The one that is the subject is job
[101438136143](https://github.com/P4suta/ginary/actions/runs/34015391532/job/101438136143),
`Windows build, launch and exit-code propagation`, on `windows-2022` with OTP 29.0.5 /
erts-17.0.5.

Two things were genuinely unknown before it and are now measured rather than assumed.

**The `otp_win64_<version>.zip` layout is what this repository said it was.** ADR 0015 has said
since D2 that `beam.smp.dll` is "what the documentation says rather than what a real zip was read
for". `ginary inspect` on the artifact lists it off a real tree:

```text
5660672  erts-17.0.5/bin/beam.smp.dll
 185856  erts-17.0.5/bin/erlexec.dll
 138752  erts-17.0.5/bin/erl.exe
  67072  erts-17.0.5/bin/inet_gethost.exe
```

All three required names are where `otp::check_windows_erts_binaries` looks for them, and
`erlexec.dll` — a name no unix tree has, and one this repository does not require — travels as one
of the DLLs beside `erl.exe`.

**The build path runs unchanged on a Windows host.** `gleam export erlang-shipment`, the closure,
the staging, the strip and the payload all ran with nothing Windows-specific asked of them, and
the TOML literal string arrived intact:

```text
[tools.ginary.target."windows-x86_64"]
erts = 'dir:D:\a\_temp\.setup-beam\otp'
```

And the launch, which is the whole point:

```text
extract: PASS
preflight: PASS
run: PASS
args=0 hello world
hello from priv
cwd=d:/a/ginary/ginary
the artifact exited 0 on its first run
the artifact exited 0 on its second, warm-cache run
halt(3) through the launcher left exit code 3
```

`launch_windows::run` — the spawn, the job object and the console control handler — has now
executed. `tests/windows_build.rs::the_windows_launcher_adr_records_the_run_that_proved_halt_propagation`
requires the ADR to cite **both** runs, because they are two different facts about the same three
digits: 33864729638 proved that a bare `erl.exe` leaves 3 behind for its parent, and this one that
a packaged artifact carries that code across the spawn ginary owns. An ADR citing only the first
would be crediting the emulator with the launcher's work.

## 9 — what the first Windows artifact turned up, and what it is not

The artifact line is the first ever measured for this target, and one of its three numbers is
wrong in a way nothing in the tree was watching:

```text
stub: ginary-stub-0.1.0-windows-x86_64.exe 1012224 bytes
artifact: …\hello_ffi-windows-x86_64.exe (7170048 stub + 3881941 payload + 64 trailer)
```

The stub this job built and handed over through `GINARY_STUB_DIR` is 1,012,224 bytes. The stub
inside the artifact is 7,170,048 — the **full command line tool**. `bundle::resolve_stubs` takes
the host target before any search happens:

```rust
if target == host && opts.stub.is_none() {
    resolved.push(TargetStub { target, path: self_stub.to_path_buf(), len: self_len });
    continue;
}
```

`windows-x86_64` *is* the host on `windows-2022`, so `GINARY_STUB_DIR` was never consulted. That
contradicts the search order both `README.md` and `src/stub.rs`'s own module doc state, where the
environment directory is source 2 and the running executable is source 3, and
`stub::candidate_paths` implements exactly that order — for every target the short-circuit does
not swallow.

The cost is not small and it is not Windows-only. Measured on this machine, at this commit:

| | full tool | launcher-only stub | carried for nothing |
|---|---|---|---|
| linux-x86_64-gnu | 6,718,872 | 1,151,776 | 5,567,096 |
| windows-x86_64 | 7,170,048 | 1,012,224 | 6,157,824 |

Every artifact built for the machine it was built on therefore ships clap, the TOML reader, the
OTP catalog, the downloader and the SBOM writer inside it, and starts none of them. The
`hello_ffi` host artifact measures **10,821,175 bytes** today, against the **5.4 MB** this
repository records for it in `README.md` and `docs/dev/v1-readiness.md` as Phase A acceptance
evidence. That figure predates the `cli` feature split in C2 and nothing has measured it since,
because no test asserts an artifact size — which is the actual defect, the number being only its
symptom.

**None of that is fixed here, and it is not deferred quietly either.** It is a change to what
`ginary build` produces, it moves the bytes of every host artifact, and the honest fix is not the
one-line short-circuit but a test that measures and gates the sizes so the next drift is caught by
the suite rather than by a milestone that happened to read a log. That is E24's subject, stated
here with the measurements already taken, so it starts from evidence rather than from a hunch.
What E23 does not do is leave the wrong number standing while claiming to be the milestone about
documents telling the truth — §5 of this record is exactly that principle, and the size figures are
the same defect one layer down.
