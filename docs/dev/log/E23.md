# E23 — the Windows launcher stops being inferred

Date: 2026-09-06 · Status: GREEN complete

## Housekeeping

E23 has one subject: the launcher this project has shipped for two milestones without ever
running it. The whole of `tests/launcher.rs` — 64 claims about the cache, the argument vector, the
environment difference, the five numbered exit codes and the `GINARY_CMD` commands — carried
`#![cfg(unix)]`, so it compiled to nothing on Windows. `tests/windows.rs` said in its own header
that the job object, the console control handler and a real runtime's exit code were "not here,
and cannot be". `mise.toml`'s `build:windows` said the launcher's spawn, job object and console
handler "are compiled and nothing more". And `docs/dev/v1-readiness.md` nonetheless booked
"Windows artifact **launch**, exit-code propagation" against the `windows` job of
`.github/workflows/ci.yml` — a job whose assertion step ran

```text
& $erl -noshell -eval "halt(3)"
```

which is `erl.exe`, not an artifact, with no launcher anywhere in it.

**What changed is the machine.** This is the first milestone worked on a Windows host: Windows 11
x86_64, Rust stable 1.98.0 msvc. Every previous milestone was done on Linux, and every document
above was written by someone who had no Windows to check it on. No Erlang was needed to use it:
E10 and E11 had already built the pattern — a compiled program planted where a `#!/bin/sh` script
will not start — for the *build-side* fixtures, and never applied it to the launcher's.

**Nothing is tagged, merged or released in this milestone.** The work was written with nothing
committed, then committed and pushed on request as
[#11](https://github.com/P4suta/ginary/pull/11); §8b records what the first runner and the first
review found there. Pull request #7 and the 0.1.0 release are untouched, and so is
[#10](https://github.com/P4suta/ginary/pull/10) — an independent E23 worked on Linux in parallel
with this one, which covers the CI half and collides with this branch on nine files including
this document. Which of the two is `docs/dev/log/E23.md` is an editorial decision about the
project's own record and is left to be made rather than settled here.

Three more baseline facts, none of them E23's doing:

- **`cargo clippy` reports 27 `result_large_err` warnings** in `src/config.rs` and

  them means boxing error variants across the crate. **Declined**, recorded.
- **`cargo doc` with warnings denied fails on Windows.** Three intra-doc links point at
  `#[cfg(unix)]` items — `launch::exec` twice and `cache::prepare` once — which resolve on Linux

- **`cargo clippy` on Windows reports four dead items in `tests/native.rs`**: `HookCtx` and three

- **`mise run <task>` cannot provision here.** `mise.toml` pins `erlang = "29.0.5"`, which mise
  builds from source through kerl; that does not work on Windows. Every gate below was therefore
  run as the `cargo` command line the task wraps. Making the task file usable on a Windows
  development host is not this milestone's subject and is recorded rather than attempted.

## 3 — the message assertion written in one language

RED, GREEN and a scanner, in
`tests/regressions/e23_a_test_expected_the_operating_systems_words_in_english.rs`.

This is E7's rule at a site E7 did not reach. E7 established that the text after ginary's own
colon belongs to `io::Error`'s `Display` and scanned `src/error.rs` for the `(os error ` tail.
`tests/cli.rs` spells the same fact differently — it quotes the *words* — so that scan could not
see it. The fix is `common::oserror::os_words`, the same one-liner `src/error.rs`'s unit tests
have had since E7, now where the integration suite can reach it. The scan is over every tracked
test source, for the two English spellings of "that file is not there"; they appear nowhere else
in the tree outside prose.

**The scan reads *tracked* sources, and that hid a defect until the commit.** Every run of the
suite in this milestone was made with the four new `e23_*` files untracked, so the scan never
read them — including the scanner itself, which has to spell both English phrases in order to
look for them. `git add` made it visible and it failed immediately, on its own two lines. The
fix is E15's idiom: `file!()` is the scanner's own path and cannot go stale under a rename. Worth
recording twice over, because it is a rule about *when* the suite is honest: a scan of tracked
files says nothing about work that is not committed yet, and every scanner in
`tests/regressions/` that reads `tracked_test_sources()` shares that blind spot. Both flavors
were re-run with everything staged.

## 4 — the launcher fixture gains a body Windows can start

`tests/common/artifact.rs` builds a packaged application with no Erlang. Its `erts-<vsn>/bin`
programs were `#!/bin/sh` scripts, and one of them is the program the launcher starts.

- `examples/ginary_test_erlexec.rs` is the compiled counterpart, planted on Windows the way
  `examples/ginary_test_shim.rs` is planted for the build-side fixtures. It is argument-driven
  rather than a step list, because that is what standing in for `erlexec` means.
- Neither rendering spells the contract. `CONTRACT_VARS`, `EXIT_ARG`, `SIGNAL_ARG`, `SLEEP_ARG`,
  `DUMP_ARG`, `HALT_EVAL`, `STUB_EXIT` and the dump's lines are constants; the shell body is
  built from them and the compiled program reads them out of a `<program>.contract` sidecar
  staged beside it. `tests/windows.rs::both_renderings_of_the_runtime_stub_carry_every_term_of_the_contract`
  holds the two against each other.
- The generated shell body was diffed against the constant it replaced: identical but for the
  line continuation in the variable list, which `/bin/sh` reads the same either way. That check
  matters because no Linux runs here.
- `Runner` now scrubs into `%LOCALAPPDATA%`, `%TEMP%`, `%TMP%` and `%USERNAME%` as well as `HOME`
  and `XDG_CACHE_HOME`. `%LOCALAPPDATA%\ginary` is `cache::resolve_windows`'s second rung and
  lands on the same `<dir>/xdg/ginary` the unix rung does, so `cache_root()` answers for both.
- An artifact is written as `hello.exe` on Windows: `std::process::Command` resolves an
  extensionless path by appending one, so a file called `hello` is a file nothing will start.
- `host_manifest()` is the manifest an artifact *on this host* carries, and `stage` writes the
  bindir `launch::required_binaries` will look for. `canonical_manifest()` is untouched, because
  `tests/launch.rs` and `tests/windows.rs` assert against it on purpose.
- The reader fixtures ask for the old tree explicitly. `ArtifactOptions::placeholder_runtime`
  makes `common::repack::build` — which feeds `inspect`, `verify` and `sbom` — stage the
  canonical unix tree on every host, because those tests are held to what an artifact *contains*
  and a real program in the bindir is a native object.

That last point was found the hard way: with the startable tree everywhere, 14 `verify` tests and
2 regressions failed at once. The first reading of those failures produced the milestone's second
product defect.

## 5 — the Windows allowlist named the CRT's API sets and not the base's

`tests/regressions/e23_the_windows_allowlist_named_no_api_set_but_the_crt_one.rs`.

With a real PE inside a payload for the first time, `ginary verify` reported two of its imports
as libraries the artifact expects a stranger's machine to supply:

```text
erts-17.0.5/bin/erl.exe: needs `api-ms-win-core-synch-l1-2-0.dll`, which the artifact does not carry
erts-17.0.5/bin/erl.exe: needs `ntdll.dll`, which the artifact does not carry
```

`WINDOWS_NEEDED_ALLOWLIST` admits the Universal CRT's forwarding libraries through a companion
rule — an allowlist naming `ucrtbase.dll` admits `api-ms-win-crt-*` — and the Universal CRT is
not the only family Windows forwards. `KERNEL32.dll` publishes its own surface as
`api-ms-win-core-*`, and every program links `ntdll.dll`. This is E12's defect again, in the same
list, invisible for the same reason: no test had ever put a genuine Windows binary in a payload.

The fix keeps the shape of the rule rather than widening it: `WINDOWS_CORE_PREFIX` with
`WINDOWS_CORE_COMPANION`, so an allowlist a test narrows to `&[]` still admits nothing and the C
runtime does not vouch for the Win32 base. `ext-ms-win-*` stays reported — an extension API set
is the half of the mechanism an edition of Windows may genuinely lack.

**Every real Windows artifact would have raised these two findings.** They were never seen
because nothing had ever verified one.

## 6 — the launcher claims run natively

`tests/launcher.rs` loses its file-level gate and states the rule instead:

> A launcher claim runs on every platform when it is about the payload, the cache, the manifest,
> the launch plan, `GINARY_CMD` or the exit code. It stays `#[cfg(unix)]` when it is about
> `execve`, mode bits, `flock` semantics or signals.

**Five claims stay gated**, each with its own reason in the source: a non-UTF-8 argument (Windows
has none), `128 + signo` (no signals), the read-only cache root and the failing prune (both make
their condition with a mode word), and the missing-interpreter hint (glibc's, and `hint_for` on
Windows deliberately returns nothing).

**Fifty-nine run, and eight failed on the first attempt.** Every one was diagnosed rather than
gated away:

| claim | why it failed | resolution |
|---|---|---|
| `the_runtime_starts_in_the_callers_working_directory` | `canonicalize` answers with `\\?\` | expectation goes through `winpath::plain_path` |
| `the_trace_records_a_launch_that_can_be_reproduced` | expected `erlexec` and a `/` separator | built from the host's launch program and the extraction spelling |
| `heart_bundles_its_program_and_names_the_artifact_in_heart_command` | `HEART_COMMAND` is quoted | correct: `shell_word`'s Windows arm is the `CommandLineToArgvW` rule, and this is the first run that has ever exercised it |
| `an_old_sibling_is_pruned_by_the_next_run…` | substring match against a JSON-escaped path | the record is parsed as the JSON array it is |
| `a_damaged_entry_is_extracted_again` | removed `beam.smp` | the emulator is `beam.smp.dll` there |
| `a_payload_that_cannot_pass_preflight_exits_124…` | omitted `beam.smp` | as above |
| `a_selftest_of_a_runtime_that_cannot_start…` | omitted `beam.smp` | as above |
| `a_process_killed_mid_extraction_is_swept_by_the_next_run` | the sweep kept the tree | see below |

The last one is worth stating on its own. `cache::sweep` asks `win32::process_is_alive` whether
the owner of a `.tmp-<pid>` tree is still extracting, and it answered yes about a process the test
had just killed. **The launcher is right.** Killing a process on Windows does not retire its id:
the process object outlives it for as long as anybody holds a handle, and
`std::process::Child` holds one until it is dropped. The fixture reaps and now also releases. A
sweep that defers while a handle is open is conservative in the safe direction, and the tree goes
on the run after.

**A ninth failed, and only on a runner.** `the_runtime_starts_in_the_callers_working_directory`
passed on the development host and failed on the first GitHub Windows runner it ever reached:

```text
  left: Some("C:\Users\RUNNER~1\AppData\Local\Temp\.tmpVCyusT")
 right: Some("C:\Users\runneradmin\AppData\Local\Temp\.tmpVCyusT")
```

One directory, two spellings. `%TEMP%` on that runner carries an 8.3 short name because
`runneradmin` is long enough to have one; `livec` is not, so this host cannot produce the failure
at all. The claim is that the launcher did not `chdir`, which is about *which* directory and not
about how it is written — and the test settled it with `assert_eq!` over a canonicalised string.

This is E12's defect, in a file E12 never touched. `common::hostpath::names_the_same_directory`
has existed since then and reconciles exactly this — the short name, the verbatim prefix, the
drive-letter case, a `/tmp` that is a symlink — by asking the filesystem. Un-gating moved a text
comparison, correct for as long as it only ran on unix, onto the platform where it is wrong.
E12's regression proved the *rule* and did nothing to stop a fourth site bypassing it, so the
new regression is a scan rather than a case:
`tests/regressions/e23_a_reported_working_directory_was_compared_as_text_again.rs` requires every
tracked test that reads a directory a program reported to settle it through that rule. Three do.

Two Windows-only code paths got their first execution here rather than a test of their own: the
`\\?\` extraction and the two-open share-mode lock, which `README.md` recorded as having tests
that "run nowhere yet".

The plan asked for one claim to be *added* here — that a default first run writes nothing to
standard error, the user's actual first impression. It turned out to exist already:
`nothing_is_printed_when_neither_switch_is_set` asserts `stderr` is exactly empty after a cold
run, it was `#[cfg(unix)]` until this section, and it now holds on Windows. Nothing was written;
the item is closed by the gate coming off. Its other half — that the one line `cache::prepare`
may emit when the primary root is refused still appears —
is `tests/cache.rs::an_unwritable_root_falls_back_with_exactly_one_warning`, and that one stays
unix-only for the reason the two gated launcher claims do: it makes its condition with a mode
word. The Windows fallback (`prepare_windows`) writes the same single line and nothing asserts
it, which is a smaller gap than the one this milestone closed and is named here rather than
quietly left.

## 7 — the job object, and the one thing that is still not proved

`a_killed_launcher_takes_its_runtime_with_it` is the first test of the job object, and therefore
the first execution of the reason this crate carries a `#[allow(unsafe_code)]` at all. It starts
an artifact whose runtime is mid-nap, kills the resident launcher, and requires the runtime to go
with it. The probe is deletion — Windows will not unlink the image of a running program — and the
probe's own ability to tell the two states apart is asserted before it is used, so a removal that
succeeded while the runtime ran would fail the test rather than pass it for nothing.

**The console control handler is declined, with a reason.** `ignore_console_ctrl` runs on every
Windows launch, so the handler is installed; what has never happened is an event arriving at a
launcher that installed one. Delivering one needs `GenerateConsoleCtrlEvent` against a process
group the test owns — a Win32 call with no safe counterpart, which would be a second
`#[allow(unsafe_code)]` in the tree, and `CLAUDE.md` requires an ADR before there is one. That is
a decision, not a skip: `docs/adr/0015`, `docs/dev/v1-readiness.md`, `README.md` and
`tests/regressions/e15_…` all say it in as many words, and the E15 regression asserts that the
ADR keeps saying it.

Also in this section, both found by the baseline: the three intra-doc links to `#[cfg(unix)]`
items, and the four dead items in `tests/native.rs`.

## 8 — the CI job launches an artifact instead of probing `erl`

RED in `tests/regressions/e23_the_windows_job_proved_erlang_rather_than_the_launcher.rs`, which
reads the job's steps and requires one to package `hello_ffi` and one to name `build/ginary` and
*compare* a captured `$LASTEXITCODE` against 3. Against the committed workflow both fail and name
every step. The comparison matters: a rule written as `contains('3')` is met by a version number
or a comment, which is the same looseness the old `ci_matrix` assertion had and the reason this
file exists, so the rule carries a test of its own that a script merely mentioning the number
does not satisfy it.

**And the rule is applied at the original site, not only beside it.**
`tests/ci_matrix.rs::the_windows_job_asserts_exit_code_propagation` still read

```rust,ignore
job.contains("halt(3)") || job.contains("ERRORLEVEL") || job.contains("exit-code")
```

over the job's whole text. The rewritten step satisfies that from a *comment*, so leaving it
would have closed the milestone with its own defect intact in the file the plan named. The rule
moves to `tests/common/repo.rs` as `captured_exit_codes` and `compares_a_captured_exit_code` —
the same shared home the `shell_code` fix used — and both sites call it. A fresh RED could not be
staged for this one, because `ci.yml` had already moved by the time it was reached; the RED for
the rule itself was the regression above, taken against the committed workflow.

Two smaller things fell out of that. `exit_code_probe()` looked its step up by
`run.contains("halt(3)")`, and two steps of the job now say `halt(3)` — the probe, and the
packaging step's comment — so it now excludes the one that names `build/ginary` rather than
depending on which comes first in the file. And its documentation called it "the one step in this
repository that checks the Windows exit-code contract end to end", which was never true and is
now plainly not: it is the precondition, and the sentence says so.

The job now mirrors the macOS job: the launcher-only build goes to a target directory of its own
and is named `ginary-stub-<version>-windows-x86_64`; the fixture is copied, given an
`erts = "dir:…"` line pointing at the runtime `setup-beam` installed, and packaged; and the
artifact is run three times — once for `0` with arguments, once for `halt(3)`, and once more warm.
Each comparison is captured, printed and exited on, which is E15's lesson. The bare `erl` probe
stays as a labelled precondition.

**The rewritten step had not run when it was written**, and that is worth keeping in the record
rather than smoothing over. It was asserted, `actionlint`-clean and written against the macOS job
that does the same thing on a runner, and that was all.

It has since run — on somebody else's branch. `feat/windows-end-to-end-launch` (PR
[#10](https://github.com/P4suta/ginary/pull/10)) is an independent E23, worked on Linux in
parallel with this one, and its `windows` job — the same rewrite, differently worded — passed in
9m43s on `windows-2022` in run
[34018931746](https://github.com/P4suta/ginary/actions/runs/34018931746). So the half that needs
a real `erl.exe` is proved: `halt(3)` inside a packaged application does reach `%ERRORLEVEL%`.
It is not proved *by this branch*, which has never been near a runner, and
`docs/dev/v1-readiness.md` keeps booking it as CI-gated until one of the two lands.

The two branches were checked against each other by hand rather than assumed compatible. Their
step spells the artifact `build\ginary\…` where this one spells it `build/ginary/…`, which the
rule above read as two different directories — a rule about how a step was typed rather than
about what it runs, and the same defect class again. `common::repo::names_path` is the fix, and
with it every rule this milestone tightened passes over their workflow too: their bare-`erl`
probe keeps `halt(3)` without naming the artifact directory, so it is still found as the
precondition, and their packaging step captures `$halted` and compares it against 3.

`tests/regressions/e15_the_adr_credited_the_windows_job_with_a_spawn_that_never_ran.rs` failed
when the workflow changed, which is exactly what it was written to do — "the day one of those
premises stops holding, this test fails and points at the sentence to update". Its assertions are
inverted rather than deleted: what it derives from the tree now is that the spawn and the job
object *are* reached, that ADR 0015 says so, and that the console event is still recorded as
unreached.

`tests/windows_build.rs::the_windows_build_task_builds_both_flavors_for_the_windows_triple`
failed too, and for a reason worth the fix: it counted the phrase `cross build` over the whole
task text, comments included, so rewording the paragraph above the task took it from 2 to 4. It
counts the task's code now, through `repo::shell_code`. A rule about what a task runs has to read
what it runs — which is the same defect, in miniature, that this milestone is about.

## 8b — what the first runner and the first review found

The branch was pushed as [#11](https://github.com/P4suta/ginary/pull/11). The whole Linux side
passed first time — both flavors, coverage, the cross-Linux smoke matrix, the clean-room smoke,
all five cross-builds and both macOS jobs — which is the half of this milestone no development
host could check. Three things failed that no local gate could have caught, and each is the same
shape: a rule satisfied by something that is not the thing it names.

**A backtick made the whole step a parse error.** The packaging step printed the arguments it had
just run and quoted them the way this repository's prose quotes things —
`` "…for `0 hello world`" ``. A backtick is PowerShell's escape character, so the trailing one
escaped the closing quote and the string ran on to the next `"` eleven lines later:

```text
ParserError: ...ps1:56
  56 |   Write-Host "::error::expected 3 from the warm run, got $again"
     | The string is missing the terminator: ".
```

A parse error is for the whole script, so the step packaged nothing, started nothing and asserted
nothing — and reported a fault eleven lines past the cause. `actionlint` was clean over it,
because it reads workflow structure and `bash` and does not parse `pwsh`; and the `ci_matrix`
rules were happy, because they read the script as *text* and found a captured code and a
comparison in a script no shell would run. The regression is
`tests/regressions/e23_a_backtick_in_a_pwsh_step_ran_the_whole_step_nowhere.rs`: every committed
`shell: pwsh` step goes through PowerShell's own `Parser`, under the existing
`require_working_pwsh` gate, because the question "will `pwsh` accept this" has exactly one
authority.

**Three review findings, all in code this milestone added.** Taken on their merits rather than
applied:

- *The three facts were not about one command.* `names_path` and `compares_a_captured_exit_code`
  read a step independently, so a step could name `build/ginary`, run `erl.exe`, capture *that*
  code and compare it to 3 — every predicate satisfied, the launcher never started. Which is
  precisely the defect this section is named for, one level up, reintroduced by the rule written
  to remove it. `repo::runs_and_checks` ties them: the variable an invocation names has to hold a
  path under the directory, the capture has to be the next executable line — anything between has
  already overwritten `$LASTEXITCODE` — and the comparison has to be against what that capture
  filled. The negative control is the `erl.exe` step above, and it is the point of the test.
- *`verify` admitted a prefix, not a contract.* `api-ms-win-core-` is the start of an API-set
  contract name and equally the start of any file somebody calls that, so
  `api-ms-win-core-not-a-contract.dll` passed. The loader's documented grammar ends a contract in
  `l<n>-<n>-<n>`, and `is_api_set_contract` now requires it — for both families, since the CRT's
  prefix had the same hole and the `FAMILIES` table exists so the two cannot drift.
- *The rules read comments.* `shell_code` was already in `repo.rs` for exactly that and was not
  being used; the predicates now strip comments and fold case, since PowerShell does. **Declined:
  parsing a PowerShell AST for these rules.** There is no parser in the tree, `CLAUDE.md` forbids
  a dependency this milestone does not use, and `shell_code` covers `pwsh`'s single-line comments.
  Where a real parser *is* the right answer — deciding whether a step is valid PowerShell at all —
  it is `pwsh`'s own, above.

**And `e15`'s matcher accepted the builder.** `command.contains("ginary.exe")` is satisfied by
`& $ginary build`, which is `target/release/ginary.exe` — so a test named
"the windows job starts a packaged artifact" would pass over a job that packaged one and started
nothing. It reads a path under `build/ginary` now. That file had its assertions inverted earlier
in this milestone and the matcher was left as it was, which is its own small lesson about
inverting a claim without re-reading how it is measured.

## 9 — the records

- `docs/dev/v1-readiness.md`, `README.md` (the status matrix, the limitation, and the eight-item
  untested list), `tests/windows.rs`'s header, `mise.toml`'s `build:windows` comment,

- `docs/dev/testing.md` is the file `CLAUDE.md` sends a contributor to before a behaviour change,

  not interchangeable; `tests/common/artifact.rs` follows the host while the reader fixtures ask

## What this leaves

- **A console control event.** Declined above, with the reason and the ADR it would need.
- **`mise run doc` never documents the stub flavor.** `cargo doc --no-default-features` fails on
  an intra-doc link in `src/target.rs`; the gate builds default features only, so a broken link
  in stub-only documentation rots unseen. Found here, out of subject, recorded.
- **The 27 `result_large_err` warnings.** Toolchain drift, a crate-wide change to fix, declined.
- **`mise` cannot provision this host.** Every task that shells out to `cargo` works when run as
  its command line; the task file has never been asked to work on Windows.
- **The launcher's cost is still unmeasured.** No benchmark, no latency budget, and a size budget
  that guards the staged tree and not the artifact. That is the next milestone's subject and the
  measurements it starts from are in the plan this one was written to.
