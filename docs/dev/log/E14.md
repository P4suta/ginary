## RED — the diagnosis, and the invariant re-expressed

### 10 — the diagnosis: (a), a test written in terms of the host

**It is (a): the test encodes premises about the host's socket buffering and its send timeout,
and states nothing about the fixture when they do not hold. It is not (b): the E13 fix is
complete on Windows, and the same Windows job proves it.**

The four pieces of evidence, in order.

**1. The assertion that fired is the deadline, so no fault was recorded at all.** Section 5 has it
verbatim: the panic is at line 103, the `while server.faults().is_empty()` loop, and the target
reports `finished in 34.18s` — the whole of `REPORT_BUDGET` elapsed rather than an early
mismatch. The fixture recorded nothing about that reply within thirty seconds.

**2. A fault list cannot tell the two candidate causes apart.** The test reads one thing: whether
a fault appeared. "The fixture stayed silent about a write that failed" and "no write failed"
produce the same empty list. The test's premise — that a write would fail at all — is a property
of the host that it never checks, so the assertion it makes on Windows is unfalsifiable in the
direction it cares about.

**3. The same reply, through the same code, on the same job, went out whole and reported
nothing.** `e13_the_fixture_server_inherited_its_listeners_non_blocking_mode::`
`a_reply_too_large_for_one_write_is_written_whole` scripts the identical
`Reply::ok(&vec![b'x'; 16 MiB])`, serves it through the identical `write_reply` on a socket
`adopt` prepared, and asserts both that the body arrives with exactly `BULK_BYTES` bytes under
its `Content-Length` and — through `answer_one`, which panics on any recorded fault — that the
fixture reported nothing. That test **passed** on Windows job 100964443199, along with the other
357. If the E13 fix were incomplete there, if `write_reply` still gave up silently under some
condition, that is the test that would have caught it: it is the one that checks the bytes.
It did not, so the write path does not truncate silently on Windows.

**4. The only premise the failing test adds is about the peer, and therefore about the host.**
The two tests differ in exactly one way: the passing one's client holds off for 250 ms and then
reads, the failing one's client never reads. So the extra thing the failing test needs is *"a
blocking write of sixteen mebibytes to a peer that never reads fails within thirty seconds on
this operating system"* — a statement about send buffering and about `SO_SNDTIMEO`, not about
ginary. The passing test knows its premise is the host's and asks first, in
`a_loopback_connection_blocks_before`, "say so rather than passing without it". The failing test
asserts the same class of premise implicitly and never asks. And the probe would not have saved
it either: it fills a **non-blocking** socket and returns at the first `WouldBlock`, which on
Windows is the default sixty-four kilobyte send buffer, while a **blocking** send is buffered by
the stack well past that.

Which of the two Windows behaviours actually occurred — the stack absorbing the whole reply so
that no write ever failed, or a send whose timeout did not end the wait inside the budget —
cannot be told apart from a fault list, and does not need to be: neither is something this
fixture does, and neither changes what the fixture owes. What it owes is two things, and both are
now asserted directly rather than inferred from a stopwatch:

- a write that fails, and is not the peer letting go, is named rather than swallowed — asserted
  over a transport that fails on demand, on every platform, in the same byte;
- a reply's wait is bounded at all — asserted of the socket `adopt` hands over, which is the
  fixture's own decision, rather than of the platform's honouring of it.

No gate is weakened by this, no assertion is deleted and no check is skipped: the claim
`a reply the fixture could not write whole is named, not sent short in silence` is the same claim,
made of the same code, and the replacement still fails against the pre-E13 fixture — see
section 12.

### 12 — the seam, and why it is a stub in this section

Two additions to `tests/common/http.rs`, the fixture the regression is about:

- `pub struct HaltingSink` — a `Write` that takes a stated number of bytes and then fails every
  write with a stated `ErrorKind`, recording what it took. A write that spans the boundary takes
  what is left and reports the number, the way a socket does, so `write_all` reaches the failure
  after a partial write: the exact shape of the defect.
- `pub fn send_reply<W: Write>(sink: &mut W, path: &str, reply: &Reply) -> Option<String>` — the
  reply half of `serve_one` over any writer: write, classify with `after_write`, and answer with
  the fault for the caller to record, or `None`.

`write_reply` becomes generic over `W: Write` (a signature change, no behaviour change) and
`adopt` becomes `pub` (a visibility change, no behaviour change). `serve_one` is untouched in this
section, so nothing that passes today changes.

**`send_reply`'s body in this section is the pre-E13 fixture, on purpose**, marked
`// RED: replaced in GREEN`:

```rust
let _ = path;
let _ = write_reply(sink, reply);
None
```

That is `let _ = stream.write_all(head); let _ = stream.write_all(body);` — write it, discard
whatever the write said, tell the caller there was nothing to record — which is what the module
looked like before E13 and what this regression exists to pin. So the RED run below is at the same
time the proof the brief asks for: **the replacement still fails against the pre-E13 fixture**,
and it fails on the claim rather than on a compile error. GREEN replaces the body with the
classification and points `serve_one` at it.

```rust
pub fn send_reply<W: Write>(sink: &mut W, path: &str, reply: &Reply) -> Option<String> {
    match write_reply(sink, reply) {
        Ok(()) => None,
        Err(error) => match after_write(error.kind()) {
            AfterWrite::Expected => None,
            AfterWrite::Reported => Some(format!(
                "the reply to {path} was not written whole: {error}"
            )),
        },
    }
}
```

A reply that went out whole is `None`; a write the peer refused because it had let go of the body
is `None`, because `after_write` calls that the client's doing and every client of this fixture
does it; every other write failure — [`REPLY_BUDGET`] running out above all, which is `EAGAIN` on
unix and `WSAETIMEDOUT` on Windows — becomes a fault that names the reply it could not send.

**`serve_one` was rewired through it**, which is the half of the change that matters beyond the
test. It had its own copy of the rule:

```rust
if let Err(error) = write_reply(&mut stream, &reply)
    && after_write(error.kind()) == AfterWrite::Reported
{
    record(faults, format!("the reply to {path} was not written whole: {error}"));
}
```

Two statements of one rule is one statement too many: the regression would have pinned the seam
while the server ran the copy, and a later edit to either could have parted them without any test
saying so. The server now calls `send_reply` and records what it hands back, so the code the
regression holds is the code the fixture really runs, and the fault text every `tests/download.rs`
assertion reads is produced in exactly one place.

Nothing else changed. `write_reply` keeps the generic signature RED gave it, with its doc now
naming `send_reply` as the caller that asks `after_write`; `adopt`, `after_write`, `finish_reply`
and the budgets are untouched, so no reply that passed before goes out differently now.

## Fix round 1

A review of the staged tree returned three findings: one high, one medium, one low. All three are
about the *instrument* rather than about `src/`, which is where this milestone's whole change
lives, and the high one says that the re-expression of section 11 gave up coverage rather than
merely restating it. It is right, and this section fixes it.

### 20 — the three findings

**High — the replacement stopped pinning the code the fixture runs.** Section 16 routed
`serve_one` through `send_reply` so that the rule would be stated once, and the seven new tests
call `send_reply` directly over a `HaltingSink`. But `send_reply` only *answers* the question; the
recording was still a separate statement in `serve_one`:

```rust
    if let Some(fault) = send_reply(&mut stream, &path, &reply) {
        record(faults, fault);
    }
```

Nothing held those three lines. A `serve_one` that asked and threw the answer away —
`let _ = send_reply(&mut stream, &path, &reply);` — is the pre-E13 defect exactly, one level up
from where E13 fixed it: a body sent short under a full `Content-Length`, in silence, which every
retry test in `tests/download.rs` reads as a connection that broke. The reviewer ran that mutation
over a copy of the tree and the suite stayed green, while the deleted live test killed it. So the
claim of section 16 — *the code the regression holds is the code the fixture really runs* — was
true of the decision and false of the recording, and section 17's proof could not see the
difference because it grafted the defect into `send_reply`, which both shapes call.

**Medium — the sink hangs the binary on one `ErrorKind`.** `HaltingSink::write` answers its stated
kind for every write once it is full, and `std::io::Write::write_all` retries `Interrupted` for
ever. So `HaltingSink::halting_after(n, ErrorKind::Interrupted)` never returns from a write past
`n` — and `after_write` sends `Interrupted` down its `_ => AfterWrite::Reported` arm, so "an
interrupted write is the fixture's own failure" is precisely the next test somebody writes here.
That contradicts the doctrine `REQUEST_BUDGET`, `REPLY_BUDGET`, `DRAIN_BUDGET` and `WAIT_BUDGET`
state four times over: a stuck thing in this fixture is a failed assertion, never a hung binary.

Reproduced standalone, with the sink's own body and nothing else (`rustc -O`, a sink built with
`halting_after(10, ErrorKind::Interrupted)`, then `write_all(&[b'x'; 100])`):

```console
$ timeout 5 ./hang; echo "exit: $?"
exit: 124
```

124 is `timeout`'s: it never returned, and it printed nothing.

**Low — the two new helpers were undocumented in `docs/dev/testing.md`.** That file enumerates
this fixture down to `adopt`, `after_write` and each budget, and `grep -n "HaltingSink\|send_reply"`
over it returned nothing.
