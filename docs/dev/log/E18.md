check, and the first that starts from a **rebased** branch. E17 opened `ci/release-environment`

`tests/regressions/e18_the_notice_overclaimed_what_repository_scope_exposes.rs` carries two

### 8 — thread 2, `PRRT_kwDOUL26dM6ff3ru`: the environment is not an exclusive ACL

`docs/RELEASE.md` lines 33 to 35 close the argument for the environment with

```text
GitHub enforces that from the other side too: an environment's variables and secrets reach a job
**only when the job declares that environment**, so no other job of any other workflow can read
them by accident.
```

The premise is true and is the whole of what GitHub does. The conclusion is not: declaring an
environment is not a privilege GitHub hands to one job. Any job of any workflow of this
repository may write `environment: release`, and on a ref the deployment-branch policy admits it
is handed the same client id and the same private key. A second reader is one line of YAML away.

What keeps this repository to one reader is this repository's own test —
`no_job_of_any_workflow_reads_the_release_credentials_without_declaring_the_environment` in
`tests/release_workflow.rs`, which walks every scalar of every workflow for either credential
name and holds every site it finds to the rule, with
`tests/regressions/e17_the_release_credentials_were_read_outside_their_environment.rs` pinning
it. That is a real control and worth documenting as one. It is also ours, which is the half the
document dropped: a section that credits the platform with a repository's own discipline is the
section that survives the deletion of the discipline.

`tests/regressions/e18_the_environment_was_credited_with_keeping_other_jobs_out.rs` therefore
asserts both directions — no record claims the exclusivity, and `## One-time setup` names the
control — and then holds the citation against the tree, because a document that names a test by
name is worth exactly as much as that test still being there.

### 11 — thread 3, the fix: the notice is excused by which step it is

`tests/common/release.rs` carried the defect as its only `// RED: replaced in GREEN` marker:

```rust
.filter(|step| step.position != 1 && !step.cond.contains(ABSENT))
```

It is now

```rust
let notice = notice_step(workflow).map(|step| (step.job, step.position));
…
.filter(|step| {
    step.position != 1 && notice.as_ref() != Some(&(step.job.clone(), step.position))
})
```

Two things about the replacement are deliberate.

**The identity is `(job, position)` and not `position` alone.** `WorkflowStep::position` counts
from one *within its job*, and `notice_step` searches every step of the workflow rather than only
the credentials job's. Excusing by a bare position would excuse the credentials job's step *n*
because some other job's step *n* looked like a notice — a second string-shaped hole in the place
the first one was closed.

**Nothing else about the rule moved.** `needs_the_credentials`, the position-one exception and
`steps_that_need_the_credentials_and_are_not_gated` are as RED left them, and `ABSENT` stays
exported because the E5 and E18 regressions assert *about* the notice's condition — the constant
was never the problem, reading a step's identity out of it was.

`a_step_that_is_not_the_notice_does_not_inherit_the_notices_excuse` now reports exactly
`Open the follow-up issue as the App` over
`tests/fixtures/release/a_second_step_guarded_on_absent.yml`, and still reports nothing over the
real `.github/workflows/release.yml`. The rule is one that has been shown to fire.

### 12 — thread 1, the fix: what the environment actually applies

The notice's closing paragraph in `.github/workflows/release.yml` said the environment was worth
using because a repository-scope secret is universally readable. The claim is gone and the reason
is now the two restrictions that are real:

```text
Both belong to the release environment rather than to repository scope, which
applies two restrictions repository scope does not. An environment's values
reach a job only when that job declares the environment, so a job that does
not name it is handed nothing; and they are released only on a ref the
environment's deployment-branch policy admits, which here is the main branch
and the v* tags and nothing else. Neither value is therefore reachable from a
pull request, from a fork, or from any other branch.
```

The brief's "check the whole file" was widened in RED to the four records the sentence reached,
and all four are rewritten:

| record | what it said | what it says |
|---|---|---|
| `.github/workflows/release.yml:111` | a repository-scope secret is universally readable | the declaration binding, then the branch policy |
| `docs/RELEASE.md:29` | the same, as the argument for the setup | the same two restrictions, and what repository scope lacks |
| `docs/dev/log/E17.md:512` | the same, as E17's reason for the section | the same two restrictions, plus a parenthesis recording the correction |
| `tests/release_workflow.rs:820` | the same, inside an assertion message | the same two restrictions |

The rest of `release.yml` was read for the claim rather than grepped for one spelling of it. Its
header comment (lines 11 to 20) already described the binding and the branch policy correctly and
is unchanged; `repository-scoped installation token` at line 123 is about the App token's scope

The E17 record is a past milestone's log, and rewriting one is not free. The paragraph was
corrected rather than annotated because a log is read for what the tree is, not only for what a
milestone did, and a false sentence left standing under a note saying it is false is still the
sentence the next reader quotes; the parenthesis added beneath it says what was there, why it was
wrong and where the correction was made, so nothing is quietly rewritten.

### 18 — finding 1: the citation was thread 2's defect with a new subject

Section 13 replaced *GitHub keeps a second job out* with *our own test keeps this repository to
one reader*, and named
`no_job_of_any_workflow_reads_the_release_credentials_without_declaring_the_environment`. That
test does exactly one thing per site it finds:

```text
assert_eq!(job_environment(&site.workflow, &site.job), ENVIRONMENT, "…declares no `environment: release`…");
```

It constrains **where** a credential may be named — the job naming it has to declare the
environment — and places no bound on **how many** jobs do. A second job that writes
`environment: release` and `secrets.RELEASE_PLEASE_APP_PRIVATE_KEY` satisfies it: the site sits in
a declaring job, the occurrence counts still match, and the suite is green. The only second reader
it turns red is one that does *not* declare the environment, and that one is handed two empty
strings and cannot read the values anyway.

So the sentence promised a bound nobody enforced, and it was worse than the original overclaim in
one respect: `the_one_time_setup_credits_the_test_that_is_the_actual_control` **required** the
citation to be present, so the suite held the false sentence in the document.

The fix is not to soften the sentence. The document is right about what this repository needs; what
was missing is the rule. So the bound became a rule of its own, the document names both halves and
says which half each one covers, and the regression pins the new one against a fixture that breaks
it.

### 20 — GREEN: two rules widened, one rule added

**The step rule now reads every job that can be handed the credentials.** Three ways in, and it
takes all of them, because taking one is how a scan gets narrow enough to miss the bug: a job that
*declares* the environment is handed the values whether or not it names them, the job holding the
credentials check is the one the rule was written about, and a job that *names* a credential is
asking for one however it declared itself. Both exceptions are now by identity — the check found
by its `id:` at the `(job, position)` it sits at, the notice at the one [`notice_step`] found it
at — so neither "position one" nor "contains the absent guard" excuses anything again.

**The bound is a rule.** `jobs_declaring_the_environment(workflows)` collects every job of every
given workflow whose `environment:` is the release one — the jobs GitHub hands the values to,
named or not — and
`exactly_one_job_of_this_repository_declares_the_release_environment` in
`tests/release_workflow.rs` requires exactly one of them across
`yaml_files_under(".github/workflows")`. It passes on the committed tree, where that declaration
appears once, at `.github/workflows/release.yml:37`.
`tests/regressions/e18_nothing_bounded_the_number_of_jobs_that_may_read_the_credentials.rs` pins
it, and hands it the fixture pair so that the rule is one that can be seen to fire rather than one
that has never fired.

**`docs/RELEASE.md` says which half each test covers.** The retraction stays; the paragraph after
it now lists the two tests as a pair and says, of the first, that it bounds where a credential may
be read and not how many jobs read it. A citation that overstates its own test is the defect this
round is about, so the document states the limitation of each half rather than the sum of the two.

**The fixture's guard is asserted before it is trusted.** The central regression reads the
injected step out of the rule's own output and requires it to still carry `ABSENT`, so any edit
that defuses the fixture is a loud failure rather than a silent pass.
