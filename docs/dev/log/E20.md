# E20 — nothing has been released, and the configuration says otherwise

Date: 2026-09-05 · Status: in progress

## Housekeeping

E20 is the first milestone whose subject is a *proposal* rather than a check. `main` is green,
the release path works end to end, and that is exactly the problem: release-please ran, believed
the repository's own record of what it had released, and proposed **0.2.0** for a project that has
never released anything at all. The user is explicit that they do not want to release now, so the
deliverable is a correct proposal — the next release-please run offering **0.1.0** — and not a
release.

This section pins the merge E20 starts after, the branch, the tree, the server-side release state
as the API actually describes it (rather than as the committed files claim it), the Nightly run
dispatched from `main` to prove E19's fixes on the real runners, this machine's toolchain and its
disk, the ways this machine's Bash sandbox misreports the suite, and the gate results as measured
here — so that every later section can attribute a result either to an E20 edit or to something
that was already there. **No product code is touched in this section**, and **no fix is proposed
here**: reading release-please's own documentation and deciding what a never-released repository
should record belongs to the sections that follow.

```console
Running `fuzz/target/x86_64-unknown-linux-gnu/release/payload_read_manifest \
  -artifact_prefix=.../ -max_total_time=30 -rss_limit_mb=4096 \
```

The cause is a difference between the two ways this repository runs the same command. `mise.toml`'s
`fuzz` task creates the generated corpus first — `mkdir -p fuzz/corpus/"$target"` — because

creates neither. libFuzzer refuses a corpus directory that is not there, on all four targets,
before it reads a single seed. The two callers of one command disagreeing about a precondition is
the same shape of defect E19 fixed twice over; it is recorded and left to the milestone that takes
it.

## What release-please actually does, read rather than assumed

Before any file was edited, the two semantics the fix turns on were read out of release-please's
own source and schema rather than guessed. Both are quoted here so a later reader can re-check
them instead of believing this record.

**1 — `0.0.0` in the manifest means "never released", and it is a literal in the code.**
`src/manifest.ts`, in the loop that back-fills a latest release when the GitHub API reported none,
carries the only occurrence of the string `0.0.0` in the file:

```ts
if (
  !latestRelease &&
  this.releasedVersions[path] &&
  this.releasedVersions[path].toString() !== '0.0.0'
) {
  const version = this.releasedVersions[path];
  ...
  releasesByPath[path] = {
    tag: new TagName(version, component, ...),
    sha: '',
    notes: '',
  };
}
```

So a manifest entry of `0.0.0` is the one value that leaves `latestRelease` undefined. Any other
value — `0.1.0` included — is turned into a synthetic release the next version is *bumped from*,
which is exactly how `feat:` commits plus `bump-minor-pre-major` produced 0.2.0 for a repository
with no tags. `docs/manifest-releaser.md` says the same thing from the other side: "The simplest
way to tell release-please the current version for a package it has never released before is to
manually add an entry into `.release-please-manifest.json`" — an entry that asserts a release.

**2 — with no latest release the version comes from the strategy, and the rust strategy starts at
0.1.0.** `src/strategies/base.ts`:

```ts
if (latestRelease) {
  return await this.versioningStrategy.bump(
    latestRelease.tag.version,
    conventionalCommits
  );
}

return this.initialReleaseVersion();
```

```ts
protected initialReleaseVersion(): Version {
  if (this.initialVersion) {
    return Version.parse(this.initialVersion);
  }
  return Version.parse('1.0.0');
}
```

and `src/strategies/rust.ts` overrides it:

```ts
protected initialReleaseVersion(): Version {
  return Version.parse('0.1.0');
}
```

**3 — `initial-version` is a real configuration key, and the rust strategy currently ignores it.**
`schemas/config.json` declares it in `ReleaserConfigOptions`, so it is valid at the root and per
package:

```json
"initial-version": {
  "description": "Releases the initial library with a specified version",
  "type": "string"
}
```

The base strategy honours it; the rust override above does not consult `this.initialVersion`, so
for `release-type: rust` it decides nothing today. Both facts are recorded because both matter:
the key is what states the intent in the file release-please reads, and the strategy is what
actually answers. They agree on `0.1.0`, so neither can move the first proposal on its own — and
the load-bearing change is the manifest, not the key. (The open issue
[#2397](https://github.com/googleapis/release-please/issues/2397) is the same override observed
from the outside, on the `expo` strategy.)

**4 — the changelog updater inserts a section, it does not rewrite one.** Read in fix round 1,
after the review pointed out that this whole section had not read it. `src/updaters/changelog.ts`:

```ts
const DEFAULT_VERSION_HEADER_REGEX = '\n###? v?[0-9[]';
...
updateContent(content: string | undefined): string {
  content = content || '';
  // Handle both H2 (features/BREAKING CHANGES) and H3 (fixes).
  const lastEntryIndex = content.search(this.versionHeaderRegex);
  if (lastEntryIndex === -1) {
    ...
  } else {
    const before = content.slice(0, lastEntryIndex);
    const after = content.slice(lastEntryIndex);
    return `${before}\n${this.changelogEntry}\n${after}`.trim() + '\n';
  }
}
```

The `[` is inside the character class, so `\n## [Unreleased]` is the first match: it becomes
`after`, the generated section is spliced in above it, and the body of `[Unreleased]` is neither
moved nor consumed. release-please does **not** rewrite `[Unreleased]` into a dated section, which
is what `CHANGELOG.md` and `docs/RELEASE.md` said it did. Both now say what it does, and
`docs/RELEASE.md` carries the step that follows: the maintainer clears `[Unreleased]` by hand while
reviewing the release pull request. Fetched from `googleapis/release-please` `main`.

**What follows for this repository.** With `.release-please-manifest.json` recording `0.0.0`, no
tag on the server and `release-type: rust`, release-please has no latest release to bump and
proposes **0.1.0** — the version `Cargo.toml` already carries. Nothing needs to be released for
that to be true, which is the whole point: the deliverable is the proposal.

hypothetical.
