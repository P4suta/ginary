# E22 — the release could not be merged, and a refusal would not say why

Date: 2026-09-06 · Status: GREEN complete

## Housekeeping

E22 has one subject with two halves, and they meet on the same pull request. `main` is green,
every workflow runs, the release path is authored end to end — and the repository cannot cut its
first release. Pull request [#7](https://github.com/P4suta/ginary/pull/7),
`chore(main): release 0.1.0`, is release-please's own proposal, and its CI is red for two reasons
that have nothing to do with each other. Four tests fail because the suite reads "has anything
been released?" from a sentence in a document release-please does not write. A fifth job fails
because `ginary otp repack` reads the GitHub API with no credential and was refused.

Neither is a plumbing accident. The first is a rule stated over the wrong record, and it fails on
the one input it exists to judge. The second is a diagnostic that reports four words for a
condition with a specific cause and a specific remedy, and it reaches a user long before it
reaches CI.

**Nothing is committed, tagged, pushed, merged or released in this milestone.** The release
itself waits on an explicit request, as the house rule says.

### 3 — the four tests, and the one thing they all read

| test | file |
|---|---|
| `the_committed_changelog_names_no_tag_and_claims_no_release` | `tests/regressions/e20_a_dangling_changelog_link_was_pinned_by_its_tag.rs` |
| `the_changelog_has_exactly_one_insertion_point_and_it_is_unreleased` | `tests/regressions/e20_release_please_did_not_rewrite_the_unreleased_section.rs` |
| `the_changelog_claims_no_release_that_has_not_been_cut` | `tests/v1_readiness.rs` |
| `the_manifest_records_what_has_been_released_and_nothing_has` | `tests/version_consistency.rs` |

All four go through `crate::common::version::nothing_has_been_released`, which was

```rust
pub fn nothing_has_been_released() -> bool {
    read(RELEASE_DOC).contains(NO_RELEASE_YET)
}
```

with `NO_RELEASE_YET = "No release has been cut yet."` and `RELEASE_DOC = "docs/RELEASE.md"`.

E20 chose that on an argument worth quoting, because it is half right:

> The tree's own answer to a question no committed file can derive: a tag and a GitHub release
> live on the server, a shallow CI checkout fetches no tags, and `git tag` in a `cargo mutants`
> copy of the tree answers about nothing.

Every clause of that is true of `git tag`. What it misses is that a committed file *does* derive
it. `.release-please-manifest.json` is release-please's record of the last released version, its
`0.0.0` is release-please's own spelling of "never released", `docs/RELEASE.md` already documents
that meaning and `scripts/ci/version-consistency.sh` already reads it that way. It is in the
tree — so the shallow checkout and the `cargo mutants` copy both answer — and it moves in the
*same commit* as the changelog section it has to agree with.

The diff of pull request #7 is two files:

```diff
-  ".": "0.0.0"
+  ".": "0.1.0"
```
```diff
+## 0.1.0 (2026-09-05)
+### Features
+* **stub:** embedded identity marker ...
 ## [Unreleased]
```

The manifest says a release is being cut. The sentence in `docs/RELEASE.md` says none has been.
The suite believed the sentence, and reported a correct changelog as a false claim.

### 4 — the second failure that guard hides

All five guards built on that oracle began `if !nothing_has_been_released() { return; }`. They
were **one-shot**: from the first release onward none of them checks anything, for ever. The
guard `the_work_that_is_done_and_not_released_sits_under_unreleased` — the one that would notice
the phase summary stranded under `## [Unreleased]` after 0.1.0 went out — is among them, and E20's
own log had already named that outcome as the thing to avoid ("filed as unreleased for ever").

There is a third consequence, and it is the one with a horizon. `src/updaters/changelog.ts`
splices the generated section in **above** the first line matching `\n###? v?[0-9[]`, which in
this changelog is `## [Unreleased]` itself. So `[Unreleased]` ends up below the 0.1.0 section —
and it is below the insertion point of the 0.2.0 section too, and the 0.3.0 one, sinking one
place with every release until the section for work that is *not* released is at the bottom of
the file. `the_changelog_has_exactly_one_insertion_point_and_it_is_unreleased` cannot see this: it
stands down before it looks.

### 5 — the third-party read that is not authenticated

`coverage` failed at its repack step:

```text
error: cannot fetch the upstream asset: https://api.github.com/repos/gleam-community/erlang-linux-builds/releases/tags/OTP-29.0.5 answered HTTP 403
```

`src/catalog.rs::release_asset` is the one GitHub API request this project makes; it goes through
`download::get_text`, which sent an `accept` header and nothing else. GitHub allows an
unauthenticated read 60 an hour **by source address** — one address for a pool of hosted runners,
for an office, for anything behind a proxy — and answers over it with 403. `download::retryable`
is 5xx only, correctly, so the run ends on one request and that message.

Two things are wrong with it and both matter to somebody who is not this repository. The read is
anonymous when a token costs one line of YAML. And the message is indistinguishable from a
private repository, a tag that does not exist and a token that is wrong: it names no cause and no
remedy. `grep` over `src/` for `Authorization`, `Bearer`, `ratelimit`, `rate limit` and
`Retry-After` returned nothing at all, and none of the five workflow steps that run `otp repack`
carried any `env:`.

## GREEN

### 10 — the oracle moves to the record

`NO_RELEASE_YET` and `nothing_has_been_released` are **deleted**. The suite's one oracle is
`last_released_version()`, which was already there and already correct: `None` while the manifest
records `0.0.0`, the recorded version otherwise.

`tests/common/version.rs` gains the rules as pure functions over `(text, last_released)`, so that
the state this checkout is not in can be driven from a fixture string — the same reasoning that
gave `VersionRoot` and `GINARY_VERSION_ROOT` their seam:

| function | answers |
|---|---|
| `first_version_header` | the line release-please would insert its next section *above* |
| `sections_claiming_a_release_not_recorded` | headings naming a version past the record |
| `tag_references_not_recorded` | links naming a version past the record |
| `unreleased_section`, `released_section` | which section a body sits under |
| `parse_version`, `version_at`, `heading_version`, `versions_in` | the readers under all four |

`unreleased_section` moved here from `tests/v1_readiness.rs`, and its delimiter changed from "the
next line starting `## `" to "the next *version header*". That keeps `### Added` inside the
section it belongs to and stops at `## 0.1.0`, and it closes the H2-only hole the old private
copy had.

### 11 — the guards, restated over both states

| was | is | now holds |
|---|---|---|
| `the_work_that_is_done_and_not_released_sits_under_unreleased` | `the_unreleased_section_holds_only_work_that_is_not_released` | before a release the body is under `[Unreleased]`; after one it is under the released section and *not* under `[Unreleased]` |
| `the_changelog_claims_no_release_that_has_not_been_cut` | `the_changelog_claims_no_release_the_manifest_does_not_record` | no heading names a version past the record, in either state |
| `the_changelog_links_no_tag_that_does_not_exist` | `the_changelog_links_no_tag_the_manifest_does_not_record` | no link names a version past the record; `[Unreleased]` points at `commits/main` **or** `compare/v<last>...HEAD` |
| `the_changelog_has_exactly_one_insertion_point_and_it_is_unreleased` | `the_unreleased_heading_is_the_first_version_header` | unconditional |
| `the_manifest_records_what_has_been_released_and_nothing_has` | `the_two_version_records_hold_one_release_between_them` | a recorded release equals `Cargo.toml`; no document is read |

The fourth is the one that earns its place. "Exactly one version header" is true only before the
first release. "`[Unreleased]` is the first version header" is true for ever, pins the same
property, and is what catches the sinking described in section 4 — at the release pull request,
where it can still be fixed.

The `[Unreleased]` link rule deliberately accepts **both** spellings. Requiring
`compare/v<last>...HEAD` after a release would oblige a maintainer to rewrite that line every
time; both are honest, and what is not honest — a comparison against a tag the record does not
have — is what the rule refuses.

### 13 — the token, and where it may go

`download::Net` gains `token: Option<Token>`. `Token` is a newtype whose `Debug` is **written
rather than derived** and prints `Token(<redacted>)`; that is the reason the type exists at all,
since `Net` is `Debug` and travels inside the build context. `Net::from_vars` reads
`GINARY_GITHUB_TOKEN`, then `GH_TOKEN`, then `GITHUB_TOKEN` — `gh`'s own precedence, with a
ginary-only name in front of it — and an empty variable is no token, because a workflow that
exports a secret it does not have exports the name with nothing in it and an empty
`Authorization` is refused outright.

Where it goes is three rules, and the tests are the statement of them:

- `get_text` attaches it only when the URL it was **given** starts with `GITHUB_API_BASE`. Before
  the rewrite, deliberately: the question is which service is being read, and
  `GINARY_GITHUB_BASE_URL` answers where that service lives. A mirror of the API is still the API;
  a catalogue document `ginary otp update` was pointed at is not, whatever host it sits on.
- `fetch` attaches none at all. The asset bytes come from a `browser_download_url` that redirects
  to a storage host, so a credential there is handed to a third party for nothing. The test drives
  a `fetch` whose URL *is* under the API base, so the rule cannot be satisfied by the host by
  accident.
- A redirect does not carry it onward. ureq's default is `RedirectAuthHeaders::Never`, which drops
  the header on every redirect rather than on cross-host ones; the test proves the behaviour with
  a 302 rather than asserting the configuration value.

### 14 — the refusal is read

`status_attempt` is the one place a non-2xx becomes an outcome, for both request paths — which
also removes a block that was duplicated verbatim between them. A 5xx is retryable, as before. A
403 or a 429 carrying `x-ratelimit-remaining: 0` or `retry-after` is
`DownloadError::RateLimited`, which names the limit, the delay when the server gave one, and the
three variables a token comes from. Everything else is the plain `Status` it always was.

`retryable` is unchanged. Three asks 200 ms apart do not outlast a limit measured in minutes, and
the answer a user needs is the message rather than a slower failure.

The five workflow steps are handed `GITHUB_TOKEN: ${{ github.token }}`; `contents: read` is
enough for a public repository, and no job's `permissions:` changed. `release.yml` is untouched:
`tests/release_workflow.rs` forbids `github.token` there, and correctly.

The variable names now live in two places, and the pairing is held: `tests/common/github.rs`
carries the list for `tests/ci_matrix.rs`, which reads `.github/` in **both** flavors of the suite
and therefore cannot import a `cli`-gated constant, and
`the_downloader_reads_the_variables_the_workflows_are_held_to` in `tests/download.rs` asserts the
two are equal. Rename the variable in `src/download.rs`, leave the workflows alone, and without
that test the reads go quietly back to being anonymous.

## Fix round 1

One finding, from reviewing E22's own new code. It was a real defect, and it failed in the
direction that passes.

### 15 — a pre-release read as the release it precedes

Both changelog rules are stated over a ceiling, and reading a version out of a heading meant
taking the run of digits and dots and parsing it. What ended the run was allowed to be anything,
because the spellings the rule was written for end it with a space, a `]` or a `)`. Semantic
versioning spells a pre-release with a `-` directly against the digits, so with the manifest
recording `1.2.3`, both

```text
## 1.2.3-rc.1 - 2026-09-05
[1.2.3-rc.1]: https://github.com/P4suta/ginary/releases/tag/v1.2.3-rc.1
```

read as `1.2.3`, were found to be at the ceiling, and passed. A section and a link for a release
nobody cut, reported by neither rule — which is the whole of what the two rules are for.

`tests/regressions/e22_a_prerelease_heading_read_as_the_release_it_precedes.rs` failed on both,
and the fix is `version_at`, one reader for both sides: the digits have to be the *whole* version,
so the character after them may not be a letter, a digit, a `-` or a `+`. The trailing dots of a
`compare/v0.1.0...HEAD` range are trimmed before that character is looked at, which is why a
range still reads. The file's third test drives the five ordinary spellings — `## [1.2.3] - …`,
`## 1.2.3 - …`, `## 1.2.3 (…)`, `## v1.2.3`, `## 1.2.3` — so tightening the rule cannot quietly
stop the scanner reading release-please's own output.

### 16 — three guards that pass, and why they are here

None of these was a defect. Each is a place where the obvious implementation is wrong, so the
correct behaviour is pinned rather than left to be rediscovered.

- **A 403 carrying `x-ratelimit-remaining: 5` is not a rate limit.** Every GitHub answer carries
  that header; it is the *value* that says the budget is gone. A
  `headers.contains_key(...)` reading would send a user to wait an hour for something waiting does
  not fix.
- **A `retry-after` that is an HTTP date is still a rate limit.** The header is defined as seconds
  *or* a date. The delay is what a message can offer and the date is not, but a header this cannot
  parse must not turn the answer back into a bare status: the reason for the refusal is the same.
- **A recorded version that cannot be read covers nothing.** A ceiling that will not parse is not
  a ceiling of infinity. The natural reading goes the other way and would pass every changelog
  there is.

## What this leaves for the release pull request

Two of the four failures are now correct and pass on their merits:
`the_two_version_records_hold_one_release_between_them` and
`the_changelog_claims_no_release_the_manifest_does_not_record`.

The other two — `the_unreleased_heading_is_the_first_version_header` and
`the_unreleased_section_holds_only_work_that_is_not_released` — will be **red on the release pull
request until the maintainer makes the edit `docs/RELEASE.md` step 1 describes**, and that is the
design rather than an unfinished job. Without the edit, the release notes for 0.1.0 are
seventeen commit subjects, the real release notes stay under a heading that says they are
unreleased, and `[Unreleased]` begins the descent to the bottom of the file. The two messages
name the edit; the document numbers it. release-please writes commit subjects and cannot write
prose, so this is work a person does, once, for the release where it matters most.
