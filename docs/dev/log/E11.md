### 14 — cause 17: the fixture server tore down a connection it had just answered

Section 9 left `download::every_attempt_failing_reports_the_url_and_how_many_were_made` without a
cause. It has one.

**The excerpt.** `gh api --allow-escape-sequences repos/P4suta/ginary/actions/jobs/100636537290/logs`,
the whole `tests/download.rs` target:

```text
     Running tests\download.rs (target\debug\deps\download-c6c0640ab79acd0f.exe)

running 23 tests

thread 'every_attempt_failing_reports_the_url_and_how_many_were_made' (752) panicked at
tests\download.rs:255:13:
the last failure is quoted, not summarised: io: An established connection was aborted by
the software in your host machine. (os error 10053)

test result: FAILED. 22 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.83s
```

**What the ledger says.** Twenty-two of the twenty-three passed, and the twenty-two include every
other test that scripts an empty-bodied status — `a_not_found_is_asked_exactly_once_and_names_the_status`
(404), `only_a_server_error_is_worth_asking_again`, `a_server_error_is_asked_again_and_the_second_answer_is_the_file`
(503 then 200). So this is not a rule the server gets wrong every time; it is a race it loses
sometimes. `every_attempt_failing_…` is the test that opens the most connections — three, one
per attempt, because `MAX_ATTEMPTS` is three and every one of them is answered `503` — and the
only one that asserts on the *last* of them. Most chances to lose, least tolerance for losing.

**The cause.** `tests/common/http.rs` finished every reply with

```rust
    write_reply(&mut stream, &reply);
    let _ = stream.shutdown(Shutdown::Both);
```

and then dropped the socket. That is an abortive close. With the receiving half shut down the
stack answers anything still in flight with a reset instead of an acknowledgement, and a reset
tells the peer to discard what it has already buffered. Unix tolerates it, which is why this has
never been visible here: a reset on Linux is delivered *after* the bytes that arrived before it,
so the client reads the reply and only then sees the connection end. Windows does not — the
buffered reply is thrown away, and `10053` is `WSAECONNABORTED`, the local stack reporting that it
aborted a connection it had accepted. `src/download.rs` classifies that as a transport failure,
so the third attempt's `last` quotes the socket error rather than the `503` the server had in fact
already sent.

This was measured rather than assumed, in both directions. A standalone program that reproduces
the shape — server writes, `shutdown(Shutdown::Both)`, drop; client reads — returns the whole
reply on this Linux host every time, including with several kilobytes of unread request still in
the server's receive queue:

```console
$ ./exp
OK read 74 bytes: "HTTP/1.1 503 Service Unavailable\r\nContent-Length: 0\r\nConnection: close\r\n\r\n"
```

so there is no Linux symptom to assert on, and a test that watched the wire would pass here and
prove nothing. The rule is what is portable, so the rule is what the test pins.

**The fix RED prepares.** The graceful close every HTTP/1.1 server that sends `Connection: close`
performs, in this order: write the reply, shut down the *sending* half only so the peer sees the
end of the body, read until the peer closes, and only then let the socket go. A close that
follows the peer's own close cannot reset anything, because nothing is left in flight to reset.
`tests/common/http.rs` gains three things:

| where | rule | RED body |
| --- | --- | --- |
| `tests/common/http.rs` | `REPLY_SHUTDOWN` | `Shutdown::Both`, the abortive close |
| `tests/common/http.rs` | `DRAIN_BUDGET` | finished: the bound on waiting for a peer that never closes |
| `tests/common/http.rs` | `answer_one(stream, routes)` | finished: the server's own loop body, exposed |

`finish_reply` carries the `// RED: replaced in GREEN` comment and is
`stream.shutdown(REPLY_SHUTDOWN)` and nothing else, so today's behaviour is unchanged and the
failing assertion is the rule.

**The test.** `tests/regressions/e11_the_fixture_server_tore_down_a_connection_it_had_just_answered.rs`,
two tests, both on Linux:

- `a_finished_reply_closes_the_sending_half_and_not_both` — the rule itself: `REPLY_SHUTDOWN` is
  `Shutdown::Write` and is not `Shutdown::Both`.
- `the_server_lets_go_of_a_connection_only_after_the_client_has` — the behaviour, and the half
  that is observable here. The test accepts a connection itself, answers it on a thread through
  `answer_one`, reads the whole `503` back, and then asserts that the serving thread has *not*
  finished: a server that has already let go is one whose close can reset a reply the client has
  not read yet. It then closes the client and asserts the thread finishes within `DRAIN_BUDGET`,
  so one client that never closes cannot stall every request after it, and that the request was
  still recorded exactly once.

The fix was tried locally and reverted, to be sure the tests are reachable and that draining does
not deadlock a real client: with `REPLY_SHUTDOWN = Shutdown::Write` and a bounded read-to-EOF in
`finish_reply`, both new tests pass and `cargo test --features fault-injection --test download`
is 23 passed, 0 failed in 0.67s — no stall, and `Reply::Truncated` and `Reply::Hangup` still end
the way the client detects. The working tree is back to the RED body; that change belongs to
GREEN.

### 18 — the two rules RED left stubbed

**`common::tools::require_posix_shell`** (cause 13). The body was
`Some(Path::new("bash"))` — a `PATH` lookup that never reports an absence and that resolves on a
Windows runner to `C:\Windows\System32\bash.exe`, the WSL launcher, which exits `1` with nothing
on either stream. It is now the question it was always meant to be: is there a file at
[`POSIX_SHELL`], asked by absolute path, answered `Some` when there is, and a printed
`skipping: no POSIX shell at /bin/sh` — a panic under `GINARY_REQUIRE_TOOLCHAIN=1` — when there is
not.

`POSIX_SHELL` is a new constant in `tests/common/tools.rs` rather than a re-export of
`ginary::native::HOOK_SHELL`, because `native` is a `cli`-only module and one of the two tests
this gate serves, `the_notice_script_exits_zero_under_the_shell_that_runs_it`, is compiled into
both feature flavours. The two are held equal by the RED test itself, which asserts that what the
gate answers *is* `HOOK_SHELL`, so a change to one and not the other fails a test rather than
drifting.

Both call sites now use it: `c4_a_hook_token_was_pasted_unquoted::a_hook_is_handed_its_output_directory_as_one_word`
(which runs the hook through `/bin/sh` and failed at the spawn) and
`release_workflow::the_notice_script_exits_zero_under_the_shell_that_runs_it` (which still runs
the block under `bash -e -o pipefail`, because that is what GitHub runs it under, but only on a
host whose `/bin/sh` says the `bash` on `PATH` is a shell).

**`common::http::REPLY_SHUTDOWN` and `finish_reply`** (cause 17). `REPLY_SHUTDOWN` is
`Shutdown::Write`, and `finish_reply` performs the graceful close in the order section 14 sets
out: write the reply, shut down the sending half so the peer sees the end of the body, read to
EOF so the close follows the peer's own, and only then let the socket go. The read is bounded by
`DRAIN_BUDGET` and by a `set_read_timeout` recomputed each pass, so a client that never closes is
one slow request rather than a hung binary; a timeout, a reset or a failure to set the timeout all
end the wait, because none of them leaves anything further to wait for.

`--test download` is 23 passed, 0 failed in under a second, so draining deadlocks neither
`Reply::Truncated` nor `Reply::Hangup`.

### 24 — a sentence with two NUL bytes in it (behavioural)

**The defect.** `native::inspect_object_bytes` and `native::describe_object` answer the same
condition — a file that begins `MZ` and carries no PE signature behind it — with what was meant
to be the same sentence, written out twice. The older one spells the signature `` `PE\\0\\0` ``,
a Rust escape for the four characters a reader sees. The one this milestone added spells it
`` `PE\0\0` ``, a Rust escape for *two NUL bytes*. That message is the one on the deep-check
path: `verify::verify_with` puts it in `Issue::UnreadableObject`, whose `Display` prints it into
the rendered findings table, and `report::collect_elf_deps` turns the same error into a
`SizeReport` warning. Two raw NULs on the user's terminal, and two ` ` escapes in `--json`.

**The test.** `tests/regressions/e11_a_pe_sentence_carried_two_raw_nul_bytes.rs`, two cases: the
sentence holds no control character, and the two readers of the one condition say the same thing.

```text
---- e11_a_pe_sentence_carried_two_raw_nul_bytes::the_sentence_a_dos_program_gets_holds_no_control_character ----
the sentence is printed to a terminal and serialised into JSON, so a NUL in it is a defect and
not a spelling: "it begins with the DOS magic `MZ` and carries no `PE\0\0` signature behind it,
so it is not a PE object"

---- e11_a_pe_sentence_carried_two_raw_nul_bytes::the_two_readers_of_the_same_condition_say_the_same_thing ----
assertion `left == right` failed: one condition, one sentence, spelled in one place
  left: "it begins with the DOS magic `MZ` and carries no `PE\\0\\0` signature behind it, ..."
 right: "it begins with the DOS magic `MZ` and carries no `PE\0\0` signature behind it, ..."
```

(The `right` half is where the two NUL bytes are; the panic printer escapes them back.)

**The fix.** `src/native.rs` gains `const NOT_A_PE_OBJECT`, spelled once with the backslashes
escaped, and both call sites read it. Two spellings of one sentence is what let them drift.

**The test.** `tests/regressions/e11_an_import_table_that_would_not_parse_read_as_no_imports.rs`,
which points the import data directory at RVA `0x9000` — past the `0x2000` the optional header
gives as the size of the image — and asserts `Unreadable`; plus the other side of the rule, that
a PE with an empty import directory is still a readable object that needs nothing.

```text
---- e11_an_import_table_that_would_not_parse_read_as_no_imports::an_import_table_the_reader_cannot_follow_is_unreadable_and_not_empty ----
a PE whose import directory falls outside every section is a file nobody could read; answering
that it needs nothing reports the absence of dependencies where what happened was the absence of
a reader for them
```

**The fix.** `let imports = file.imports().map_err(|source| ObjectError::Unreadable { .. })?;`.

### 26 — the one allowlist entry with an upper-case suffix (behavioural)

**The defect.** `verify::needed_is_allowed` sends a name that is not an exact match to a
case-insensitive arm, and that arm decides whether an allowlist entry is a Windows library with
`known.ends_with(".dll")` — a case-*sensitive* test applied to the entry itself.
`WINDOWS_NEEDED_ALLOWLIST` holds `IPHLPAPI.DLL`, and `"IPHLPAPI.DLL".ends_with(".dll")` is
`false`, so that entry never reached the comparison beside it. An import table spelling
`iphlpapi.dll` — a spelling Windows treats as the same file, and which the module's own
documentation promises is matched case-insensitively — raised a spurious `UnexpectedNeeded`
finding and made `ginary verify` exit non-zero. The sibling rule in `doctor::is_c_runtime` does
it correctly, so the two halves of one platform rule disagreed.

**The test.**
`tests/regressions/e11_a_dll_the_import_table_spelt_in_lower_case_was_unexpected.rs`: every entry
of the list in its own spelling, all-lower and all-upper; the Universal CRT family in both; and
the seam, that a narrowed allowlist still admits nothing.

```text
---- e11_a_dll_the_import_table_spelt_in_lower_case_was_unexpected::every_windows_library_is_admitted_in_every_spelling_of_its_name ----
a PE import table records whatever spelling the linker was handed, and "iphlpapi.dll" is
"IPHLPAPI.DLL"
```

**The fix.** The suffix is asked about case-insensitively too:
`known.to_ascii_lowercase().ends_with(WINDOWS_LIBRARY_SUFFIX)`. The guard stays, because it is
what keeps the arm Windows-only and keeps an allowlist narrowed to `&[]` admitting nothing.

### 27 — a mixed tree said nothing about the half it could not read (behavioural)

**The defect.** Section 14's new rule — a tree of objects the ELF stripper cannot read is a
*reported* skip and not `NothingToStrip` — only consulted its tally inside
`if natives.is_empty()`. After that block the tally was never read again, so a tree holding one
ELF beside twenty PE or Mach-O objects stripped the one and said nothing at all about the twenty:
`ElfOutcome::Stripped`, no warning. That is the same silence the rule exists to remove, one
branch over, and the foreign-machine rule immediately below it already has both halves —
`Skipped` when all of them are foreign, a warning when only some are.

**The test.** Two cases added to
`tests/regressions/e11_a_tree_of_objects_the_stripper_cannot_read_was_silent.rs`: a tree holding
the running test binary plus two PE objects, and the other side of the rule, a tree the stripper
reads whole warning about no container at all. Both stand aside on a host that does not write
ELF, for section 20's reason.

```text
---- e11_a_tree_of_objects_the_stripper_cannot_read_was_silent::a_tree_that_holds_both_says_out_loud_what_it_could_not_read ----
the two objects that were left alone are said out loud, the way the cross-machine rule beside
this one says so: []
```

**The fix.** The sentence moves into `strip::unreadable_sentence`, and the mixed tree pushes it
as a warning after the `natives.is_empty()` block. One sentence, two places, the same words.
