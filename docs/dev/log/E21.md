### 4 — what run 33969332537 proved, and what it exposed underneath

E19 fixed two failure families it could only reason about from logs, and neither fix could be
proved on this machine: the mutation copy and the nightly toolchain are the runners' business. The
Nightly run dispatched from `main` after E19 merged is the proof, and it is recorded here as
E21's premise because every item in E21's second half descends from it.

**Both E19 fixes did what they were written to do.**

- *Mutants.* `cargo mutants` builds and tests inside a copy of the tree that carries no `.git`, and
  every repository-property test used to ask `git check-ignore` a question it could not answer
  there, so each shard died in its baseline and no mutant was ever run. **All seven shards printed
  `ok Unmutated baseline`**, each within four minutes of starting — `trailer` 28 mutants,
  `appfile` 207, `cache` 203, `closure` 98, `launch` 104, `payload` 91, `verify` 95. No earlier
  Nightly run has ever printed that line. `require_git_work_tree` works on the runners.
- *Fuzz.* Naming `--target x86_64-unknown-linux-gnu` stopped the sanitizer being built against the
  statically linked musl libc that `cargo-fuzz`'s prebuilt archive is compiled for. All four
  targets now build and are actually launched.

**And underneath each of them stands something E19 could not see.** Three things, and the third is
the valuable one:

1. **The fuzz corpus directory does not exist.** All four shards now reach libFuzzer and exit `1`
   on its first line: `ERROR: The required directory "fuzz/corpus/<target>" does not exist`.
   `mise.toml`'s `fuzz` task runs `mkdir -p fuzz/corpus/"$target"` before the command because
   `fuzz/corpus/` is where *new* inputs land and git tracks no empty directory;
   `.github/workflows/nightly.yml` passes the identical two directories and creates neither. Two
   callers of one command disagreeing about a precondition — the same shape of defect E19 fixed
   twice. Fixing the workflow is not enough on its own; the two ways of running the fuzzers have to
   be pinned so they cannot drift apart again.
2. **The mutants shards cannot finish.** A mutant costs about 3.5 minutes (≈39 s build + 171 s
   test), so shards of 91 to 207 mutants need five to twelve hours against `timeout-minutes: 90`.
   `appfile` died on `The runner has received a shutdown signal`; `cache`, `closure`, `launch`,
   `payload` and `verify` were `cancelled` at the cap, having reported survivors so far and never a
   total. A gate that cannot finish is not a gate, and `cancelled` is not an answer. E21 has to
   decide what an honest nightly mutation pass is and say plainly what it covers and what it does
   not.
3. **A real coverage gap the one shard that finished actually found.** `trailer` ran to completion
   and failed on its own terms: `28 mutants tested in 50m: 8 missed, 18 caught, 2 unviable`. Seven
   of the eight survivors are in `src/trailer.rs::read_exact_at` — the short-read loop at `:235`
   and `:238`, and the `error.kind() == ErrorKind::Interrupted` match guard at `:248` — and the
   eighth swaps `|` for `^` in `read_u64` at `:265`. A short read and an interrupted read are
   exactly what a real `pread` does under load, and this is the launcher path, where `CLAUDE.md`
   forbids a panic and requires a numbered exit code. Tests that kill those mutants are E21's, and
   if they find the code wrong the code changes too. The shard's caught percentage before and after
   is reported in that section.

### 10 — the trailer's positional read, and the seam that makes it testable

`src/trailer.rs::read_exact_at` existed twice, once behind `#[cfg(unix)]` and once behind
`#[cfg(windows)]`, and the Windows copy carried the short-read loop `cargo mutants` reported seven
survivors in. Two things follow from that shape, and both of them are why the loop was never
tested. The loop is not compiled on the machine the mutation shard runs on, so every mutant inside
it survives by construction. And neither copy can be handed a reader that answers the way a real
`pread(2)` under load answers — fewer bytes than were asked for, or `EINTR` — because both
take a `&File`, and no file on a test machine does either on demand.

So the trait is the seam:

```rust
trait ReadAt {
    fn read_at(&self, buffer: &mut [u8], offset: u64) -> std::io::Result<usize>;
}
```

`File` implements it once per platform — `pread` on unix, `seek_read` on Windows, three lines each
— and one `fill_exact_at`, compiled everywhere, holds the loop. `read_exact_at` is now a single
cfg-free function that calls it, so `crate::payload::locate` and `Trailer::read_from` are unchanged
at their call sites.

**What the RED body does.** It reads once and, if the answer is shorter than the buffer, reports
the end of the file:

```rust
let read = reader.read_at(buffer, offset)?;
if read != buffer.len() {
    return Err(std::io::Error::new(std::io::ErrorKind::UnexpectedEof, SHORT_FILE));
}
Ok(())
```

It is deliberately not a placeholder. It never answers `Ok` with a buffer it did not fill, so no
caller can read a trailer out of uninitialised bytes; a truncated artifact is still
`UnexpectedEof`, which is what the suite already asserts; and on a regular file a 64-byte `pread`
answers 64 bytes, so the existing 2050 tests are unaffected. What it does *not* do is the three
things the five tests below demand, and it is replaced in GREEN.

**And one survivor that no test can kill.** The eighth mutant, `|` replaced by `^` in `read_u64`'s
fold, is an **equivalent mutant**. `value << 8` leaves the low eight bits zero, so
`(value << 8) | byte` and `(value << 8) ^ byte` are equal for every byte and every value; no input
distinguishes them, and a test that claimed to kill it would be asserting something else.
The honest answer is to remove the operator rather than to chase it — `u64::from_le_bytes` over a
copied array reads the same eight bytes and generates no `|` for the mutation to replace — and
that is a GREEN change, not a test. What RED adds is the characterization test that makes the
rewrite provably a rewrite:
`trailer::tests::a_u64_is_read_from_eight_little_endian_bytes_and_every_byte_counts` passes before
and after, and is labelled in the source as not being RED evidence.

### 17 — thread `PRRT_kwDOUL26dM6flP6o`: a quoted command substitution hid a removal

**Verdict: correct, and it was the one that mattered. Fixed.** `crate::common::mise::segments`
stopped splitting inside `'…'` and `"…"`. That is right for a separator — `echo "a; b"` is one
command — and wrong for a substitution: bash runs a `$( … )` and a `` ` … ` `` wherever they
appear and puts the quotes round their *output*. So `echo "$(rm -rf target/stubs)"` read to every
rule in `cleaner_violations` as one `echo` with one text argument, and `removed_paths()` answered
`["target/debug"]`. Four spellings were checked and all four were approved before the fix: the
plain one, `kept="$(rm -rf dist/otp)"`, `echo "$(find target/stubs -type f -delete)"` — which
walks round the verb allowlist as well — and the backtick spelling.

The fix reads a command substitution as commands wherever it is written. Its opening and closing
are segment boundaries, and the quoting outside it does not reach in; when it closes, the quoting
outside comes back. Two exceptions are deliberate and both are exercised by the committed cleaner:
a substitution inside `'…'` is literal, and `$(( … ))` is arithmetic, stepped over whole by
parenthesis depth because `echo "clean:cache: reclaimed $(( (before - after) / 1024 )) MiB"` nests
one. Splitting an argument round its substitution leaves the two halves of that argument behind —
`echo "` and `"` — so `verbs` now drops the quote characters from a word's edges and a word that
was nothing but quotes is not a verb.

`a_separator_inside_a_plain_quoted_string_is_still_text` is the calibration and it passed before
and after: the fix is "read inside a substitution", not "stop reading quotes", and the committed
cleaner's own diagnostic — one `echo`, one `;`, one mention of a removal it does not perform — is
still one command that removes nothing. `the_committed_cleaner_still_passes_the_rule_it_is_held_to`
and the `clean_cache_plan` snapshot are unchanged.

### 23 — the trailer survivors, and the loop that was never compiled where it ran

**Job:** the one shard of run 33969332537 that finished:
`28 mutants tested in 50m: 8 missed, 18 caught, 2 unviable`. Twenty-six viable, eighteen caught —
**69%**.

Seven of the eight survivors were in `read_exact_at`: the short-read loop at `:235` and `:238` and
the `error.kind() == ErrorKind::Interrupted` match guard at `:248`. **Both reasons they survived
are structural, and neither is a missing assertion.** `read_exact_at` existed twice, once behind
`#[cfg(unix)]` and once behind `#[cfg(windows)]`, and the loop was in the Windows copy — not
compiled on the machine the shard runs on, so every mutant inside it survives by construction.
And neither copy could be handed a reader that answers the way a real `pread(2)` under load
answers, because both take a `&File` and no file on a test machine returns a short count or
`EINTR` on demand.

So the seam is a trait. `ReadAt` has one method, `File` implements it once per platform — `pread`
on unix, `seek_read` on Windows, three lines each — and one `fill_exact_at`, compiled everywhere,
holds the loop. `read_exact_at` is a single cfg-free function that calls it, so
`crate::payload::locate` and `Trailer::read_from` are unchanged at their call sites. Five unit
tests drive a scripted reader through it: four sixteen-byte answers fill sixty-four bytes; each
read starts where the last one stopped, asserted as `(30,40) (40,30) (50,20) (60,10)` rather than
four reads at the base offset; a zero-byte answer is `UnexpectedEof` and only after a *second*
read, because a short answer is not the end of a file; `EINTR` is retried; and any other error
travels as it arrived, because reporting a `PermissionDenied` as `UnexpectedEof` would tell a
reader their artifact is truncated when it is not.

**The code was not wrong, and one survivor could not be killed.** The eighth, `|` replaced by `^`
in `read_u64`'s fold, is an *equivalent* mutant: each `value << 8` leaves the low eight bits zero,
so the two operators agree on every byte and every value and no input distinguishes them. A test
that claimed to kill it would be asserting something else. The honest answer is to remove the
operator rather than chase it, so `read_u64` now copies the eight bytes into an array and calls
`u64::from_le_bytes` — no `<<` and no `|` for a mutation to replace. The copy is a `zip` rather
than `copy_from_slice`, which panics on a length mismatch, or an index, which panics out of range:
neither can happen at the two offsets the layout fixes, and neither is spelled in a way that could.
`a_u64_is_read_from_eight_little_endian_bytes_and_every_byte_counts` passed before and after, which
is what makes the change provably a rewrite rather than a change of reading.

### `the_shards_of_a_module_cover_all_of_it` — shard numbering is zero-based

**What it asserted.** That the shard indices of a module divided `n` ways are `1..=n`:

```rust
assert_eq!(*indices, (1..=divided).collect::<Vec<_>>(), …);
```

**Why it is wrong.** `cargo mutants` numbers a division from zero. The first matrix written to the
test's expectation was rejected by the tool itself, before a single mutant ran:

```console
$ cargo mutants --file src/trailer.rs --shard 1/1 --timeout 420 --features fault-injection
error: invalid value '1/1' for '--shard <SHARD>': shard k must be less than n
```

`cargo-mutants 27.1.0`, which is the version `.github/workflows/nightly.yml` pins. So the complete
division `--shard k/n` runs is `0/n` to `n-1/n`, and a matrix written `1/n … n/n` would have every
one of its jobs fail on an argument error while the test that was meant to guard the division
reported it complete. The tool's own `--help` gives `1/4` as its example, which is where the RED
expectation came from; the validator is the authority and it disagrees.

**The correction.** The expectation is `(0..divided)`, the assertion message names the convention,
and `crate::common::nightly::shard_of` now defaults an undivided command to shard `0` of `1` rather
than `1` of `1` — which is the same statement about the same numbering, and keeps a `cargo mutants`
with no `--shard` reading as the one complete shard it is. What the test *holds* is unchanged: the
shards of a division must be all of it, and the modules the matrix mutates must be exactly the
modules the measured record covers. It refuses a matrix missing `0/6` exactly as it refused one
missing `1/6`.

behind and a word that is nothing but a quote is not a verb. `removed_paths` was left comparing
the raw word:

```rust
let mut words = segment
    .split_whitespace()
    .skip_while(|word| CONTROL_WORDS.contains(word));
if words.next() != Some("rm") {
    continue;
}
```

Two readers of one grammar, and after section 17 two spellings of one word. Bash strips the quotes
round a command word before it looks the word up, so `'rm' -rf target/stubs` is an ordinary
removal. To `verbs` it was the allowed verb `rm`; to `removed_paths` it was no removal at all. Every
rule in `cleaner_violations` then passes — the plain `rm -rf target/debug` beside it keeps the
removal list non-empty, no removal is a kept tree because the one that is never enters the list,
the verb is on the allowlist, and the prologue supplies the `cd` and the root check — so the guard
approves a cleaner that deletes the five cross-built stubs. Before section 17 the same case was
refused, for the wrong reason: `verbs` answered the untrimmed `'rm'`, which is not on the
allowlist. Neither `tests/regressions/e20_a_removal_the_cleaner_rule_could_not_see.rs` nor
`e21_a_quoted_command_substitution_hid_a_removal.rs` quotes a verb, so nothing in the suite saw
it.

**The test, watched failing first.**
`tests/regressions/e21_a_quoted_verb_walked_around_the_cleaner_guard.rs` drives
`cleaner_violations` and `removed_paths` over the committed prologue plus four spellings —
`'rm' -rf target/stubs`, `"rm" -rf dist/otp`, a quoted `rm` inside a quoted substitution, and a
quoted `rm` after an `&&` — and holds a calibration case that a quoted *argument* still names the
path inside the quotes.

### 30 — the residual `--timeout` does not bound

`--timeout 420` is a cap on one `cargo` invocation, not on a shard. Thirty-five mutants that all
hang cost about four hours against `timeout-minutes: 150`, which is the failure mode section 22
set out to remove, and the budget test multiplies shard size by the measured *average* so it
cannot see that tail. Bounding it would mean either a `--timeout` of about 257 seconds — 1.5 times
the measured test time, which would start reporting slow mutants as timeouts — or roughly twice as
many shards, and neither is paid for by a failure anybody has seen.

So the pass is bounded in expectation and not in the worst case, and that is now written down
where a contributor reads what the pass proves: `docs/dev/testing.md`, in the "does not cover"
list, with the arithmetic and with what paying to close it would cost. The workflow comment says
the same thing beside the budget it qualifies. A residual somebody can read is a decision; an
unstated one is a surprise.

### 33 — a read that answered a zero-padded number

Section 23's rewrite of `read_u64` removed the `<<`/`|` fold, which was right, and left a runtime
offset:

```rust
for (byte, source) in bytes.iter_mut().zip(raw.iter().skip(offset)) {
```

`zip` stops at whichever side runs out. For `offset > 56` that is the slice, the missing high
bytes read as zero, and the function hands back a quietly wrong number where the fold would have
panicked. Not reachable today — both call sites pass the two constants the 64-byte layout fixes —
but CLAUDE.md's rule is that skipping is a reported decision or an error, never a default, and a
zero-padded answer is neither.

The offset is now a const parameter with a `const { assert!(AT + 8 <= 64, …) }`, so an offset that
cannot yield eight bytes is a compile error for every call there will ever be. Demonstrated rather
than asserted:

```console
$ # read_u64::<56> in the unit test temporarily changed to read_u64::<57>
$ cargo test --lib trailer
error[E0080]: evaluation panicked: a trailer field starts within the 64 bytes and has eight of them
   --> src/trailer.rs:326:9
    | evaluation of `trailer::read_u64::<57>::{constant#1}` failed here
note: the above error was encountered while instantiating `fn trailer::read_u64::<57>`
```

The unit test gains `read_u64::<56>` — the last offset the layout has room for — beside the two
the parser uses and the reserved one. The `zip` stays: `copy_from_slice` panics on a length
mismatch and an index panics out of range, and neither may be spelled on the launcher path.
