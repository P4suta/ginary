### 11 — the diagnosis

**The cause is one line of `tests/common/http.rs`, and it produces three separate silent
failures.** `TestServer::start` puts its listener into non-blocking mode so the accept loop can
poll its stop flag, and then serves whatever `accept` hands back:

```rust
listener.set_nonblocking(true).expect("a non-blocking listener");
...
Ok((stream, _)) => serve_one(stream, &routes, &mut answered, &served),
```

POSIX says an accepted socket does **not** inherit the listening socket's `O_NONBLOCK`, so on
unix `serve_one` is handed a blocking connection and every read waits for the bytes it was
promised. Winsock says the opposite: the socket `accept` returns carries the properties of the
socket it was accepted from, non-blocking mode included, and `std`'s Windows implementation is a
bare `accept()` that does nothing to reset it
(`library/std/src/sys/net/connection/socket/windows.rs`, `Socket::accept`) while the unix one
goes through `accept4`. On Windows the fixture therefore serves a **non-blocking** socket, and it
discards every I/O error it gets:

| site | what it does with an error | what that becomes on Windows |
| --- | --- | --- |
| `read_request` | `.ok()?` — answers `None` | a request that had not arrived by the time `accept` returned is neither recorded nor answered; the client's attempt dies in the transport and the fixture's own count is short by one |
| `write_reply` | `let _ = stream.write_all(..)` | a body larger than one non-blocking write can take is truncated, and the client sees the transport failure the retry rule exists for |
| `finish_reply` | `Err(_) => break` after `set_read_timeout` | a timeout means nothing to a non-blocking socket, so the first read answers `WouldBlock`, the drain takes that for the peer letting go, and E11's graceful close never happens on the one platform it was written for |

That first row is `left: 2, right: 3`, twice. It is also the *only* way a fixture in blocking mode
can lose a request that a client certainly sent: `read_request` answers `None` only for a read
that failed or a peer that closed, and `ureq` does neither between opening a connection and
writing its request line. It explains every fact section 6 recorded — the count is short by
exactly one, `Exhausted { attempts: 3 }` and `last` containing `503` still hold because the
*client* did keep its promise and the attempt that was lost was not the last one, the whole target
still finishes in 0.83 s because a lost attempt fails at once rather than timing out, and the
result is different on every run because `accept` wins or loses that race per connection. It also
explains why E11's fix appeared to work and then stopped: on Windows the drain it added has never
run, so both the green run and the two red ones were luck.

**The second failure is the same cause, plus one defect of its own.**
`a_document_larger_than_the_bound_is_refused_rather_than_read_into_memory` failed on the same
sentence for the same reason — but it only had three connections to lose because `get_text` asks
three times for a document it can never accept. `text_once` classifies every failure of
`read_to_string` as retryable, and the `MAX_TEXT_BYTES` limit fails that read exactly as a broken
connection does, so four mebibytes and one byte are transferred, refused, backed off from and
transferred again, twice, before the reader reports `Exhausted`. The retry rule's own reason for
not retrying a 4xx — "a body that is not there will not be there on the third ask, and retrying it
only slows the error down" — applies word for word to a body that is over the bound. The honest
rule is that the bound is an answer, so E13 adds `DownloadError::TooLarge { url, limit }` and the
document is asked for exactly once.

mode `TestServer::start` uses, accepts through the same polling loop, and then calls

fixture and what POSIX's does not. They therefore fail on Linux, for the Windows reason, and they
are `cfg`-free, so both flavors of the suite carry them.

### 15 — the fixture decides the mode of the connections it serves

`tests/common/http.rs` accepted from a listener it had put into non-blocking mode and served
whatever `accept` handed back, which is a *blocking* socket on unix and a non-blocking one on
Windows (section 11). The fix is one function, called first in `serve_one` so that both the
server's own loop and `answer_one` go through it:

```rust
fn adopt(stream: &TcpStream) {
    stream
        .set_nonblocking(false)
        .expect("a blocking connection, whatever mode `accept` handed one over in");
    stream
        .set_read_timeout(Some(REQUEST_BUDGET))
        .expect("a bounded wait for the request");
    stream
        .set_write_timeout(Some(REPLY_BUDGET))
        .expect("a bounded wait for the reply to be taken");
}
```

The two waits this opens up are bounded rather than left to hang, for the reason `DRAIN_BUDGET`
already gives: this fixture serves one connection at a time, so a peer that connects and then says
nothing, or one that stops reading mid-reply, would otherwise stall every request after it.
`REQUEST_BUDGET` and `REPLY_BUDGET` are five seconds each — two orders of magnitude past anything
a client of this fixture does, and short enough that a stuck one is a slow test rather than a hung
binary. Nothing is silently skipped: a socket that cannot be put into that mode panics with the
reason, because serving it in whatever mode it arrived in is exactly the defect being closed.

`finish_reply` is untouched. It still sets its own read timeout from the remaining `DRAIN_BUDGET`
and still waits for the peer's close — but now on a blocking socket, where a timeout means what it
says, so E11's graceful close runs on Windows for the first time.

### 16 — the bound is an answer, asked for once

### 27 — the bound counted the bytes on the wire, not the bytes in memory

The review's first finding, and the only one that reaches a user. `MAX_TEXT_BYTES` is the bound

`ureq` puts the limit given to `into_with_config().limit(..)` at the *bottom* of the body chain:
`ureq-3.4.0/src/body/mod.rs:735` builds
`MaybeLossyDecoder<CharsetDecoder<ContentDecoder<LimitReader<..>>>>`, so the limit counts what came
off the socket and the gzip decoder inflates afterwards. Nothing at the call site turned that
decoder off, and nothing asked it to be there: the `gzip` feature is on in `Cargo.toml`, and
`ureq-3.4.0/src/run.rs:315-323` adds `accept-encoding: gzip` to every request whose caller has not

No test could see it. `tests/common/http.rs` had no shape that sends any header beyond
`Content-Length`, so every test of the bound spoke to a server that never compressed.

**RED.** `tests/common/http.rs` grew `Reply::Encoded { status, encoding, body }` — one status, one
body and the `Content-Encoding` it is in, sent under a `Content-Length` that counts the bytes on
the wire, which is what a compressing server sends. Against it,

Sixty-four mebibytes in memory, from three hundred kilobytes on the wire, under a bound of four
mebibytes — the test's own name is the promise, and it was refusing nothing.

**GREEN.** The bound is on the document, so it is counted where the document is: `text_once` reads
through `.reader()` and `Read::take(READ_LIMIT)` on the *decoded* stream, and a buffer that came
back full is the proof there was more. `ureq::Error::from(io::Error)` unwraps the wrapped
`BodyExceedsLimit` back out of the reader's `io::Error`, so the transfer's own bound still reports

the first attempt at this fix got wrong, and which the fourth test caught:


An encoding is allowed to make a body *larger* than what it encodes: deflate's stored block adds

any. `MAX_TEXT_BYTES`, `READ_LIMIT` and `TRANSFER_LIMIT` now say which count is which and why there
are two.

read whole too, and an ordinary compressed answer is still read — this build asks for gzip, so it
has to be able to read what it asked for.

  "this host ... cannot state the claim it exists for" instead of passing quietly. The `BULK_BYTES`
  comment and this record say that, and no longer say the other thing.
- **Two regression headers named a witness that is not one.** Both cited
  `a_document_over_the_bound_is_refused_after_exactly_one_request` as a case where `ureq` abandons a
  body mid-stream. It is not: `READ_LIMIT` is `MAX_TEXT_BYTES + 1` and that test's body is exactly
  `MAX_TEXT_BYTES + 1` bytes, so `ureq` takes every byte off the socket and only then fails —
  nothing is abandoned and no connection is reset. The general claim is true and the milestone now
  has a real witness for it: the compressed document above stops four mebibytes into a sixty-four
  mebibyte body and leaves the rest on the socket, and
  `a_client_that_abandons_a_reply_leaves_the_server_serving` does the same by hand. Both headers
  cite those instead.

first try with the sandbox disabled. Every figure in the table above is from a run with the
sandbox disabled, which is what the brief asks for.
