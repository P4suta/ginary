taken from the E3 log, because the settings are what the two workstreams are up against.

**Both rulesets are active.** `gh api repos/P4suta/ginary/rulesets`:

`ci.yml` that `tests/ci_matrix.rs` and `tests/repo_hardening.rs` already hold the name of.
`Protect release tags` carries `deletion` and `non_fast_forward`.

**Security features are on.** `security_and_analysis` reports `secret_scanning` enabled,
`secret_scanning_push_protection` enabled, and `dependabot_security_updates` enabled;
`gh api repos/P4suta/ginary/vulnerability-alerts` answers `204 No Content`, meaning alerts are
enabled; and `gh api repos/P4suta/ginary/private-vulnerability-reporting` answers
`{"enabled": true}`. (`secret_scanning_non_provider_patterns` and
`secret_scanning_validity_checks` are the two that remain disabled — neither is claimed
anywhere and neither is in scope for E5.)

**The default `GITHUB_TOKEN` is read-only and Actions may not create pull requests.**
`gh api repos/P4suta/ginary/actions/permissions/workflow`:

```json
{"default_workflow_permissions": "read", "can_approve_pull_request_reviews": false}
```

This pair is the deliberate hardening E3 applied, matching the strict siblings `release-glz` and
`beamtrace`, and it is **the root cause of the `Release` failure**: `release-please` cannot open
its release PR with a token that GitHub forbids from creating pull requests. The correct fix is
the App-token pattern Workstream 1 implements, not a loosened toggle — that toggle stays off.

### 9 — Workstream 1: a Release workflow that degrades honestly

`release.yml` now authenticates as a GitHub App and, when the App is not installed, says so and
exits 0.

**The App token.** A `actions/create-github-app-token` step carries `id: app-token` and is pinned
to `bcd2ba49218906704ab6c1aa796996da409d3eb1`. The SHA was resolved against the action's own
repository rather than copied from `beamtrace`, and re-resolved in this phase:

```console
$ git ls-remote https://github.com/actions/create-github-app-token refs/tags/v3.2.0 refs/tags/v3
bcd2ba49218906704ab6c1aa796996da409d3eb1	refs/tags/v3
bcd2ba49218906704ab6c1aa796996da409d3eb1	refs/tags/v3.2.0
```

It reads `${{ vars.RELEASE_PLEASE_APP_CLIENT_ID }}` and
`${{ secrets.RELEASE_PLEASE_APP_PRIVATE_KEY }}`, and narrows the installation token to
`permission-contents: write`, `permission-pull-requests: write` and `permission-issues: write` —
the version bump and changelog, the pull request itself, and the label it carries. Nothing wider.

**release-please consumes it explicitly.** `token: ${{ steps.app-token.outputs.token }}`. Without
that input release-please falls back to the workflow's own `GITHUB_TOKEN`, which is precisely the
token that failed run <https://github.com/P4suta/ginary/actions/runs/33658759645> with `GitHub
Actions is not permitted to create or approve pull requests`. `release.yml` now names neither
`secrets.GITHUB_TOKEN` nor `github.token` anywhere.

**The job's own token was narrowed at the same time.** It was `contents: write` plus
`pull-requests: write`; every write now travels on the installation token, so the only thing left
using the workflow token is `actions/checkout`, and the job asks for `contents: read`. A scope
nothing uses is a scope that should not be granted.

**The guard and the notice.** `release-please` is gated on
`if: ${{ vars.RELEASE_PLEASE_APP_CLIENT_ID != '' }}`. A second job, `credentials-notice`, carries
the complementary `== ''` guard, `permissions: {}`, one `run:` step and no way to exit non-zero.
Its prose is the insta snapshot `tests/snapshots/release_workflow__missing_credentials_notice.snap`
written in RED, reproduced byte for byte by the YAML block scalar: it names `P4suta/ginary`, both
credential names, the three App scopes, and why the default token is deliberately not an
alternative. `::notice title=…` puts a one-line summary on the run summary page as well as in the
log. The script was extracted from the parsed block scalar and run under `bash -e -o pipefail`,
GitHub's own default shell for a `run:` step, to prove that the quoted heredoc closes and that the
step exits 0 — a heredoc terminator that the YAML indentation had left indented would have hung the
step, not failed it.

The result is the property the brief asked for: **a repository with no release credentials has a
green Release workflow that says why it did nothing.** Adding the credentials later flips it to a
real release-please run with no further edit; removing them returns it to the notice.

**The document.** `docs/RELEASE.md` gains `## One-time setup` — the App install on `P4suta/ginary`
with its three scopes, the `RELEASE_PLEASE_APP_CLIENT_ID` *variable* (a client id is public, and
the job's `if:` has to be able to read it), and the `RELEASE_PLEASE_APP_PRIVATE_KEY` *secret*, each
with the settings page it is added on. The stale opening line — "ginary has no published repository
yet" — was corrected in the same edit; the repository has been live since E4.

### 10 — Workstream 2: every red job of the first live run

Run <https://github.com/P4suta/ginary/actions/runs/33658759531>, job by job, diagnosed from the
log in RED and fixed here.

| job | root cause | fix |
|---|---|---|
| `test`, `coverage` | a gated test defaulted to a path inside one developer's home directory, and `GINARY_REQUIRE_TOOLCHAIN=1` escalated the missing directory to a panic | `tests/common/shipment.rs::choose_shipment` |
| `windows` | `build.rs` had no target name for `x86_64-pc-windows-msvc` | an eighth row in `TARGETS` |
| `macos` | the launcher stub overwrote `target/release/ginary` before the job ran the command line tool | the stub gets a target directory of its own |
| `smoke-matrix` | three `cross` images shared one `CARGO_TARGET_DIR` | one target directory per triple, in `ci.yml` and `nightly.yml` |
| `lint` | `cargo-deny` was installed unpinned, resolved to 0.18.5, and could not parse a CVSS 4.0 advisory | every `install-action` tool pinned to an exact version, and the action pinned forward far enough to have them |

**`test` and `coverage` — the shipment.** `GINARY_REQUIRE_TOOLCHAIN` is a claim about programs the
machine installs. It is not, and cannot be, a claim that somebody exported a Gleam project here, so
the two questions are now separate and the rule lives in one pure function:

- nothing named: `Skip`, loudly, *however* the toolchain flag is set;
- named and a directory: `Run` it, *however* the flag is set;
- named and not a directory: `Fail`, *however* the flag is set — the caller asked for a run and
  mistyped a path.

`tests/closure.rs` now calls it and holds no path of its own; `DEFAULT_REAL_SHIPMENT` is gone.
`docs/dev/testing.md` said the same wrong thing twice ("defaulting to the author's `notify`
shipment", "a path on the author's machine otherwise") and both passages were rewritten. The scan
in the regression file is what keeps it gone: no tracked file under `tests/`, `src/`, `scripts/` or
`.github/` may contain this machine's `$HOME` on any machine — with one argued exception, the
three compiled `.beam` fixtures, recorded in the fix round below.

**`windows` — the MSVC triple.** `build.rs` mapped the seven triples ginary *distributes* for, and
the Windows one of those is `x86_64-pc-windows-gnu`, because the released Windows stub is
cross-compiled from Linux. The default host triple on a Windows machine — and on the
`windows-2022` runner — is `x86_64-pc-windows-msvc`, so `cargo build` died in the build script
before the job compiled a line. The table now has eight rows and both Windows triples map to
`windows-x86_64`, because the embedded marker names the platform an artifact runs on and not the
ABI it was linked with. The mapping stops being one-to-one, which is a fact about Windows rather
than a hole: `Target::rust_triple` still names the `-gnu` triple as the one releases are built
with, so the *other* direction stays single-valued and a release stays reproducible from one
triple. A triple that is still unknown is still a `panic!`.

**`macos` — the stub over the command line tool.** Both flavors are one Cargo target and share

next step invoked, and the packaging step was answered by the launcher stub's payloadless sentence
and exit 2. The stub is now built with `--target-dir target/stub` and copied from there. The
regression test states the rule rather than the edit — when a step runs `target/release/ginary` as
a command line tool, the last build to have written that path must be the full-feature one — so a
reorder would satisfy it too, and a future step that reintroduces the clobber will not.

**`smoke-matrix` — one target directory per container image.** `cross` runs each triple's compiler
in its own image, and the `x86_64-unknown-linux-gnu` image is deliberately ancient so the artifact
has a low glibc floor. A build script is compiled *for the host* and cached under the target
directory, so one `CARGO_TARGET_DIR` for three images handed the gnu image a `build-script-build`
linked against the musl image's libc: `GLIBC_2.28 not found`, before a single stub was built. Each
triple now gets `target/cross/$triple`, exported inside a subshell around its own build, in
`ci.yml` and in `nightly.yml`'s copy of the same loop. `cross-build` was never red because there
each triple is a matrix row with a runner, and therefore a target directory, of its own; it keeps
its step-level `CARGO_TARGET_DIR` unchanged.

release cannot parse a CVSS 4.0 vector, which `RUSTSEC-2026-0066` (`astral-tokio-tar`) had just
started carrying. `cargo deny check` failed on a tree nothing had changed. Two things were needed:

1. **Every tool is pinned to the version the gates were run against**: `cargo-deny@0.19.7`,

### 15 — RED: the notice was never proved unreachable when the credentials exist

**Finding (high).** `tests/release_workflow.rs::a_repository_without_the_credentials_…` asserted

```rust
guard.contains(&format!("vars.{CLIENT_ID_VAR}")) || step.run.contains(CLIENT_ID_VAR)
```

and `notice_step()` selects the step *by* its `run:` naming that very variable, so the right-hand
disjunct was true by construction and the assertion could not fail. The `if:` on
`credentials-notice` — the whole degrade-gracefully requirement — had nothing behind it.

Demonstrated rather than argued. With `credentials-notice` temporarily flipped from `== ''` to
`!= ''` (the exact inverse of the requirement: print the "add these credentials" notice only on a
repository that already has them, and print nothing on one that does not), the old test was still
green:

```text
running 1 test
test a_repository_without_the_credentials_is_told_what_to_add_and_the_job_stays_green ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 13 filtered out
```

The new regression file, over that same flipped workflow:

```text
---- e5_the_credentials_notice_was_not_tied_to_the_missing_credentials::
     the_notice_runs_exactly_when_the_release_job_does_not ----
job `credentials-notice` prints the missing-credentials notice, so it runs when the client-id
variable *is* the empty string and at no other time. Its `if:` is
`${{ vars.RELEASE_PLEASE_APP_CLIENT_ID != '' }}`
```

**Fix.** `tests/regressions/e5_the_credentials_notice_was_not_tied_to_the_missing_credentials.rs`
reads both `if:` expressions out of the parsed YAML and holds them against each other: the
release-please job's guard is `vars.RELEASE_PLEASE_APP_CLIENT_ID != ''`, the notice job's is
`== ''`, and the notice's may not contain `!= ''`. The step is still *found* by the credential
names it prints — there is no other way to find it — but no assertion reads that text, so no
assertion can be satisfied by the search that produced the step. `release_workflow.rs` lost the
tautological disjunct in the same breath: its assertion is now `guard.contains("vars.…") &&
guard.contains("== ''")`, and the file's comment says why no assertion there may read `step.run`.

### 16 — RED: the home-directory scan dropped every file it could not decode

**Finding (high).** `collect_text_files` used `read_to_string` and silently skipped anything that
was not UTF-8, which is the whole class of file most likely to embed an absolute path: a compiled
artifact. Three *tracked* fixtures do embed one right now. The invariant this log and
`docs/dev/testing.md` both state was therefore false and undetected, and the silent drop is the
default CLAUDE.md forbids ("Skipping is a reported decision or an error, never a default"). The
failure message also said *tracked* while the walker enumerated the filesystem, so a gitignored
`gleam build` artifact would have been reported as tracked.

Rewritten to scan bytes over `git ls-files`, before any allowlist:

```text
---- e5_a_gated_test_defaulted_to_one_developers_machine::
     no_source_or_test_file_names_the_home_directory_of_the_machine_it_was_written_on ----
a tracked file names `/home/yasunobu`, the home directory of the machine it was written on. A
path that exists on one machine is not a default, a fixture or a fallback:
tests/fixtures/beam/gleam@bool.beam:13
tests/fixtures/beam/gleam@list.beam:206
tests/fixtures/beam/gleam@string.beam:110
```

Each is the `Dbgi` chunk, where the Erlang compiler records the absolute path of the `.erl` it
compiled:

```console
$ strings -a tests/fixtures/beam/gleam@bool.beam | grep -o '/home/[^"]*'
/home/…/projects/gleam/notify/build/prod/erlang/gleam_stdlib/_gleam_artefacts/gleam@bool.erl
```

**Fix.** Three changes, and the exception is the interesting one.

- The scan reads bytes (`std::fs::read`, `windows(home.len())`) rather than text, so nothing is
  dropped for being undecodable, and a tracked file it cannot open at all is its own reported
  failure rather than a pass.
- The walk is `git ls-files -z -- tests src scripts .github`, so the message's word *tracked* is
  true. `git` not answering is a reported skip, not a quiet fall back to the directory read: the
  two answer different questions, and `tests/fixtures/hello_ffi/build/` — which a local
  `gleam build` fills with absolute paths — is not a bug in the repository.
- The three `.beam` fixtures are an argued `ALLOWED` entry rather than a silent pass. They were
  copied verbatim out of a real shipment, which is exactly what they are for: `tests/beam.rs`
  pins the grammar with hand-built bytes and these pin what a real compiler emits. Rewriting the
  chunk would make them no longer that, and recompiling `gleam_stdlib` with a relative `-o` would
  change every offset and size `tests/fixtures/beam/README.md` records and would no longer be
  1.0.5 as shipped. Nothing reads the path and nothing falls back to it. The reason is in the
  test, in that README, and here. A stale `ALLOWED` entry — one naming a file that is no longer
  in the tree — fails the test, so the exception cannot outlive the fixtures.

### 17 — RED: an empty `GINARY_TEST_SHIPMENT` was a panic, not a skip

**Finding (medium).** `std::env::var_os` reports `GINARY_TEST_SHIPMENT=` as `Some("")`, so
`choose_shipment` treated it as a *named* shipment, `PathBuf::from("")` is not a directory, and
`tests/closure.rs` panicked the whole binary with a message reading ``GINARY_TEST_SHIPMENT names
``, which is not a directory``. That is the shape a workflow produces on its own: `env:
GINARY_TEST_SHIPMENT: ${{ vars.SOMETHING }}` with the variable unset expands to the empty string
— precisely the "nobody named a shipment" case the module exists to turn into a skip.

```text
---- e5_a_gated_test_defaulted_to_one_developers_machine::
     an_empty_shipment_variable_is_the_same_as_an_unnamed_one ----
an empty value names nothing to look at on disk
```

(The `is_dir` probe passed to `choose_shipment` panics if it is ever called, so reaching the
filesystem at all *is* the failure: an empty value must be answered before any path exists.)

**Fix.** `choose_shipment` filters a value that is empty or entirely ASCII whitespace back to the
unset case, before the path is built. The new test covers three empty spellings across both
settings of `GINARY_REQUIRE_TOOLCHAIN`; `docs/dev/testing.md` states the rule with the empty
value in it.
