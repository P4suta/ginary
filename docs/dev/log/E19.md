### Family A — the fuzz smoke names its triple

The fix is one flag and the paragraph that says why it is there, in `.github/workflows/nightly.yml`:

```diff
-      - run: |
-          cargo fuzz run "${{ matrix.target }}" \
+      - run: |
+          cargo fuzz run --target x86_64-unknown-linux-gnu "${{ matrix.target }}" \
             fuzz/corpus/"${{ matrix.target }}" fuzz/seeds/"${{ matrix.target }}" \
             -- -max_total_time=30 -rss_limit_mb=4096
```

with a comment above the step naming the two words the pin exists for — `sanitizer` and
`crt-static` — the error text it prevents, and the wrong fix it is not (`rustup target add
x86_64-unknown-linux-musl`, which silences the consequential `E0463` and leaves
`sanitizer is incompatible with statically linked libc` standing).

Nothing else changed. There is still no `.cargo/config.toml`, no `RUSTFLAGS` and no
`target-feature` anywhere in the tree; the cause was never a setting this repository made, it was
cargo-fuzz's default target being the triple `taiki-e/install-action`'s prebuilt archive was
compiled for.

**Measured here, not reasoned about.** The brief asked for `cargo +nightly fuzz build` if this
machine can run it. It can, and it was run three ways with `cargo-fuzz 0.13.2` and
`nightly 1.100.0`, whose only installed target is `x86_64-unknown-linux-gnu` — the same shape as
the runner:

| command | result |
|---|---|
| `cargo +nightly fuzz build --target x86_64-unknown-linux-musl trailer_parse` | **the CI failure, exactly**: `error: sanitizer is incompatible with statically linked libc, disable it using `-C target-feature=-crt-static``, then `error[E0463]: can't find crate for `core`` with `= note: the `x86_64-unknown-linux-musl` target may not be installed` |
| `cargo +nightly fuzz build --target x86_64-unknown-linux-gnu trailer_parse` | `Finished `release` profile [optimized + debuginfo] target(s) in 2m 21s` |
| `cargo +nightly fuzz run --target x86_64-unknown-linux-gnu trailer_parse fuzz/corpus/… fuzz/seeds/… -- -max_total_time=5 -rss_limit_mb=4096` | `#4420288 DONE cov: 55 ft: 57 corp: 7/433b`, `Done 4420288 runs in 6 second(s)` |

so it is reproducible on a machine that never installed a musl target. The third is the proof
that the fix is a build **and** a run — the ASAN runtime links and 4.4 million inputs go through
the target under it — rather than a compile that would fall over when libFuzzer started.

The build wrote `fuzz/target` (602 MB) and refreshed `fuzz/Cargo.lock`. The directory was removed

### Family B — one gate for every question asked of `git`

The honest fix is the first of the two the brief offers: **the test stands down, out loud**, and
`cargo mutants` is left alone. Excluding the repository-property tests from the mutants suite
would stop them running in the one place they can answer, and a check that silently vanishes from

weakening: it names the directory, says what could not be asked there, and says why that run has
no `.git`.

`tests/common/tools.rs` gained the gate, and all four RED stubs are gone:

- `work_tree_gate(git_found, is_work_tree, toolchain_required)` — the rule as a pure function, so
  the table can be asserted row by row without a test mutating the environment. Deliberately
  asymmetric: no `git` escalates to a failure under `GINARY_REQUIRE_TOOLCHAIN`, because that
  variable is a claim somebody can make true by installing something; a directory that is not a
  checkout never escalates, because nobody can install being one. This is
  `require_elf_stripper`'s rule, applied to a second genuine inability.
- `git_says_work_tree(git, directory)` — `git -C <dir> rev-parse --is-inside-work-tree`, bounded

  `status.success()` **and** stdout `== "true"`: a bare repository answers `false` with exit zero,
  and reading either half alone is the same class of mistake as the one being fixed. Spawned by
  hand rather than through `run_bounded` because `run_bounded` turns a program that cannot start
  into a panic, and here that is an answer.
- `work_tree_skip_message(directory)` — the sentence, rendered as a value so a snapshot can hold
  it.
- `require_git_work_tree(directory)` — the gate itself, driving `work_tree_gate` rather than
  restating it, so the table the test asserts *is* the implementation.

### 1 — the positive-control fixture asserted a working `git` into existence

shape round 1's finding 4 rated, and the opposite of the rule `work_tree_gate` states.

**RED.** A `git` on `PATH` that runs, says what a refusal says, and exits `128` — planted with

### 2 — a `git` that refused to look was reported as the copy of the tree

`git_says_own_work_tree` mapped every non-zero `rev-parse --show-toplevel` to `Ok(false)` and
discarded `git`'s stderr, so `require_git_work_tree` printed `work_tree_skip_message` — which
names `cargo mutants` and "a copy of the tree that carries no `.git`" — for a checkout that is
sitting right there with its `.git` intact and a `git` that refused to read it. Round 1's finding
6 moved from the spawn path to the run path: the one sentence that would tell the reader to run
`git config --global --add safe.directory` was thrown away, and `GINARY_REQUIRE_TOOLCHAIN=1` could
not escalate it because the row was `NotItsOwnWorkTree`.

**RED.** The same planted `git`, asked about this repository root, which still carries its `.git`:

```console

and where it refuses to look at one, so a probe that reads every failure as an answer reports an
ownership refusal — or a typo in `~/.gitconfig`, which reaches every `git` child alike — as the
`cargo mutants` copy of the tree. /home/…/ginary still carries its `.git`
  left: NotItsOwnWorkTree

---- …::a_refusal_is_reported_in_gits_own_words_and_escalates_where_a_missing_checkout_does_not ----
panicked at …rs:250:5:

own, and a probe that returns a bare `false` throws it away:
```

(The empty tail of that last line is the finding: `detail` was the empty string.)

**Fix.** A fifth `WorkTreeProbe` arm, `GitRefused`, and the two `WorkTreeGate` arms that go with
it, `SkipGitRefused` and `FailGitRefused`. `git_says_own_work_tree` becomes `probe_own_work_tree`
and returns `WorkTreeAnswer { probe, detail }` rather than `Result<bool, String>`, so `git`'s own

program that would not start. The two `128`s are told apart by what `git` said — the new
`NOT_A_REPOSITORY` constant — and `git_command` now exports `LC_ALL=C` so there is one thing to

sentence: the program, the directory, the status, `git`'s words, and the one line that undoes an
ownership refusal.

The escalation is deliberately unlike the row beside it. Nobody can install being a checkout, so
`NotItsOwnWorkTree` never escalates; a refusal is one `git config --global --add safe.directory`
in a job, so `GitRefused` escalates under `GINARY_REQUIRE_TOOLCHAIN` like a missing or unrunnable

**Tests.** The two RED tests above, plus `the_one_failure_that_is_an_answer_is_the_one_that_says_so`

whole subject of this milestone, into a toolchain failure under `GINARY_REQUIRE_TOOLCHAIN=1`. The
gate table test grows from eight rows to ten.
