### 4 — `Protect main` now refuses direct pushes, and that is the intended behaviour

E3 wrote the rulesets; E5 applied them. They are now **active** and, for the first time, they
bind the work in progress. `gh api repos/P4suta/ginary/rulesets` reports two, both
`enforcement: active`: `Protect main` (id 22128494, target `branch`) and `Protect release tags`
(id 22128499, target `tag`).

`Protect main` applies to `~DEFAULT_BRANCH` with an **empty `bypass_actors` list** — nobody,
including the repository owner, is exempt — and carries five rules:

- `deletion` and `non_fast_forward` — `main` cannot be deleted or force-pushed.
- `required_linear_history` — merge commits are refused on `main`.
- `pull_request` — zero approvals required, but a pull request is *mandatory*, thread resolution
  is required, unattributed changes need an extra approval, and `squash` is the only permitted
  merge method.
- `required_status_checks` with `strict_required_status_checks_policy: true` — the `Required CI`
  check must pass **and** the branch must be up to date with `main` before a merge.

The practical consequence is the one the task brief states: a direct `git push` to `main` is
refused. That is correct and is not to be worked around — no bypass entry, no ruleset edit, no
force. The only route to `main` is PR #3 going green and the orchestrator squash-merging it,
which is precisely why "make the four jobs pass" *is* this milestone.

It also fixes the shape of the work: because `strict_required_status_checks_policy` is on, PR #3
must additionally be up to date with `main` at merge time. Nothing has landed on `main` since
`dfcfda3`, so today the branch is up to date; if that changes, the fix is a rebase by the
orchestrator, not a ruleset change.

Three of the five contradict the guesses the brief offered, and the fifth is not in it at all.

**`test` and `coverage` are one defect, not two.** The E5 shipment fix is complete and is not
involved. What fails is `tests/common/stubfile.rs::cross_stub`, which escalates a missing
cross-built stub to a panic under `GINARY_REQUIRE_TOOLCHAIN=1`. That variable is a claim about
*programs the machine installs*; a cross stub is the output of `mise run stubs:build`, which
needs `cross`, a docker daemon and minutes per target, and neither job runs it. The brief's
coverage-specific worry — that `cargo llvm-cov` wipes `target/` and so loses stubs the `test`
job kept — is not what happened: neither job ever had a stub to lose, and both failed on the
same three tests. The asymmetry it predicted does not exist.

**Windows is not a launcher bug, and no launcher code ran.** E5's `build.rs` fix works: both
flavors built, release, `--locked`, green. The suite then failed to *compile*, because the shared
test helpers reach into `std::os::unix` at file scope. `Assert exit-code propagation` was
skipped, so the `erl -noshell -eval halt(3)` claim is still unproved and the winpath, cache and
exit-code helpers the brief expected to find a genuine bug in were never executed on Windows at
all. Fifteen errors is a floor: cargo stopped with the other test targets still queued, and a
scan of the tracked tree finds **43** ungated reaches across 33 files.

**macOS never packaged anything, for the second run running.** `ginary build` has no `--erts`
flag and never has; an ERTS source is `[tools.ginary] erts` in `gleam.toml`, which is exactly what
`scripts/smoke-matrix.sh` appends before it builds. So `payload::locate` never looked for a
`__GINARY,__payload` section in a real Mach-O, the artifact never ran, and `codesign --verify
--strict` never saw the ad-hoc signature. Whether `src/sign_macos.rs` produces a signature the
kernel accepts remains unknown, and ADR 0016 has nothing to correct yet.

**The fifth defect is the one that would have blocked the merge anyway.** `macos-13` is not slow;
it is not scheduled. Across both runs the job holds `runner_name: ""` and never leaves `queued`,
while the `macos-14` row is picked up three seconds after the run starts. A withdrawn runner
label is accepted by the workflow parser, shown as a job, and never assigned — so the *run* keeps
the `queued` status indefinitely and any check computed from it never resolves. Four green jobs
and one unschedulable label is an unmergeable pull request.

### 11 — the stub gate: one variable answers one question

`tests/common/stubfile.rs::choose_cross_stub` is implemented, and `cross_stub` is now nothing but
a lookup around it: the environment is read once into two booleans, the rule decides, and the
three answers are executed — `Run` returns the path, `Skip` prints the reason, `Fail` panics with
it. The RED body — `StubChoice::Fail("choose_cross_stub is not implemented …")` — is gone.

The rule, in the order the questions are asked:

1. the first directory in `dirs` that holds the file wins, whatever either flag says;
2. otherwise `GINARY_REQUIRE_STUBS=1` makes it a failure;
3. otherwise it is a skip naming `mise run stubs:build`.

`required_toolchain` is still a parameter and is deliberately never read; a `let _ =` with a
comment says so, because deleting the parameter would leave the whole point of the function
invisible at its one call site.

The other half is that a job which *does* build the stubs now says so, and — this is the change
RED deferred and GREEN did not — actually runs the tests that need them. `ci.yml`'s
`smoke-matrix` job is the only job in the repository that runs `cross` and writes `target/stubs`,
so it gains two things: `GINARY_REQUIRE_STUBS: "1"`, and a step that runs exactly the two test
targets `cross_stub` gates.

### F1 (high, behavioural) — `coverage` obtained the stubs and not the runtimes they build from

`.github/workflows/ci.yml`, the `coverage` job.

**What the review found.** `dist/otp/catalog.json` is committed; every tarball it names is
gitignored:

```console

dist/otp/catalog.json
$ sed -n '4,11p' .gitignore
/dist/*
!/dist/otp/
/dist/otp/*
!/dist/otp/catalog.json
```

So on a CI checkout `catalog()` (`tests/e2e_cross.rs:51`, `tests/e2e_native.rs:52`) finds the
file, returns `Some`, and neither skips nor trips its own `GINARY_REQUIRE_TOOLCHAIN` assert.
Seven of the nine stub-gated tests — `tests/e2e_cross.rs` times three and `tests/e2e_native.rs`
times four — then write `erts = "catalog"` into the fixture and build against it, and
`catalog::resolve_url` turns the entry's bare `"url"` into a `SourceUrl::File` beside the
catalog that is not there. Downloading the stubs therefore moved the `coverage` failure from
`stubfile::cross_stub` to `ginary build`; it did not remove it. Only two jobs repacked —
`ci.yml` `smoke-matrix` and `nightly.yml` — and `coverage` was neither.

**Reproduced here**, with exactly the command `build_for` runs, against a directory holding
only the committed catalog:

```console
$ GINARY_CATALOG=<scratch>/cat/catalog.json GINARY_CACHE_DIR=<scratch>/cache \
    target/debug/ginary build --target linux-x86_64-musl \

error: cannot resolve the runtime to bundle
  caused by: cannot use the catalog
  caused by: cannot use <scratch>/cat/otp-29.0.5-linux-x86_64-musl-static.tar.zst: No such file or directory (os error 2)
rc=1
```

`build_for` asserts `output.status.success()` (`tests/e2e_cross.rs:104`), so all three
`e2e_cross` tests panic; the four `e2e_native` tests assert on a specific stderr and get
`cannot use the catalog` instead. The 90.26% the first round quoted was measured on this
machine, where `dist/otp` holds three 13 MB tarballs. The runner has none.

`tests/regressions/e6_the_coverage_floor_measured_a_stubless_subset.rs` — one naming the

**The fix.** `coverage` now runs the same repack step `smoke-matrix` has, after the stub-naming
step and before `cargo llvm-cov`:

```yaml
- name: Repack the OTP runtimes the catalog-built tests bundle
  run: |
    cargo run --quiet --locked -- otp repack \
      --upstream-tag OTP-29.0.5 \
      --targets linux-x86_64-musl:static,linux-x86_64-gnu,linux-aarch64-musl:static \
      --out dist/otp
```

Repack rather than a `dist/otp` artifact download, because `coverage` already waits on
`cross-build` and not on `smoke-matrix`, and adding a second wait would serialise it behind the
longest job in the matrix for 40 MB it can rebuild in a few minutes. `cargo llvm-cov` builds
into `target/llvm-cov-target`, so neither `target/stubs` nor `dist/otp` is disturbed by it.

cross builds are all work it did not do when 40 was chosen.

**The tests that pin it.** In
`tests/regressions/e6_the_coverage_floor_measured_a_stubless_subset.rs`, an `obtains_runtimes`
helper and:

- `a_job_that_obtains_the_stubs_also_obtains_the_runtimes_those_tests_build_from` states the
