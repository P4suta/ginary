### Finding 1 (medium, behavioural) — the OTP tarballs escaped verification

`.github/workflows/distribute.yml`: the `publish` job computed `SHA256SUMS`,
attested provenance, re-downloaded, and verified over a `ginary-*` glob, but
`ginary otp repack` writes `otp-<version>-<target>-<variant>.tar.zst` and
`catalog.json` (src/catalog.rs:2292, :2184) into the same `dist/release`, and
the release was created from `dist/release/*`. So the OTP runtime tarballs --
the BEAM bytes a user executes -- reached the published release unchecksummed,
unattested, and unverified, contradicting the workflow's own header and the
house rule against silently skipping a verification.

RED: `tests/regressions/e1_otp_tarballs_escaped_the_verification.rs`, watched
failing before the fix:

```
$ cargo test --test regressions e1_otp_tarballs
---- the_checksum_manifest_covers_the_otp_tarballs_and_catalog stdout ----
SHA256SUMS must checksum the OTP runtime tarballs
(`otp-<version>-<target>-<variant>.tar.zst`), not only `ginary-*`; the runtime
bytes a user executes cannot ship unchecksummed:
  run: sha256sum ginary-* > SHA256SUMS
---- the_attestation_covers_the_otp_tarballs_and_catalog stdout ----
the provenance attestation subject-path must cover the OTP runtime tarballs,
not only `ginary-*`
---- the_redownload_verification_is_not_narrowed_to_ginary_only stdout ----
the re-download and the attestation-verify loop must not restrict to `ginary-*`,
which drops the OTP runtime tarballs and `catalog.json` from `sha256sum --check`
and `gh attestation verify`:
  gh release download "${GITHUB_REF_NAME}" --pattern 'ginary-*' ...
  for asset in ginary-*; do ...

test result: FAILED. 0 passed; 3 failed
```

## Fix round 2

Reviewer findings addressed: one medium (behavioural) and one low
(behavioural). Both got a regression test watched failing before the fix, per
the house TDD rule.

### Finding 1 (medium, behavioural) — the round-1 fix broke actionlint

The round-1 checksum command
(`find . -maxdepth 1 -type f ! -name SHA256SUMS ... | xargs sha256sum >
SHA256SUMS`) names `SHA256SUMS` in both the `find` predicate and the pipeline
redirect, so shellcheck SC2094 ("Make sure not to read and write the same file
in the same pipeline") fired twice and `actionlint .github/workflows/
distribute.yml` exited 1 -- a regression that made the log's "all four clean"
claim false. No existing test caught it: `tests/ci_matrix.rs` reads the YAML
but never runs actionlint.

RED: added `tests/regressions/e1_the_sha256sums_step_read_and_wrote_one_file.rs`
(runs `actionlint` over all four workflows via `require_tools`), watched failing
before the fix:

```
$ GINARY_REQUIRE_TOOLCHAIN=1 cargo test --test regressions actionlint_accepts_every_workflow
test e1_the_sha256sums_step_read_and_wrote_one_file::actionlint_accepts_every_workflow ... FAILED

actionlint rejected .github/workflows/distribute.yml (exit Some(1)); every
workflow must be actionlint-clean:
.github/workflows/distribute.yml:200:9: shellcheck reported issue in this script:
  SC2094:info:1:36: Make sure not to read and write the same file in the same pipeline
.github/workflows/distribute.yml:200:9: shellcheck reported issue in this script:
  SC2094:info:3:23: Make sure not to read and write the same file in the same pipeline

test result: FAILED. 0 passed; 1 failed
```

GREEN: the `Compute SHA256SUMS` step now excludes the manifest with a glob
(`! -name 'SHA256SUMS*'`), writes to a scratch name, and renames it into place,
so the pipeline never reads and writes one name:

```
find . -maxdepth 1 -type f ! -name 'SHA256SUMS*' -printf '%P\n' \
  | LC_ALL=C sort \
  | xargs -r sha256sum > SHA256SUMS.tmp
mv SHA256SUMS.tmp SHA256SUMS
```

`actionlint` over all four workflows -- `ci.yml`, `nightly.yml`, `release.yml`,
`distribute.yml` -- exits 0 again, and the new test passes. The `# vX.Y.Z`
SHA pins were untouched, so the pin table above still holds.

### Finding 2 (low, behavioural) — a checksum sub-test matched the comment

`the_checksum_manifest_covers_the_otp_tarballs_and_catalog` in
`e1_otp_tarballs_escaped_the_verification.rs` asserted the whole step text
`contains("otp-")` and `contains("catalog.json")`. After round 1 those two
substrings live only in the step's `#` comment, not in the command, so a revert
of the command alone to `sha256sum ginary-* > SHA256SUMS` -- with the comment
