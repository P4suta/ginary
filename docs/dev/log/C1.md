### 1 — `ginary verify` compared one of the index's three columns (low)

`ginary.index.json` describes every payload entry with a `path`, a `size`, a `mode` and a
`sha256`. The stream loop in `src/verify.rs` matched a row by path and then compared the digest
and nothing else, so two of the three columns the format defines were carried in every artifact
and checked by nobody. An index row promising `0700` over an entry the launcher extracts `0644`,
or claiming a length the entry does not have, verified clean: exit 0, no findings, over an
artifact whose own two descriptions of a file disagree. The digest hid it, because nothing in a
packer recomputes one column from another — a row can hold the right hash beside wrong metadata.

`docs/format.md` already fixed the relation the columns stand in, so the fix is the reader
catching up with the document rather than a change to the format:

- `size` is the file's own length in both the header and the row, so they are compared for
  equality.
- `mode` is *not*. The header is written with `HeaderMode::Deterministic`, which propagates the
  user execute bit and nothing else, while the row records the staged file's own
  `st_mode & 0o7777`; the document says in as many words that the two agree for a `0644`/`0755`
  tree and that the index is the record of what was staged. Comparing them for equality would
  therefore report a finding against every artifact staged from a tree whose modes are neither —
  a read-only `0444` file out of an OTP install is enough. What is checked is the relation:
  `header_mode(row.mode)` is `0755` when the row has the user execute bit and `0644` otherwise,
  and a header that is not that is the finding. No artifact ginary itself packs can trip it,
  because that function is exactly the rule the packer applies.

The changes:

- `src/verify.rs` gains `Issue::IndexSizeMismatch { path, expected, actual }` and
  `Issue::IndexModeMismatch { path, indexed, expected, actual }`. Both name the column in the
  variant and in the sentence, beside the digest's existing `IndexMismatch`; `IndexModeMismatch`
  prints the row's staged mode, the header mode it implies and the one the entry carries, so a
  reader can see which of the two is wrong. They take ranks 4 and 5, directly after the digest,
  and the six variants below them move down — the declared order is what `Issue::rank` and the
  exhaustive unit test hold.
- The `expected` map is now `BTreeMap<&str, &IndexFile>` rather than a path-to-digest map, and
  the three comparisons live in one `row_issues` helper so that every column a row carries is
  checked in one place and a fourth cannot be added without passing through it.
- `Scan` gains a counted `len`. The length a finding reports is the number of bytes that were
  really hashed rather than the number the header claims, so a header that lies about its own
  size is reported against what the payload holds.
- A header whose mode field is not an octal number is `actual: "unreadable"` rather than a
  skipped check: it is a header that agrees with no row at all, and skipping is the one thing
  this module may not do.

RED first, watched failing, in `tests/regressions/b2_verify_compared_only_the_digest.rs`: the
two variants were declared with no comparison behind them so the file compiled, and all three
findings-shaped tests failed on their assertions (`an index that promises an executable verified
clean: []`) with the command test reporting `Unexpected success ... code=0`. The fourth test,
that a whole artifact raises neither finding, passed from the start and is the guard against a
check that reports every honest artifact.

`tests/common/repack.rs` gains `index_mode_lies` and `index_size_lies`, which rewrite a row after
`Index::from_staged` has read the tree and before the archive is written, so the tar header keeps
the truth and the row is the only thing that moved. That is the same seam `corrupt`,
`drop_from_index` and `ghost_index_rows` already use for the digest findings.

`tests/verify.rs`'s `a_file_whose_bytes_are_not_the_indexed_ones_is_named` now expects two
findings rather than one: its replacement bytes are two longer than the ones the row was written
from, so the row's length is wrong as well as its digest and each column is named on its own.
The assertion was strengthened rather than relaxed.

Documents: `docs/format.md` states that the mode columns are related rather than equal and that

### One decision the specification could not make

`[tools.ginary] targets` is a list of strings and `[tools.ginary.targets.<name>]` would be a
table, and TOML will not let one key be both — a manifest holding the two is a duplicate-key
parse error before anything of ginary's runs. The list keeps the name `targets`, because that is
the one a user types and the one `--target` mirrors, and the per-target sub-tables are
`[tools.ginary.target.<name>]`, singular. The plan's Phase C4 example message names the plural
form and moves to the singular with the milestone that prints it.

### Seven decisions the specification left to the implementation

1. **A sub-table's unknown keys are collected, not refused by serde.** The test requires
   `ConfigError::TargetKey` naming *both* the table and the key, and `deny_unknown_fields` raises
   its error inside `toml::from_str`, where the only thing that can be said is what serde says:
   the key, and no table. `TargetConfig` therefore keeps a `#[serde(flatten)] unknown` map and
   `validate_targets` refuses the first key in it, with the same sentence serde would have
   written plus the sub-table's name in front. The refusal is identical; the difference is that
   a manifest holding seven of these tables now points at one of them.
2. **`--otp-root` is a `dir:` source.** The flag names a directory holding a runtime, which is
   exactly what `dir:PATH` means, so it resolves as one and overrides every sub-table — a flag
   the user typed just now wins, as every other flag in `BuildOptions::merge` does. The
   consequence is visible: an artifact built with `--otp-root /opt/otp` records
   `source: "dir:/opt/otp"` rather than `host:`, which is the more precise of the two. The
   `ErtsSourceSpec::Host` doc comment lost its "or `--otp-root`" clause to match.
3. **`libc_min` is reported only for a dynamically linked gnu target.** musl carries no symbol
   versions to derive a floor from, and a static emulator resolves nothing at load time whatever
   it was built against, so both are `None` rather than a number that would describe the machine
   the runtime was compiled on.
4. **The linkage is the interpreter, corroborated by the needed set.** `linkage_of` reads
   `Linkage::Static` only when the emulator names neither a `PT_INTERP` nor a `DT_NEEDED`: a file
   that names shared libraries and no loader is not a static runtime, and calling it one would
   write `nif_loading: false` into a manifest for a runtime that does load them. This is the
   "interp presence + needed set" the specification asked for.
5. **`doctor`'s `resolves` column is a capability, not an attempt.** `yes` means this ginary
   knows how to resolve that kind of source today and `not yet` names the milestone that brings
   it; a `dir:` on this machine is `yes` without being opened, because `doctor` describes the
   machine and inspecting a runtime root is half of a build. The one runtime it reads is the one
   it is standing on, and when *that* read fails the row still says `yes` — the source is
   resolvable, this installation is what could not be read — with the whole error chain in
   `detail` so the sentence names a directory rather than a fault.
6. **`doctor` reads the project's own target list.** `Report::gather` looks for a `gleam.toml`
   at or above the working directory and probes what its `targets` resolves to, with its

`BundleError::ManifestCopy` covers both halves of writing `<app>-<target>.json`: the serialisation

### The build loop

`build_with_stub` checks the stub, refuses every target that is not the host, exports once, and

still has one work directory and one removal site. The report's own fields are the first target's,

the host is buildable today, so the loop runs once; the loop, the naming and the row-per-target
