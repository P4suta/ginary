## The diagnosis

The brief names three candidates for the failing step and forbids assuming between them: `erl`
not on `PATH` in that `pwsh` step, `erl.exe` genuinely not propagating `halt(3)`, or something
else the log shows. It is the third, and the first two are **refuted by the same fact** — the
step said nothing at all.

### 10 — silence is the evidence

The log of step 8, re-fetched with the sandbox disabled and read whole, is the eleven lines
section 5 quotes: the `##[group]`, the two script lines, the shell, the five environment
variables, the `##[endgroup]`, and then `##[error]Process completed with exit code 1.` Nothing
else. It is not a truncation: the same job's `cargo build` steps put rustc's warnings —
standard error — in this very log, so a step's standard error reaches it.

The two candidate causes both **write a line before they fail**, and `pwsh` 7.6.5 on this machine
was asked to say what each of them looks like. GitHub runs a `shell: pwsh` step as
`pwsh -command ". '<file>'"` over a file it wraps: `$ErrorActionPreference = 'stop'` before the
script and `if ((Test-Path -LiteralPath variable:\LASTEXITCODE)) { exit $LASTEXITCODE }` after
it. Three files, the same wrapper, the same invocation:

```console
$ pwsh -command ". '/tmp/s1.ps1'"   # `erlnotthere` in place of `erl`
exit=1
erlnotthere: /tmp/s1.ps1:2
Line |
   2 |  erlnotthere -noshell -eval "halt(3)"
     |  ~~~~~~~~~~~
     | The term 'erlnotthere' is not recognized as a name of a cmdlet,
     | function, script file, or executable program. …

$ pwsh -command ". '/tmp/s3.ps1'"   # a program that exits 0, so the `throw` fires
exit=1
Exception: /tmp/s3.ps1:3
Line |
   3 | … TEXITCODE -ne 3) { throw "expected ERRORLEVEL 3, got $LASTEXITCODE" }
     |                      ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
     | expected ERRORLEVEL 3, got 0

$ pwsh -command ". '/tmp/s2.ps1'"   # a program that exits 3, so the assertion holds
exit=1
(no output on either stream)
```

An `erl` the step cannot find prints a five-line block naming the word it could not resolve. An
`erl` that ran and left the wrong number prints the thrown message with the number in it. **Only
the case where `erl` ran and left exactly 3 is silent**, and silence with `exit code 1` is what
the runner recorded. So `erl.exe` was found, it ran, and `halt(3)` reached the parent as 3.

### 11 — what actually failed the step

The third line of the file is GitHub's, not ours. With `$LASTEXITCODE` at 3 the appended
`exit $LASTEXITCODE` runs, and under `pwsh -command ". '<file>'"` an `exit` of anything non-zero
from the sourced script comes back to the caller as **1**:

```console
$ for n in 0 1 3 7 101; do printf "exit $n\n" > x.ps1; pwsh -command ". 'x.ps1'"; echo "$n -> $?"; done
0 -> 0
1 -> 1
3 -> 1
7 -> 1
101 -> 1
```

The same collapse is visible on the runner itself and has been all along: run 33854462719's
Windows job failed at `cargo test`, which exits **101**, and the runner reported
`Process completed with exit code 1`.

Put together, with the real `erl` on this Linux machine — the same OTP 29.0.5 the Windows job
installs, and one that does propagate `halt(3)`:

```console
$ cat asis.ps1
$ErrorActionPreference = 'stop'
erl -noshell -eval "halt(3)"
if ($LASTEXITCODE -ne 3) { throw "expected ERRORLEVEL 3, got $LASTEXITCODE" }
if ((Test-Path -LiteralPath variable:\LASTEXITCODE)) { exit $LASTEXITCODE }

$ pwsh -command ". 'asis.ps1'"; echo "exit=$?"
exit=1                       # stdout 0 bytes, stderr 0 bytes

$ cat fixed.ps1
$ErrorActionPreference = 'stop'
erl -noshell -eval "halt(3)"
$code = $LASTEXITCODE
Write-Host "erl -noshell -eval halt(3) left exit code $code"
if ($code -ne 3) { Write-Host "::error::expected exit code 3, got $code"; exit 1 }
exit 0

$ pwsh -command ". 'fixed.ps1'"; echo "exit=$?"
erl -noshell -eval halt(3) left exit code 3
exit=0
```

The CI symptom — exit 1, nothing on either stream, half a second — reproduces exactly on a host
where the propagation under test **works**. The step asserted the platform fact correctly, and
then handed the number it had just proved to the epilogue, which failed the job with it.

So:

- **The platform fact holds.** `erl.exe` on `windows-2022`, OTP 29.0.5 / erts-17.0.5, propagates
  `halt(3)` to its parent as 3. D2's open question is answered and `launch_windows`'s contract —
  spawn, wait, mirror the child's code — rests on something a real Windows host has now done.
  Nothing in `src/` is wrong, and nothing in `src/` changes in this milestone.
- **The step is wrong**, in three ways that the fix has to take together: it ends with the code it
  asserts, so a correct answer fails the job; it says nothing on any path, so the failure it
  reported was unreadable; and it invokes a bare `erl` off `PATH` rather than the runtime the job
  installed at `%INSTALL_DIR_FOR_OTP%\bin\erl.exe`, so a `setup-beam` that stopped exporting the
  directory would report a number rather than saying it could not find a runtime.
- **ADR 0015 is out of date.** It still lists `halt(N)` propagation to `%ERRORLEVEL%` among the
  things "compiled and not run", on "a `windows-latest` runner" this repository deliberately does
  not use.

The fix therefore belongs in `.github/workflows/ci.yml`, in `tests/ci_matrix.rs` and
`tests/regressions/`, and in ADR 0015 — and the step is repaired, never deleted: it is the only
end-to-end check of the Windows exit-code contract there is.

### 23 — the suite's own `pwsh` children were unbounded, profile-loaded and unescaped

Three findings against
`tests/regressions/e15_a_pwsh_step_ended_with_the_code_it_asserted.rs` and
`tests/common/tools.rs`, all of them the same shape: the measurement was right and the way it was
spawned was not.

- **No deadline, and stdin inherited.** Both children used `Command::output()`, which
  `tests/common/bounded.rs` exists to forbid — "it waits forever, and a runtime that fails to
  halt would cost the suite its own timeout with no diagnosis at all" — and neither nulled stdin,
  so a `pwsh` that stopped at a prompt would hang the test binary. Both now go through
  `run_bounded(&mut command, PWSH_BUDGET, …)`, which nulls stdin and drains both pipes on threads
  of their own. `tools::PWSH_BUDGET` is 60 s: the two children are `exit 0` and a two-line
  script, so the budget is the interpreter's start-up on a loaded runner with room to spare.
- **No `-NoProfile` on the measurement.** `require_working_pwsh` passed it and
  `run_as_a_pwsh_step` did not, so a `$PROFILE` that printed a banner would have failed
  `assert!(said.is_empty(), …)` with a message accusing this repository of having lost the
  mechanism under test. Profile loading has no bearing on what a sourced script's non-zero `exit`
  becomes to the caller, so the flag is passed and the doc comment says it is this test's own
  rather than GitHub's.
- **An unescaped path inside a single-quoted PowerShell string.** `. '<file>'` was built by
  interpolation, and `tempfile::tempdir` honours `TMPDIR`; an apostrophe is legal in a POSIX path.
  `single_quoted` doubles any apostrophe, which is PowerShell's own escape inside single quotes.
