### 8 — the split, and why it is the one it is

Two GitHub rules decide the shape:

1. A job's `vars` and `secrets` contexts carry an environment's values **only when the job
   declares that environment**. Outside `environment: release` both `vars.RELEASE_PLEASE_APP_CLIENT_ID`
   and `secrets.RELEASE_PLEASE_APP_PRIVATE_KEY` expand to the empty string however full the
   environment is — which is precisely the live behaviour section 3 recorded.
2. A job that declares an environment the current ref may not deploy to does not skip. The run
   **fails**: `Branch is not allowed to deploy to release due to environment protection rules`.
   The `release` environment admits the `main` branch and the `v*` tags and nothing else.

E5's shape cannot survive rule 1. Its guard is a job-level `if:` reading
`vars.RELEASE_PLEASE_APP_CLIENT_ID`, and a job condition is evaluated before the job's environment
is bound — a job `if:` cannot see a `secrets` context at all, and an environment-scoped variable
cannot be relied on there either. A guard that reads repository scope to decide whether an
environment holds credentials answers a question nobody asked.

So the guard moves off the job and onto the steps, and the two jobs become one:

- **`release-please` declares `environment: release`.** It carries no `if:` at all, so it always
  starts, and it is the only job that names either credential.
- **Its first step, `id: credentials`, is the whole decision.** It reads both values through the
  step's `env:` — a secret cannot be interpolated straight into a `run:` block without writing a
  private key into a script — and classifies what the environment holds into one of three states:
  both present is `state=configured`, neither present is `state=absent`, and the variable without
  the secret is the one red state E5 established, `exit 1` naming the missing credential. The two
  survivable states are written to `$GITHUB_OUTPUT` under the name `state`.
- **Every step that needs the credentials is guarded on
  `steps.credentials.outputs.state == 'configured'`** — the checkout, the App-token mint and
  release-please itself.
- **The notice is a step of the same job, guarded on the complement,
  `steps.credentials.outputs.state == 'absent'`.**

The brief allowed either "the notice must still be reachable" or "its job must not be the one
bound to the environment"; this takes the first. The alternative — keeping `credentials-notice` as
a second job, unbound, reached through `needs:` and a job output of the first — was rejected as
machinery that buys nothing: it needs the environment-bound job to run unconditionally anyway,
adds a job output, an `always()` and a `needs:` to say what one step condition already says, and
still leaves the decision in the environment-bound job. The cost of the chosen split is that the
run list loses one job name; what it keeps is that a repository with an empty environment gets one
green job that says why it did nothing, in one place.

Rule 2 is a constraint on the triggers rather than on the jobs, and it is now asserted: `release.yml`
runs on `push` to `main` and on nothing else. A `pull_request` trigger — or a `workflow_dispatch`,
which can be aimed at any branch — would reach the environment-bound job from a ref the policy
refuses, and that is a failed run rather than a skipped one. **This is the answer to "make sure a
PR run still behaves sensibly": no PR run of this workflow exists, and a test now keeps it that
way.** A fork is safe by a different route: an environment nobody created is created implicitly with
no protection rules, holds nothing, and the run reaches the notice and stays green.

### 9 — the helpers the tests needed

`tests/common/repo.rs` could not answer either of the two new questions, so it gains four fields
and one function. None of them is specific to this milestone.

- `WorkflowStep::id` and `WorkflowStep::cond` — a step's `id:` and its `if:`. With the guard moved
  from the job to the steps, "which steps does this workflow run" is no longer answerable from the
  job conditions alone, and `steps.<id>.outputs.<name>` is the only handle one step has on
  another's answer.
- `WorkflowJob::cond` and `WorkflowJob::environment` — the job's `if:`, and the name of the
  environment it declares. `environment` collapses both spellings GitHub accepts, the scalar
  `environment: release` and the mapping `environment: {name: release, url: ...}`, through the new
  private `environment_name`; a job that declares none is the empty string, because no environment
  can be called that.

One existing caller builds a `WorkflowStep` by hand — `plain_step` and the `wrapped` closure in
`tests/regressions/e5_the_macos_job_ran_the_stub_as_the_command_line_tool.rs`, which feed synthetic
scripts to the scanners under test — and both gained the two new fields as `String::new()`. Nothing
else in the suite constructs either struct.

### 14 — what the workflow became

`.github/workflows/release.yml` is now one job. Every `// RED: replaced in GREEN` the RED section
left is filled by the shape section 8 argued for, and nothing else in the file moved.

- **`release-please` declares `environment: release` and carries no `if:`.** It is the only job in
  the workflow and the only job that names either credential, so it is the only job that can read
  them: an environment's variables and secrets are absent from a job that declares no environment,
  which is the whole defect E17 exists to fix. The job condition E5 wrote is gone rather than
  moved, because there is no condition a job `if:` could carry here that would be true: it is
  evaluated before the environment is bound and cannot see a `secrets` context at all.
- **Step 1, `id: credentials`, is the decision.** Both values reach it through the step's `env:` —
  `CLIENT_ID` from `vars.RELEASE_PLEASE_APP_CLIENT_ID` and `PRIVATE_KEY` from
  `secrets.RELEASE_PLEASE_APP_PRIVATE_KEY` — because `secrets` is not a context a shell can reach
  on its own and interpolating one into a `run:` block would write a private key into a script. It
  is unguarded; it is what computes the guard.
- **Four states, and each is now decided rather than stumbled into.** Both present writes
  `state=configured` to `$GITHUB_OUTPUT`; neither present writes `state=absent`; the variable
  without the secret and the secret without the variable each fail with an error naming the
  credential that is missing and the environment page it belongs on. E5 had only the first of
  those two red states — its job guard read the variable, so a repository with the secret alone
  skipped in silence — and the symmetric branch costs one `elif` and removes a state nobody could
  diagnose from a run.
- **Step 2 is the notice**, guarded on `steps.credentials.outputs.state == 'absent'`, printing the
  wording the committed snapshot pins and exiting 0. E5's contract is intact — no credentials is a
  green run that says why it did nothing — and the two lines that sent a maintainer to repository
  scope now send them to `Settings -> Environments -> release`, with the reason attached: the
  environment admits only `main` and the `v*` tags, so neither value is reachable from a pull
  request, from a fork, or from any other branch.
- **Steps 3 to 5 — the checkout, the App token and release-please — each carry
  `if: ${{ steps.credentials.outputs.state == 'configured' }}`.** With the guard off the job it
  has to be on every step that needs the credentials, or a repository with none reaches
  `actions/create-github-app-token` with an empty `client-id:` and fails on a message about JWT
  signing. The two action steps that gained a guard were rewritten with `uses:` as their first key
  so that `the_release_job_authenticates_with_a_github_app_token`, which splits the file on
  `- uses:`, still reads one step's chunk rather than the file's tail.
- **`credentials-notice` is gone.** Its work is step 2 of the job that can actually read the
  values, which is the point: an unbound job could print a notice but could never know whether one
  was warranted.

Everything E5 through E16 pinned about this file is untouched: the `permissions: {}` default, the
`contents: read` job scope, both action SHAs, `id: app-token`, the explicit
`token: ${{ steps.app-token.outputs.token }}` handed to release-please, the absence of
`secrets.GITHUB_TOKEN` and `github.token`, and the three App-token scopes.

The triggers did not change — `push` to `main`, and nothing else — but they are now load-bearing
rather than incidental, and a header comment says so. A job that declares an environment the
current ref may not deploy to **fails**; a `pull_request` or `workflow_dispatch` trigger could
aim this job at a ref the policy refuses, so neither may be added.
`the_release_workflow_only_runs_on_refs_the_environment_admits` is what keeps that true, and it is
the answer to the brief's "make sure a PR run still behaves sensibly": there is no PR run of this
workflow. A fork is safe by the other route — an environment nobody created is created implicitly
with no protection rules and holds nothing, so the job runs, `state=absent`, and the notice prints.

The credentials script was run outside CI in all four states before the gates, under
`bash -e -o pipefail`, the shell GitHub gives a `run:` block on Linux:

### 22 — the fixes

**Finding 1, the notice check was a tautology.** `step.run.contains("release")` is satisfied by
`release-please did not run`, which the notice prints whatever environment it names. The needle is
now the whole click-path with the environment's name on the end,
`Settings -> Environments -> release`, which only an environment-scoped instruction produces.
`tests/regressions/e17_the_notice_named_the_environment_by_accident.rs` holds the rule as a
function against the committed notice *and* against the same notice with the environment name
changed, and keeps the old predicate beside it to show what it could not see.

**Finding 3, the scan was narrower than the rule.** The old scan read `release.yml` alone, through
four node kinds. `name_sites` walks every scalar and mapping key of every workflow under
`.github/workflows`, records the job each site belongs to (empty for a workflow-level site, which
is its own failure), and `yaml_text_occurrences` counts the same name off the file text so the two
can be asserted equal: a node kind the walk cannot reach now fails loudly instead of passing.
`no_job_of_any_workflow_reads_the_release_credentials_without_declaring_the_environment` and
`every_occurrence_of_a_release_credential_is_accounted_for` are the two rules, and
`tests/regressions/e17_the_release_credentials_were_read_outside_their_environment.rs` carries
both in its own words.

**Finding 4, `if: false` read as no condition at all.** `WorkflowStep::cond` and
`WorkflowJob::cond` dropped any non-string `if:`, so the one node that means "never" became the
empty string every rule reads as "always" — and
`the_credentials_check_is_the_first_step_and_publishes_what_it_found` asserts `cond == ""` under
the message "the credentials check itself is unguarded". A new `condition` helper renders a
boolean rather than dropping it. This is the same class as `job_continues_on_error`, one helper
away, which already treated "anything but a literal `false`" carefully for the mirror-image
reason.

**Finding 7, only `uses:` steps had to carry the guard.** The rule's name says "every step that
needs the credentials"; its filter said "every step that uses an action". A `run:` step reading
the private key out of its `env:` was excused. Both the rule and its twin in the E5 regression
file now cover every step of the job except the two that *are* the guard — the check at position
one and the notice on the complement — plus any step naming a credential in `run:`, `if:`, `env:`
or `with:`.

**Finding 2, `docs/dev/testing.md` was stale.** The `WorkflowStep` listing gains `id` and `cond`,
the `WorkflowJob` listing `cond` and `environment`, each with the one-line reason it carries in
`tests/common/repo.rs`; `environment_name` and its two spellings, `workflow_steps_of` /
`workflow_jobs_of`, and `name_sites` / `yaml_text_occurrences` are described where the rest of
the repository readers are. CLAUDE.md sends a contributor to that file, so a field set it states
wrongly is worse than one it omits.

**Finding 5, the document check searched past its section.** `## One-time setup` was split on the
heading and then searched to the end of the file, so the `pull request` half of "does it say
*why*" was satisfied by `## The three steps` saying "review that pull request". The section is now
truncated at the next `\n## ` before the search.

**Finding 6, the environment must carry no other protection rule.** `release.yml`'s only job is
bound to `release` with no `if:`, so every push to `main` requests a deployment to it — the
`state=absent` notice path included. A required reviewer or a wait timer on an environment named
`release` would suspend all of them, which is E5's stay-green contract broken by a setting nobody
warned about. `docs/RELEASE.md` step 2 now says so where a maintainer acts on it, and section 23
below records the same reasoning next to the `distribute.yml` follow-up.

After the fixes the four demonstration edits were reverted (`git status` shows
`.github/workflows/dependency-review.yml` unmodified and `release.yml` byte-identical to the
GREEN section's version), and the whole suite is green again.

### 23 — the follow-up, and what §18's argument implies for `release.yml`

Section 18 records that `distribute.yml` deserves the same treatment later, and that an
environment with required reviewers would gate all seven of its build jobs rather than the
publish alone. The same argument applies to `release.yml` and was not drawn there: because its
one job is bound to `release` unconditionally, any protection rule beyond the deployment-branch
policy suspends *every* push to `main`, including the ones that release nothing. So the
constraint travels with the environment — `release` carries its branch policy and nothing else —
and a later milestone wanting a reviewer gate puts it on a second environment bound to
`distribute.yml`'s publishing job, which is where a human decision actually belongs.
`distribute.yml` is still untouched in this milestone.
