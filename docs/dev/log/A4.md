### 1 — the closed-set test asserted the table against itself (low)

`src/fault.rs` filters the action half of `GINARY_FAULT=<point>[:<action>]` through a closed set,
`ACTIONS`, so that a spec naming an action this build has no branch for arms nothing rather than
falling back to `on`. The test that was meant to hold that line,
`an_action_this_build_does_not_implement_arms_nothing`, called neither `point` nor `armed`. It
parsed each spec and then asserted `!ACTIONS.contains(&action)` — a statement about the table,
restated to itself. Nothing in it observed the filter, so removing the filter left it green.

The obstacle was structural rather than accidental. `armed` reads `VAR` through a `OnceLock`, once
per process, and edition 2024 makes `std::env::set_var` `unsafe` while the crate declares
`#![forbid(unsafe_code)]`, so a unit test cannot vary the spec a running process resolves. The
previous test worked around that by not resolving anything.

**GREEN.** `armed` splits in two. It still performs the single read of `VAR` and now delegates to
`armed_by(spec, name)`, which holds the rest — the parse, the point-name comparison and the
`ACTIONS` lookup. That is the seam a test can drive over many specs, and the four tests that
replace the old one do:

- `an_action_this_build_implements_arms_that_action` — each of the four implemented actions plus
  the bare-point `on` default resolves to itself, so the filter is pinned from both sides and a
  test cannot pass by rejecting everything.
- `an_action_this_build_does_not_implement_arms_nothing` — `rename:enospc`, `after-extract:kill`
  and `unpack:truncate` each resolve to `None`.
- `a_spec_arms_only_the_point_it_names` — a well-formed spec resolves to `None` for another point,
  and the empty spec resolves to `None`.
- `a_point_no_spec_can_name_is_never_armed` — through the public `point`, so the environment-
  reading path is exercised too. The name has no point in any build, so the assertion holds for
  whatever `GINARY_FAULT` the test process was started with, feature on or off.

Evidence that the new test observes what the old one could not: with the filter replaced by
`Some(ACTIONS.into_iter().find(|known| *known == action).unwrap_or("on"))` — the exact fallback
the closed set exists to prevent — the suite fails on an assertion,

```text
assertion `left == right` failed: `rename:enospc` armed something
  left: Some("on")
 right: None
failures:
    fault::tests::an_action_this_build_does_not_implement_arms_nothing
```

while the old test reports `ok` against that same mutation, because `ACTIONS` still does not
contain `enospc`. The filter was restored after the check.

`ACTIONS` and `armed_by` carry `expect(dead_code)` under `not(any(test, feature =
"fault-injection"))`, matching how `parse` was already gated: the default build compiles no fault
point, and the `expect` says so rather than an `allow` that would go stale silently.

### Two decisions this phase made, both for the GREEN reviewer

**`bundle::build_with_stub` and `bundle::check_stub` are public.** The spec asks for a unit seam so
that "a bundled executable cannot build" can be tested without a trailered `current_exe`.
`check_stub(&Path) -> Result<u64, BundleError>` is that seam: it is what `build` calls after
`selfexe::open_self`, it returns the stub's length — which is the payload's offset, so the caller
needs it anyway — and `tests/bundle.rs` hands it a `SyntheticArtifact`. `build_with_stub` is the
same seam one layer up, and it is where a cross-target build will later pass a downloaded stub.

**`GINARY_FAULT=pack:fail` is not in `src/fault.rs` yet.** `fault::ACTIONS` is a closed set of the
actions *this build implements*, and adding `fail` before `bundle` fires the point would make the
table a claim about nothing. GREEN adds the `pack` point, the `fail` action, and the row in the
module's own table; `a_build_that_fails_while_packing_removes_its_work_directory_too` is `#[cfg(feature
= "fault-injection")]` and fails today on the build's own failure, which is the assertion the
message above shows.

### What was implemented

**`src/config.rs`.** `ProjectConfig::from_toml` reads a `gleam.toml` through a permissive
`RawManifest` — a real manifest holds `target`, `dependencies`, `[erlang]` and whatever else, so
the strictness belongs one level down — and `[tools.ginary]` through `ToolsConfig`, which is
`deny_unknown_fields`. The four rules serde cannot state are `MissingName`, `InvalidName`,
`CompressionLevel` and `ErlFlag`, each naming the file. `BuildOptions::merge` applies the flags
over the table over the defaults, one helper per rule: `merge_strip` for the four strip flags,
`append_unique` for the two list settings, `resolve_output` for `--out`. The lint runs at the
merge as well as at the parse, because `BuildOptions` is what the bundler reads and a caller that
built one by hand must not get past the rule.

**`src/gleam.rs`.** `find_project` walks `Path::ancestors`. `export_shipment` runs the `gleam` on
`PATH` in the project directory under a ten-minute budget and passes its standard error through
verbatim. That needed one new function in `src/process.rs`: `run_in_dir_with_timeout`, which is
`run_with_timeout` plus a working directory, with the old signature delegating to it. `gleam` is
the first program ginary runs whose *input* is the directory it runs in; `doctor` and `otp` do
not care where they are.

**`src/bundle.rs`.** `build` opens `/proc/self/exe` and hands the path to `build_with_stub`, which
checks the stub, exports, discovers, resolves the closure, and then calls `assemble_and_write` for
the half that writes anything. The split is what gives the work directory exactly one removal
site rather than one per failure path.

Two orderings are worth naming. The stub check is *first*, ahead of the export the spec's sketch
put it behind: its remedy is "install plain ginary", and a build that exported a project and
staged an OTP installation before saying so would have spent minutes to say it. And
`report::measure` runs before `StagedRoot::refresh`, because `measure` wants the pre-strip
listing as its `before` and the refresh is what replaces those sizes with the ones the tree has.

The artifact is written into a `NamedTempFile` in the *output* directory — stub bytes through a
`BufWriter`, then `payload::pack`, then the 64-byte trailer — chmod 0755, then `persist`. The
rename therefore cannot cross a filesystem, and the destination is either absent or a complete
executable. `tempfile` moved from `[dev-dependencies]` to `[dependencies]`; the plan lists it
among A1's dependencies and this is the first caller.

**`src/inspect.rs`.** `open` reads the trailer, then `payload::read_index` over a `Take` of the
payload region; `verify` streams the same region past a `sha2::Sha256` in 64 KiB chunks and
returns both digests rather than a verdict, so the caller decides what a mismatch means.
`launch_plan` calls `launch::plan` against an empty `cache::Env`, so a `HOME` or a
`GINARY_ERL_FLAGS` that happens to be set where the inspection ran cannot reach the plan.

**`src/fault.rs`.** The `pack` point and the `fail` action, added together with the row in the
module's own table, as the RED note said they would be. It is the first point on the *build* side.

**`src/cli.rs`.** Only the long help changed: the pre-alpha notice said `build` was not
implemented, and a command that works beside a help text that says it does not is a worse defect
than either alone.

### The one production change RED did not ask for

`payload::pack` now flushes the compressor after `ginary.index.json`, and
`docs/adr/0009-front-entries-in-their-own-zstd-block.md` records why.

`tests/inspect.rs::a_corrupted_artifact_still_says_what_it_claims_to_be` and its two neighbours in
`tests/cli.rs` require that `ginary inspect` without `--verify` still prints the manifest of a
file that fails `--verify`. Against a real artifact that already worked, because the front entries
land in an early zstd block. Against a `SyntheticArtifact` it could not work at all: its payload
is a few kilobytes, zstd decodes a block at a time, and a single-block payload has no front — the
decoder answers `Data corruption detected` before entry 0 comes out, wherever the flipped byte
was. The property was holding by accident for large inputs and not at all for small ones, which
is not a format guarantee.

The flush makes entries 0 and 1 a block of their own. Determinism is untouched — the boundary is
at a fixed position in the archive rather than at a buffer boundary — and `tests/payload.rs`'s
`packing_the_same_tree_and_manifest_twice_produces_the_same_bytes` still passes, as does every
other payload and launcher test.

**1 — `SyntheticArtifact::break_payload_tail`, and four call sites moved onto it.**
`tests/common/artifact.rs` gained a second way to damage a payload: `break_payload` flips the byte
at the *middle* of the compressed stream, `break_payload_tail` the one sixteen bytes before its
end. The four A4 call sites — `tests/inspect.rs:254`, `tests/inspect.rs:282`, `tests/cli.rs:1620`,
`tests/cli.rs:1647` — use the new one; the two A3b call sites in `tests/cache.rs` and
`tests/launcher.rs` are untouched.

The reason is the one above. Those four tests are about a file that fails `--verify` and can still
be *read*, and with the flush in place the readable region is everything up to the end of entry 1.
The middle of a small payload is past that boundary only by luck — for this artifact the manifest
and the index are most of it — so the tests would have been asserting a coincidence. Sixteen bytes
before the end is past both front entries in any tree, and it is exactly where
`tests/e2e_hello.rs` damages a real artifact by hand, so the synthetic and the real case now
disagree about nothing. The launcher's exit-123 tests keep the middle-of-payload damage, because
what they need is a digest that no longer matches and nothing more.

**2 — `tests/e2e_hello.rs::two_builds_of_one_project_with_a_pinned_clock_are_byte_identical`
passes `--out first/` and `--out second/` rather than `--out first` and `--out second`.**
The test then read `<root>/first/hello_ffi`, so it wanted `first` to be a *directory*. Without a
trailing separator it is not one: `config::resolve_output` treats a `--out` that is neither an
existing directory nor separator-terminated as the artifact's own path, which
`tests/config.rs::an_out_that_names_a_file_is_the_artifacts_own_path` and
`a_relative_out_is_relative_to_where_the_user_is_and_not_to_the_project` both pin. The build was
correct and wrote a file called `first`; the test's two halves disagreed with each other. Adding
the separator is what the test meant, and it exercises the "not there yet, so only the separator
can say so" branch of the rule into the bargain.

**3 — `src/cli.rs`'s long help.** Not a test change but the same category: the unit test
`the_long_help_mentions_the_planned_build_command` was renamed to
`the_long_help_names_the_command_a_reader_came_for` and now also asserts the absence of
`pre-alpha`, which is what `tests/cli.rs::the_help_lists_the_build_and_inspect_commands_...`
requires of the rendered help. The old name described a command that is no longer planned.

### GREEN

**1 — a program name was a path (high, `src/assemble.rs`, `src/config.rs`).** `erts_extra_bins`
and `--extra-bin` are joined onto the runtime's `erts-<vsn>/bin` to find a program and onto the
staged `bin` to write it, and nothing checked either name. A cloned project whose `gleam.toml`
held `erts_extra_bins = ["../../../victim"]` therefore had `ginary build` read one file outside
the project and truncate another, and exit 0 with a normal size report.

`assemble::is_erts_bin_name` is now the rule, and it is the one `closure` already applies to an
application name: not empty, not `.` or `..`, and holding neither a path separator nor a NUL.
Three places check it, because the value arrives from three directions and a rule enforced only
by its caller is a rule one caller can forget:

- `ToolsConfig::validate` refuses the table entry with `ConfigError::ExtraBin`, by path and
  message like the four rules beside it — so the fifth rule serde cannot state is now a rule;
- `BuildOptions::merge` refuses the flag with `ConfigError::ExtraBinFlag`, which names
  `--extra-bin` rather than a file, because no file holds it;
- `assemble::stage_erts_bins` refuses it with `AssembleError::UnusableExtraBinary` before either
  join, which is the check that actually stands between a name and the copy.

`tests/fixtures/config/bad_extra_bin.toml` joins the other invalid manifests and
`tests/config.rs` asserts its variant, its path and its message; a second test pins the rule from
both sides over four names that are program names and seven that are not.

**2 — a tautology, and `total_len` with no coverage (high, `tests/bundle.rs`).**
`the_total_length_is_the_stub_the_payload_and_the_trailer` compared a fixture's literals with
themselves. It is now `the_rendered_report_ends_with_the_artifact_line`, which keeps the half that
was genuine and says in a comment why the arithmetic is not asserted there. The arithmetic is
asserted in `tests/e2e_hello.rs::the_json_report_describes_the_file_that_is_actually_on_disk`,
against a real build: `--report json` names `format_version`, `app`, `out`, the three lengths and
the digest, and the test compares `total_len` with `std::fs::metadata(..).len()` of the artifact
and with `stub_len + payload_len + 64`. Removing the trailer term from `assemble_and_write` now
fails it by exactly 64 bytes.

**3 — the build seam had no test (medium, `src/bundle.rs`).**
`a_build_refuses_a_bundled_stub_before_it_looks_at_the_project` drives `bundle::build_with_stub`
over a `SyntheticArtifact` and a `TempProject` that has no shipment, with `--skip-export` set, so
