### 15 — cause 3, the launcher-path defect, in full

`cache::sweep` decides whether a `.<key>.tmp-<pid>` tree belongs to a launcher still extracting
into it. The whole decision was

```rust,ignore
fn is_alive(pid: u32) -> bool {
    Path::new("/proc").join(pid.to_string()).exists()
}
```

which answers `false` for every process that has ever run on Windows and on macOS, so a launcher
sweeping the cache deleted the tree another launcher was at that moment unpacking into.
Liveness is now asked of the process table:

- **unix** — `rustix::process::test_kill_process`, which is `kill(pid, 0)`. `ESRCH` is the only
  answer that means dead; `EPERM` means the process exists and belongs to somebody this user may
  not signal, which is alive. rustix is already the crate's unix dependency for `getuid`, `flock`
  and `syncfs`, so the unix launcher path still opens no `unsafe` block and no dependency was
  added.
- **Windows** — `launch_windows::win32::process_is_alive`: `OpenProcess` with
  `PROCESS_QUERY_LIMITED_INFORMATION`, the narrowest access right there is, and an immediate
  `CloseHandle`. It is a fourth call in the module that already carries the crate's only
  `#[allow(unsafe_code)]`, and it lives there rather than in `cache.rs` for exactly the reason
  the other three do: `CLAUDE.md` requires an ADR for a *new* `#[allow(unsafe_code)]` anywhere,
  and the exception is worth more as one reviewable surface than as two. No new dependency and
  no new `windows-sys` feature: `Win32_System_Threading` was already enabled for the job object.
  `ERROR_INVALID_PARAMETER` is the counterpart of `ESRCH` and the only failure read as dead;
  `ERROR_ACCESS_DENIED` — a process this user may not query — is alive, for the reason `EPERM`
  is.

Both implementations answer `true` for anything they could not determine, because the two
mistakes are not symmetric: a tree kept costs a directory until the next sweep that can name it,
and a tree removed destroys an extraction in progress. A number that *cannot* be a process id is
not uncertain and is `false` — a unix `pid_t` is a positive `i32`, so neither `0`, which names
the caller's process group to `kill`, nor anything past `i32::MAX` has ever named a process, and
`tests/cache.rs` plants `4_000_000_000` for exactly that reason.

The Linux half of the rule is `e12_the_sweep_asked_proc_whether_a_process_was_alive`, which
holds `src/cache.rs` to naming no Linux filesystem in code; the behavioural half is
`tests/cache.rs`'s own `a_live_process_s_temporary_tree_is_kept` and
`a_dead_process_s_temporary_tree_is_removed`, which run on all three platforms.

### 16 — cause 1, and why it needed two rules rather than one

`stub::verify` has two gates and `tests/stub.rs` was asking both of them for the same thing.

The *target* gate refuses a stub whose marker names somebody else's target, and it is reached
before the object header is read at all, so the container format is irrelevant to it. What it
needs is a target this ginary has a name for. `stubfile::same_format_other_arch` answered "the

host's own binary in place — `e_machine` at offset 18 of an ELF, the COFF `Machine` four bytes

### 17 — cause 5, and the half no text rule can settle

The `hello_ffi` fixture prints `cwd=` and whatever `file:get_cwd/0` gives it, and both tests that
run it compared that against a directory they had built, as strings. On Windows one directory has

neither could be resolved. `hostpath::printed_cwd` is the other half of the fix: having the
printed spelling to hand at all, rather than asking `String::contains` for a needle built with

### 33 — cause I: a file the user can see, reported missing

`assemble::windows_required_bins` compares the three required names exactly and E12 taught the
decline beside them to compare case-insensitively. A tree whose zip spelled the emulator
`BEAM.SMP.DLL` was therefore refused with

```text
the ERTS binary `beam.smp.dll` is missing; looked for it at
`…/erts-17.0.5/bin/beam.smp.dll`
```

naming a file that is in the directory the message points at, and leaving the user nothing to do.

The rule itself is right and stays: the three names are matched exactly because every other gate
that names these files names them literally — `assemble::is_windows_erts_bin` decides a tree's
flavour by joining `erl.exe` onto it, `launch::WINDOWS_REQUIRED_BINARIES` checks the extracted
tree by name, and the index a Linux host verifies a Windows artifact against carries the name the
tree was staged under. A tree admitted here under another spelling would satisfy this one rule
and fail those on any case-sensitive host, so accepting it would be a change to four rules and a
staged tree, not to one comparison. What was owed to the user is the diagnosis, so the refusal is
now `AssembleError::ErtsBinaryNamedInAnotherCase`, which names the spelling the tree really uses
beside the spelling ginary needs. A file that is genuinely not there is still
`MissingErtsBinary`: the two are different problems and only one of them is fixed by renaming.
`windows_required_bins`'s documentation now states the exactness and the reason for it, so the
next reader does not have to infer that the two comparisons beside each other disagree by
accident.

The three tests are in
`tests/regressions/e12_a_required_erts_name_was_reported_missing_from_the_tree_holding_it.rs`.
The first failed against the tree as it stood:

```text
---- …::the_refusal_names_the_spelling_the_tree_uses ----
and the spelling the tree really uses, because `BEAM.SMP.DLL` is in the directory the message
says `beam.smp.dll` is missing from, and a user told a file they can see is not there has nothing
to do next: the ERTS binary `beam.smp.dll` is missing; looked for it at
`/tmp/…/erts-17.0.5/bin/beam.smp.dll`
```

The second, `a_file_that_is_not_there_at_all_is_still_diagnosed_as_missing`, compares the two
refusals up to the path they end with — the whole messages differ only in a temporary directory,
so comparing those would have passed whatever they said — and against the old code both
diagnoses were the byte-identical `the ERTS binary `beam.smp.dll` is missing; `. The third pins
what the exactness buys: a required name travels under the name every other gate names it by.

### 35 — cause K: a test that could fail with no defect behind it

`a_reaped_process_s_temporary_tree_is_removed` is the only input in the suite that reaches the
`Errno::SRCH` / `ERROR_INVALID_PARAMETER` arm, so it earns its place. Its exposure is the window
between `drop(child)` — which is what makes the id eligible for reuse — and the sweep that asks
about it. Windows hands ids back out of a recycled pool rather than climbing to a `pid_max`; this
suite spawns many processes and CI runs its targets in parallel, so on the platform this
milestone is fixing the id can belong to somebody else by the time the sweep looks, and then
keeping the tree is the *correct* answer.

That outcome is now a re-run rather than a failure: the test asks up to `REAPED_PID_ATTEMPTS`
times, each attempt with a fresh reaped id and its own application directory, and asserts on the
last one, so a genuine defect still fails with the same message. The window and why a retry is
sound are written into the test rather than left for a future flake to re-litigate. The test is
still non-vacuous — changing `Errno::SRCH` to `Errno::PERM` in `src/cache.rs` fails it after all
five attempts:

```text
---- a_reaped_process_s_temporary_tree_is_removed ----
assertion `left == right` failed: the launcher that owned this tree has gone, so the tree it was
extracting into is a leftover and the next launcher may have the space back
  left: []
 right: ["/tmp/…/hello-5/.abc.tmp-443"]
```
