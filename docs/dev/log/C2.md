## Housekeeping

One item carried over from C1, closed before any C2 product code was written. The working tree

### 1 — two `doctor` tests failed rather than skipped on a machine with no Erlang (medium)

C1 gave the targets table a `resolves` column, and made the host's own row honest: `erts = "host"`
on the host target is the one row `doctor` actually resolves, so a machine whose installation
cannot be read answers `not yet` with the reason beside it rather than `yes` with a contradiction
three rows above. That is the right behaviour, and two tests in `tests/doctor.rs` were written
against the machine that has an Erlang on it:
`a_target_with_no_sub_table_is_probed_as_the_host_runtime` asserted `probes[0].resolvable`, and
`doctor_json_carries_a_row_per_target` asserted `targets[0]["resolvable"] == true` off the real
command's JSON. Neither was gated. On a machine with no `erl` on `PATH`, plain `cargo test`
therefore *failed*:

```
thread 'a_target_with_no_sub_table_is_probed_as_the_host_runtime' panicked at tests/doctor.rs:555:
[TargetProbe { name: "linux-x86_64-gnu", erts: "host", resolvable: false,
  detail: Some("cannot use the runtime: `erl` is not on PATH; ...") }]
```

`docs/dev/testing.md` promises the opposite: a test that needs a program it has not got prints
`skipping: <tool> not on PATH` and returns, and `GINARY_REQUIRE_TOOLCHAIN=1` is what turns that
skip back into a failure where a skip would be dishonest. A test that fails instead is a false
alarm on every contributor's machine that has no Erlang, and it is the same defect class as a
silent skip seen from the other side.

RED was reproduced by running the built `tests/doctor.rs` binary with `PATH` pointing at an empty
directory; both tests failed, for the two reasons above.

The fix takes the seam rather than the gate, because gating alone would have deleted the coverage
on exactly the machines the column exists for. `doctor::probe_targets_with` is
`doctor::probe_targets` with the runtime resolution injected — the same shape C1 gave
`erts_source::resolve_with` one layer down — and it is called only for the host's own row, which
is the only row that reads anything:

```rust
pub fn probe_targets_with(
    targets: &[Target],
    config: &BTreeMap<String, TargetConfig>,
    resolve: impl Fn(&ErtsSourceSpec, &Target) -> Result<ResolvedErts, ErtsError>,
) -> Vec<TargetProbe>
```

Both halves of that branch are now pinned with no toolchain at all. The rewritten
`a_target_with_no_sub_table_is_probed_as_the_host_runtime` hands the probe a resolution that
succeeded and asserts the row copies its provenance, its linkage and its minimum libc — values
this machine's own installation need not have, so a row that invented them rather than reading
them fails. `a_host_whose_own_installation_cannot_be_read_is_a_row_that_says_not_yet` is new: it
hands back `ErtsError::Otp(OtpError::ErlNotFound)` and asserts the `not yet`, the whole error
chain in the detail, and the two empty columns. That second test is the one a toolless machine
would have been telling the truth about all along.

The command-level test was split rather than weakened. `doctor_json_carries_a_row_per_target`
keeps the wire shape — one row, the host's name, `erts: "host"`, and a `resolvable` that is a
boolean — and the new gated
`the_host_row_the_command_prints_resolves_on_a_machine_with_an_erlang` asserts the value that
depends on the machine, behind `require_tools(&["erl"])`. The claim is pinned twice without a
toolchain and once with one; nothing was traded away for the skip.

Confirmed both ways. With `PATH` emptied, `tests/doctor.rs` runs 35 tests, all pass, and standard
error carries three `skipping: erl not on PATH` lines — the two that were already gated and the
new one. And the assertion still bites: flipping `resolvable: true` to `false` in the resolved
branch of `probe_target` fails
`a_target_with_no_sub_table_is_probed_as_the_host_runtime` on a toolless run, which is what says
the seam tests a behaviour rather than a stub.

`docs/dev/testing.md` records the new seam beside C1's, and the reason it exists.

### The marker: `build.rs` + `src/stubid.rs`

`build.rs` emits two variables and deliberately not a third. `GINARY_TARGET` is Cargo's `TARGET`
mapped onto the canonical target name through a seven-entry table — `std::env::consts` answers
for the *host*, and a cross-compiled stub is precisely the case where the host is the wrong
answer. `GINARY_FLAVOR` is `full` or `stub` from the presence of `CARGO_FEATURE_CLI`. The format
version is *not* emitted: it is `manifest::FORMAT_VERSION`, a constant the crate already owns,
and a second source for it would be a second thing to forget. A Rust triple the table has no name
for is a `panic!`, which in a build script is a compile error naming the triple and the two
places to add it.

`GINARY_STUB_ID` is `[u8; 128]`, rendered by a `const fn` over `put`/`put_u32`, so the whole
record is laid down while the crate compiles and two builds of one ginary for one target are the
same bytes down to the padding. The `assert!`s inside it are compile-time: the function's only
caller is the initialiser of a `static`, and there is no run-time path into it.

Keeping it is two things, and one alone is not enough. `#[used]` stops the compiler dropping a
static nothing reads; a linker that garbage-collects sections would still drop it, so `main` takes
its address through `std::hint::black_box` on the one path every run takes. That is one
instruction before a file read, and `tests/stubid.rs::the_binary_this_test_run_built_carries_
exactly_one_marker` is what would fail if either half were removed.

`scan` assembles its needle at run time from `NEEDLE_HEAD` and `NEEDLE_TAIL`. Checked rather than
assumed: the built binary holds the 15-byte name at exactly one offset, so the two halves did not
land adjacently in `.rodata`.

```
$ python3 - <<'PY'
b=open('target/debug/ginary','rb').read(); n=b'GINARY-STUB'+b'-ID\0'
...
PY
1 [991163]
b'GINARY-STUB-ID\x00v=0.1.0;t=linux-x86_64-gnu;f=1;k=full\x00\x00...'
```

The field parser is **positional**, and that is a decision rather than an accident. A marker is
written by ginary in one order and by nothing else, so the field at each place must carry the key
that belongs there. A record naming three fields then says which one is
*missing* — `v=…;f=1;k=…` is `MissingField { field: "t" }`, because position 1 does not hold
`t` — and a fifth field is named as the surplus it is. A key-value map would have
had to invent an answer for a duplicate key; this shape has one already.

### `src/stub.rs`

`candidate_paths` builds the list and `locate` walks it, so the order is testable without a
directory full of files and `NotFound` prints exactly what was tried. `--stub` is first and is an
instruction: a candidate marked `Explicit` that is not a file returns `Missing` rather than
falling through, because a build that quietly packaged a file the user did not name would be
wrong in a way nobody could see.

`verify` is seven gates in the order the bytes justify: the size cap before the read (so a
`--stub` aimed at a disk image is a refusal, not an allocation), exactly one marker, the version,
the payload format, the target, the object header, and the trailer last. Two of those deserve a
sentence.

**The header outranks the marker.** The marker is text and text copies — `stub_copy` in the test
suite rewrites one in milliseconds — while `e_machine` is what the linker wrote. `check_object`
reads the ELF through `crate::elf` (one place answers "what is this binary for") and a PE through
`object` directly, and a static ELF is matched on its machine alone, because a binary with no
`PT_INTERP` names no C library and `target::ElfTarget::StaticLinux` already models that. A Mach-O
is `NotYetSupported` with a sentence saying where a darwin stub comes from: there is no macOS
toolchain here, so the check would have been written against nothing.

**The trailer is last** because it is the one question about what was *done* to the file rather
than about what the file is. A damaged trailer is refused as loudly as a whole one, for the reason
`bundle::check_stub` already gives.

### The `cli` feature, and what it really gates

Eighteen modules are gated whole: `appfile`, `beam`, `bundle`, `cache_dir`, `cli`, `closure`,
`crashdump`, `doctor`, `elf`, `erts_source`, `gleam`, `inspect`, `otp`, `report`, `sbom`,
`strip`, `stub` and `verify`.

Two are split, and the reason is a dependency the launcher genuinely has:

- **`assemble`** — `manifest::Index` is written in terms of `Category` and `StagedFile`, and
  `payload::pack` reads `ginary.stage.json` as a `StageListing`. Those *listing* types stay
  unconditional (54 `#[cfg]`s gate everything from `StageOptions` down, and the `closure`/`otp`
  imports with them). Keeping `pack` unconditional is not decoration either: `SyntheticArtifact`
  is built from it, and without it the launcher contract could not be asserted in the stub flavor
  at all.
- **`config`** — `launch` maps the manifest's `filename_encoding` onto `+fnu`/`+fnl`, and
  `manifest` uses the default. `DEFAULT_FILENAME_ENCODING`, `FILENAME_ENCODINGS` and
  `filename_encoding_flag` stay; 51 `#[cfg]`s gate the rest, including every use of the TOML
  reader.

`process` stays whole: it is dependency-free, nothing on the launcher path calls it, and the
linker drops what `main` cannot reach. Its one `pub(crate)` constant that only `otp` uses is
gated, so `--no-default-features` compiles without a dead-code warning.

The rule the split follows is the one the architecture already stated, now checked by a compiler:
anything the launcher needs is unconditional, everything else is behind `cli`.

`src/main.rs` grew a second `no_trailer`. With `cli` it is `cli::run()`; without it, the sentence
`launcher::no_payload_line` owns and exit 2 — the same code a usage error leaves, because that is
what running a stub with no payload is.

### The build path

`bundle::build_targets` no longer refuses a cross target; `BundleError::CrossTargetNotAvailable`
is gone. Three things now happen before `gleam export`, in this order, because each is a fault in
the command line or in `gleam.toml` and the export costs minutes:

1. `check_stub(self)` — the "a bundled executable cannot build" rule, unchanged.
2. `resolve_stubs` — one stub per target. The host with no `--stub` is the running executable, as
   before; every other target is `stub::locate` then `stub::verify`, and the failure is
   `BundleError::Stub { target, source }` so the headline names the target and the cause names
   the file.
3. `check_cross_erts` — a target other than the host with no `[tools.ginary.target.<name>]` and
   no `--otp-root` is `BundleError::CrossErtsNotConfigured`, whose message quotes the table to
   write. There is no catalogue yet, and bundling the host's runtime instead would produce an
   artifact whose name promises a machine it cannot start on.

The stub check comes before the runtime check deliberately: the stub is about the tool's
installation and the runtime is about the project, and a developer with neither should be told
about the tool first. `tests/stub.rs::a_cross_build_with_no_stub_names_every_path_it_searched`
pins that order through the real binary.

`ginary build --stub PATH` was added to the CLI and to `BuildFlags`/`BuildOptions`, and applies
to whichever target is being built. With more than one target it is used for each and `verify`
refuses it for all but one, which is the honest outcome of naming one file for several machines.

### The chain, end to end, on this machine

The claim C2 is really making — a real cross-built stub passes every gate and the *runtime* is
then refused — reproduced by hand as well as by the gated test:

```
$ GINARY_STUB_DIR=…/target/stubs ginary build --skip-export --target linux-x86_64-musl
error: cannot resolve the runtime to bundle
  caused by: the runtime at …/erlang/29.0.5 is for linux-x86_64-gnu, and this build is for
  linux-x86_64-musl; build with `--target linux-x86_64-gnu`, or point `erts` at a
  linux-x86_64-musl runtime
```

The stub was located, its marker read, its version and format and target checked, its ELF header
read (static-pie, no interpreter, x86_64) and its lack of a trailer confirmed — and then C1's
runtime check refused the host's glibc ERTS. A complete musl artifact needs a musl runtime, and
that arrives with the catalogue milestone.

### `mise run stubs:build`

Five targets, `cross build --release --target <triple> --no-default-features` each, copied to
`target/stubs/ginary-stub-<version>-<target>[.exe]`. Two details cost a run each and are written
into the task:

- `cross` mounts the project at `/project` inside the container, so a host `--manifest-path` names
  a file that is not there. The working directory is what it maps.
- The task exports `CARGO_TARGET_DIR=target/cross`. Build scripts are compiled for the *host* and
  then run, and the host's are linked against this machine's glibc while the container's is years
  older; sharing `target/` makes every cross build fail with
  `version 'GLIBC_2.34' not found` in a build script nobody asked for.

### 1 — `the_stub_sentence_names_a_target_this_ginary_knows` could not fail (high)

The test built its sentence from `Target::host()` and then asserted that *some* member of
`target::ALL` appears in it. `Target::host()` is `Target::new(HOST_OS, HOST_ARCH, HOST_LIBC)` and
`src/target.rs` already carries a doctest asserting `ALL.contains(&Target::host())`, so the
predicate was true by construction on every machine. Its own comment claimed it pinned the
`build.rs` triple mapping against the printed sentence, and it read neither `stubid::TARGET_NAME`
nor `GINARY_STUB_ID`.

Renamed to `the_stub_sentence_names_the_target_the_marker_does` and made to assert what the
comment says: `stubid::TARGET_NAME == Target::host().name()`, then
`stubid::scan(&GINARY_STUB_ID)?.target == Target::host()`, then that the sentence names that
target. A `build.rs` table entry that mapped this triple to the wrong name now fails here as well
as in `tests/stubid.rs`. Not behavioural — no product code changed.

### 2 — a target sub-table that named no runtime slipped the pre-export guard (medium)
