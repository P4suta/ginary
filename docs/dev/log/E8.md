#### A1 — `verify`'s five issues, and what they actually are

The leading hypothesis is **confirmed, and sharpened**. The five issues the
Windows runner reported against a healthy artifact are all one kind:

```text
{ "issue": "index_mode_mismatch", "path": "erts-17.0.5/bin/beam.smp",
  "indexed": "0644", "expected": "0644", "actual": "0755" }
```

and the five paths are `erts-17.0.5/bin/beam.smp`,
`erts-17.0.5/bin/erl_child_setup`, `erts-17.0.5/bin/erlexec`,
`erts-17.0.5/bin/inet_gethost` and `lib/hello/priv/bin/tool` — every program in
the tree and nothing else.

What the hypothesis got right: the comparison is between a column the index
records and a column the header carries, and on Windows neither is what the
comparison assumes. What it got wrong is *which* side is at fault. `verify` is
correct and stays exactly as it is: an index that disagrees with the payload it
describes is a real finding, and switching the check off on one platform would
hide it. The defect is upstream, and it is that **one file's mode has three
producers and they do not agree**:

| producer | unix | a filesystem with no mode word |
|---|---|---|
| `assemble::mode_of` (the staging listing) | `st_mode & 0o7777` | **`0`** |
| `manifest::mode_of` (`ginary.index.json`) | `st_mode & 0o7777` | `0o755` dir / `0o644` file |
| `tar`'s `HeaderMode::Deterministic` (the payload header) | `0755`/`0644` | `0o755` dir / `0o644` file |

D2 already wrote the second row deliberately, so that the index and the header
would agree; the first row was never brought into line, and the test helper
that stands in for a staging tree hard-codes `0o755` for a program it then
writes without an execute bit. So on Windows the header said `0755`, the index
said `0644`, and `verify` reported the difference — which is its job.

The fix is one rule with one answer: `platform::modeless_mode`, the value a
platform without permission bits records, which is by construction the value
`HeaderMode::Deterministic` writes there. The column stays informational on
such a platform, as D2 said it was, and it stays comparable on every platform.

**Where the five issues actually came from (Fix round 1 correction).** Reviewed
again, the account above overstates the production fix. `ginary verify` compares
`ginary.index.json`'s `mode` against the payload's *tar header* — not against
`ginary.stage.json`. Both of those producers read the filesystem
(`Index::from_staged` via `manifest::mode_of`, the header via
`set_metadata_in_mode`), so on Windows both already answered `0o644` before E8:
they never disagreed with each other, and `assemble::mode_of` — which fills the
stage *listing* — is not one of the two `verify` compares. The `0o755` the
runner reported can only have come from the **test fixture**:
`tests/common/repack.rs` builds its tar headers from the *listing*, and
`tests/common/artifact.rs::stage` filled that listing with the requested `0o755`
while `set_mode` was a no-op off unix. So the change that actually fixes the
runner is test correction #1 (§10), `common::payload::recorded_mode`; the
production `assemble::mode_of` edit was brought into line for consistency —
so a future reader cannot cite a `0` where the other two producers write a real
mode — rather than because `verify` reads it. A1 is best read as a fixture
defect with a consistency tidy-up alongside, not a live product-verification
defect; the product-level guard that *would* fail if the three producers ever
diverged is `tests/regressions/e8_two_producers_disagreed_about_one_files_mode.rs`
plus the fixture round-trip through `verify` the existing `tests/verify.rs`
already performs.

#### B — which process died, and why

Reading (a), and the log says so in one line. `codesign` never ran:

```text
/Users/runner/work/_temp/84fd6172-....sh: line 10:  7695 Killed: 9   "$artifact" 0 hello world
##[error]Process completed with exit code 137.
```

Line 10 of that step is `"$artifact" 0 hello world`, the artifact's own run;
`codesign --verify` is line 12. 137 is 128+9 and `Killed: 9` before the program
prints anything is the kernel refusing to map a page whose hash does not match
the `CodeDirectory` — the failure mode ADR 0016 predicted for an appended
payload and claimed the `__GINARY,__payload` section avoided. Both runners, both
architectures, the same line: an *invalid* signature is worse than no signature
on x86_64 as well as arm64.

`Writer::build` computes the page hashes over `body`, and then writes four more
fields into it — `LC_CODE_SIGNATURE`'s `dataoff` and `datasize`, and
`__LINKEDIT`'s `vmsize` and `filesize`. All four are in the load-command area,
which is page 0. Slot 0 therefore describes a page that no longer exists by the
time the file is closed. `tests/common/codesign.rs` is the new helper that
proves it: it walks the load commands, parses the superblob and the
`CodeDirectory` field by field from Apple's `cs_blobs.h` layout, and recomputes
the SHA-256 of every 4096-byte page — none of it through `src/sign_macos.rs`,
so the test is a check of the signer rather than a restatement of it.

#### B — what the signer does now

`AdHocLayout::at(sig_off)` is the one producer of the signature's length, so
`build` can write `datasize` into a load command before the blob that fills it
exists, and `build_ad_hoc_signature` cannot drift away from the number that was
written. The order is now: assemble the body; pad to `SIGNATURE_ALIGNMENT`;
patch the four fields; hash. All four fields live in the load-command area,
which is page 0, and slot 0 is the slot that disagreed.

Both readings the milestone offered were tested against the log and (a) is the
one it supports: `codesign` never started. Line 10 of that step is the
artifact's own run and line 12 is `codesign --verify`; the step died on line 10.
So the fix is in `sign_macos.rs` and not in the runner's headroom.

The workflow step now reads the signature before it runs the artifact —
`codesign --display --verbose=4` (diagnostic, cannot fail the job) then
`codesign --verify --strict --verbose=4` — and keeps the original
`codesign --verify --strict --verbose=4` after the two runs. Neither assertion
was deleted or softened; what changed is that an invalid signature is now
reported as an invalid signature rather than as a bare `Killed: 9`, which is
the whole of what made this failure expensive to read.

### 10 — GREEN / test corrections

Four, each one a test that was asserting something the platform cannot do
rather than something the product got wrong. No assertion was deleted.

1. **`tests/common/artifact.rs::stage` and `tests/common/payload.rs::staging_tree`
   recorded the mode they asked for, not the one the file got.** Both call a
   `set_mode` that is a no-op off unix and then write the requested `0o755` into
   `ginary.stage.json`. That listing is what `tests/common/repack.rs` builds the
   payload's tar headers from, while the index is read off the filesystem — so
   on Windows the header said `0755`, the index said `0644`, and `ginary verify`
   reported five issues against an artifact nothing had damaged. Both now record
   `common::payload::recorded_mode(mode, is_dir)`, which is the requested mode
   where the filesystem has permission bits and `platform::modeless_mode` where
   it has none. On Linux nothing changes.
2. **`tests/payload.rs::the_packed_headers_keep_the_mode_the_file_has_on_disk`
   expected `0o755` for `erts-17.0.5/bin/erlexec` on every platform.** Its own

### R1 — the injected segment broke page alignment (high, behavioural)

`src/sign_macos.rs`. `Writer` inserted the `__GINARY,__payload` segment by
shifting every following byte forward by `header_growth = 152` (one
segment-and-section command, less the dropped `LC_CODE_SIGNATURE`). 152 is not
a multiple of a page, so on the committed arm64 fixture every segment after
`__TEXT` landed at `fileoff % 0x4000 == 152` and `round_page(__TEXT.vmsize) =
round_page(0x8098) = 0xC000` swallowed both `__DATA_CONST` and `__DATA`. The
new segment was also emitted *after* `__LINKEDIT` while sitting at a lower
`vmaddr`. This is independent of the hash-ordering fix and equally explains the
SIGKILL, so the "defect was ordering, not shape" claim was incomplete.

RED (`tests/regressions/e8_the_injected_segment_broke_page_alignment.rs`, three
tests, pure arithmetic over the emitted load commands, run on Linux):

```text
---- every_segment_the_writer_emits_is_page_aligned stdout ----
assertion `left == right` failed: segment __DATA_CONST has vmaddr 0x100008098,
which is not on a 0x4000 page boundary
  left: 152
 right: 0
---- no_page_rounded_segment_range_overlaps_its_neighbour stdout ----
segment __TEXT rounds up to end at 0x10000c000, past where __DATA_CONST begins
(0x100008098)
---- the_segments_are_emitted_in_increasing_vmaddr_order stdout ----
segment __LINKEDIT (vmaddr 0x100014098) is emitted before __GINARY (vmaddr
0x100010098); the load-command order must be non-decreasing in vmaddr
```

The fix: `Writer::plan` rounds the load-command growth up to
`SEGMENT_PAGE_ALIGN` (`file_shift`), shifts every following `fileoff`/`vmaddr`
by that whole page rather than by the raw 152, pads the gap between the load
commands and the first byte of content by `file_shift - header_growth`
(`lc_padding`, emitted in `build`), and inserts the new segment *before*
`__LINKEDIT` in load-command order. `header_growth` still sizes the
load-command area itself (`sizeofcmds`), which is what the header must report.

#### R2b — no Windows machine could resolve a build cache at all

`cache_dir::resolve` is the *build* side's projection of the launcher's cache
precedence. It read `GINARY_CACHE_DIR`, `XDG_CACHE_HOME` and `HOME`, and its own

those three, so the function answered `Unresolved` for every ordinary Windows
environment, and every failure downstream of a build was reported as that
instead of as itself — which is why `tests/bundle.rs` saw `CacheDir(Unresolved)`
where it expected an honest `BundleError::Stub`, and why `tests/sbom.rs` saw a
runtime-source refusal instead of a document.

The launcher half already knew the answer: `cache::resolve_windows` has returned
`%LOCALAPPDATA%\ginary` since the Windows launcher landed. The projection now
dispatches on `platform::has_local_app_data(os)` the same way, so both
precedences are asserted here, and it keeps the one deliberate difference on
*both* platforms — a build refuses the fallback root (`${TMPDIR}` on unix,
`%TEMP%` on Windows), because a build tool that silently wrote its output into a
temporary directory is a build tool nobody can find the output of.

### 17 — the low finding: a parameter named for a quantity that no longer flows

`src/sign_macos.rs`. `Writer::plan` distinguishes `header_growth` — the
`added_len - removed_len` that sizes the load-command area and is what the
header's `sizeofcmds` reports — from `file_shift`, the page-aligned distance
every byte of content and every `vmaddr` moves. R1 introduced the distinction
and passed `file_shift` into `shift_segment`, `shift_fields`, `shift_value` and
`shift_value_u64`, whose parameters were still called `header_growth` and whose
documentation still described the 152-byte quantity. Behaviour was correct; a
maintainer reading a helper saw the wrong number named. The four parameters and
their documentation now say `file_shift`, and the `plan`-level distinction —
which is the one that matters — is untouched.
