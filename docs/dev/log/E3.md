### The two guards, and why their red had to be staged

`every_workflow_defaults_to_a_read_only_token_and_never_persists_credentials` and
`every_job_of_every_workflow_declares_its_own_permissions` are guards over *every* workflow,
including the three E3 adds, so on the current tree they pass: the four committed workflows
already start from `permissions: {}` and every job already names its own scopes. A guard that
cannot fail is not evidence, so their red was demonstrated the way `tests/docs.rs` demonstrates
its own — by breaking the tree on purpose, running, and restoring:

```text
$ # temporarily: top-level `permissions: contents: write`, and the `required:` job's own
$ # permissions block deleted
$ cargo test --test ci_matrix -- every_job_of_every_workflow every_workflow_defaults
panicked at tests/ci_matrix.rs:771:9:
.github/workflows/ci.yml defaults to `permissions:
contents: write`, which grants more than read; widen per job instead

panicked at tests/ci_matrix.rs:802:5:
every job states the scopes it needs, so a widening is a line in the diff; these do not:
.github/workflows/ci.yml: job `required`
```

`ci.yml` was restored from a copy immediately afterwards; `git status` shows it unmodified.

The first of the two is the one place a rule was *changed* rather than added. It used to require
the literal `permissions: {}` in every workflow. The sibling repositories' CodeQL and Scorecard
workflows use a top-level `contents: read`, which is what the CodeQL and Scorecard actions read
the repository with before a job widens to `security-events: write`, and the E3 spec asks for that
shape. The test now parses the top-level block and accepts `{}` or a block whose every entry ends
in `: read`, refusing any `write`, and the new per-job guard closes the gap that relaxation would
otherwise open: no job may inherit the default silently. Net, the pair is stricter than the single
`contains("permissions: {}")` it replaces — that one said nothing at all about the jobs.

### The CodeQL-for-Rust decision: `build-mode: none`

Both matrix rows are `build-mode: none`, and no `cargo build` step exists in `codeql.yml`.

The evidence, in the order it was gathered:

- `src/languages/builtin.json` at tag v4.37.9 of `github/codeql-action` (read through
  `gh api repos/github/codeql-action/git/trees/v4.37.9?recursive=1` and the blob API) lists
  `rust` as a built-in language, so no experimental-features environment variable and no
  special-cased action version is needed.
- `pr-checks/checks/rust.yml` in the same tree — the action's own Rust integration check — calls
  `init` with `languages: rust` and **no** `build-mode` at all, and asserts a database is created.
  Its `versions:` list records `stable-v2.22.1` as the "first public preview version".
- GitHub's documentation states that default setup uses the `none` build mode for C/C++, C#, Java
  and Rust, and the changelog entry "CodeQL scanning Rust and C/C++ without builds is now
  generally available" (2025-10-14), together with "CodeQL 2.23.3 adds a new Rust query, Rust
  support…" (2025-10-23), puts buildless Rust analysis at generally available well before the
  bundle this action version ships.

So `none` is supported, is what GitHub's own default setup uses for Rust, and needs neither a
toolchain step nor a `--locked` build on the analysis runner. The spec's fallback — `manual` with
an explicit `cargo build --all-features --locked` — is not needed, and is in fact unreachable
here: `codeql_analyzes_the_languages_this_repository_actually_has` asserts the workflow does not
contain the substring `go`, and `cargo` contains it. Anyone who later moves the Rust row to
`manual` will have to reconcile those two assertions rather than discover the conflict on a red
run; the same substring rule is why `codeql.yml` sets no `category:` on the analyze step.

**Superseded by Fix round 1.** Recording that conflict rather than removing it was the wrong call:
the two tests were mutually unsatisfiable for the build mode the spec names as the fallback. The
substring rule is gone — the absent-language check now runs over the parsed matrix — so `manual`
with a `cargo build --all-features --locked` step is expressible today. `none` remains the choice,
for the reasons above; what changed is that it is a choice.

`autobuild` appears nowhere, as the guard requires.

## GREEN / test corrections

One correction, in `tests/ci_matrix.rs`.

`crons()` read a schedule with `line.trim().strip_prefix("cron:")`. A GitHub schedule is a YAML
sequence, so the key arrives as `- cron: "41 20 * * 3"`, whose trimmed form starts with `- `, not
with `cron:`. The helper therefore returned an empty list for every workflow written the ordinary
way — including both sibling workflows the spec points at as the house style — which made
`codeql_runs_weekly_on_a_slot_of_its_own_…` fail against a correct `codeql.yml` (`left: []`,
`right: ["41 20 * * 3"]`) and, worse, would have made every "this slot is not taken" assertion in
`scorecard_publishes_its_results_…` vacuously true had the length check not caught it first.

The fix strips an optional leading `- ` before looking for the key, so both spellings of the same
schedule are read. Nothing was relaxed: the helper now sees crons it previously could not see, and
the assertions over it are unchanged. The test's intent — one weekly slot, and not one a sibling
holds — is the intent it now actually enforces.

No other test was changed in this section. The substring rule that forbids `go` in `codeql.yml`
was left exactly as written here, and the workflow was authored to satisfy it — a decision the
review overturned; see *Fix round 1* below.

### Handover: what the orchestrator still has to do by API

Nothing below is done here, by design — this milestone authors the records; applying them is the
orchestrator's step.

1. **Create the repository** as `P4suta/ginary`, public, default branch `main`, and push. The
   badges, the advisory links and the Scorecard publication all name that slug already.
2. **Apply the rulesets**, in this order (the branch one first, so `main` is protected before any
   tag exists):
   - `gh api --method POST repos/P4suta/ginary/rulesets --input .github/rulesets/main.json`
   - `gh api --method POST repos/P4suta/ginary/rulesets --input .github/rulesets/release-tags.json`
   Applying `main.json` before the first CI run means `Required CI` shows as an expected check
   that has never reported; that is correct, and it resolves on the first run of `ci.yml`.
3. **Enable the security features** the workflows assume: private vulnerability reporting (the
   `security/advisories/new` URL in `SECURITY.md` and in the issue-template config 404s until it is
   on), the dependency graph (`dependency-review.yml` reads it), Dependabot alerts and security
   updates, and code scanning via the committed advanced setup — not default setup, which would
   fight `codeql.yml`.
4. **Create the labels** `dependabot.yml` and the issue forms apply, or the first Monday's pull
   requests arrive unlabelled: `type: dependencies`, `area: rust`, `area: ci`, `type: bug`,
   `type: feature`, `status: needs-reproduction`.
5. **Enable Discussions** — required, before the repository is made public.
   `.github/ISSUE_TEMPLATE/config.yml` offers a second contact link,
   `https://github.com/P4suta/ginary/discussions`, and GitHub renders a contact link whether or

## Fix round 1

A review of the staged tree returned eight findings: one high, three medium and four low. All
eight are addressed below. The two the review marked behavioural got a regression test first,
watched failing, as the house rule requires; the rest are corrections to tests and documents and
are recorded with the evidence that each guard now fails for the reason it claims.

### RED: the feature-request form was not YAML at all

The high finding and the medium one behind it are the same defect seen from two sides. Line 3 of
`.github/ISSUE_TEMPLATE/feature_request.yml` was a plain scalar carrying a colon-space:

```yaml
description: Propose a capability that fits what ginary is: one file, no runtime on the target machine.
```

A YAML plain scalar may not contain `": "`, so the document does not load. GitHub could not have
parsed the form, and it would never have appeared in the issue chooser. Nothing noticed:
`actionlint` does not look under `.github/ISSUE_TEMPLATE/`, and every assertion over the forms,
`dependabot.yml` and the workflows was a `str::contains` substring check — as happy with a file no
parser will accept as with a correct one. The rulesets had a real `serde_json::from_str` gate from
the start; the YAML records had nothing equivalent.

The regression test is `tests/regressions/e3_an_issue_form_was_not_valid_yaml.rs`. It walks every
`.yml`/`.yaml` file under `.github/` — the two forms and their config, `dependabot.yml`, all seven
workflows, any future composite action — and parses each one, and it reads the form's
`description:` back as a string. Written first and run against the tree as staged:

```text
running 2 tests
test e3_an_issue_form_was_not_valid_yaml::the_feature_request_description_is_a_scalar_yaml_can_read ... FAILED
test e3_an_issue_form_was_not_valid_yaml::every_github_record_parses_as_yaml ... FAILED

---- e3_an_issue_form_was_not_valid_yaml::the_feature_request_description_is_a_scalar_yaml_can_read ----
panicked at tests/common/repo.rs:84:33:
.github/ISSUE_TEMPLATE/feature_request.yml is not valid YAML: mapping values are not allowed in
this context at byte 125 line 3 column 59

---- e3_an_issue_form_was_not_valid_yaml::every_github_record_parses_as_yaml ----
panicked at tests/regressions/e3_an_issue_form_was_not_valid_yaml.rs:62:5:
GitHub loads each of these as YAML, and it cannot load these:
.github/ISSUE_TEMPLATE/feature_request.yml: mapping values are not allowed in this context at

```

The fix is one line — the description is quoted — and both tests are green. The parser is
`saphyr` 0.0.12, added as a **dev-dependency** (`default-features = false`, so the `encoding`
feature and `encoding_rs` stay out). It is not a dependency of the crate and cannot reach either
half of the binary; `cargo deny check licenses` is clean with it in the graph. The three helpers
it buys — `parse_yaml`, `yaml` and `yaml_files_under` — live in `tests/common/repo.rs` beside
`read_or_missing`, so there is one reader, not a sixth hand-rolled copy.

### The substring readers that let it through, replaced by the parser

The second behavioural finding was that nothing parsed the YAML records, so this class of failure
had no floor. Every hand-rolled line reader over a YAML record is gone:

| Was | Is now |
| --- | --- |
| `codeql_matrix()` splitting on `"- language:"` | `jobs.<id>.strategy.matrix.include`, read off the parsed document |
| `scalar()`, `labels()`, `dependabot_updates()` scanning lines | the parsed `updates:` sequence, including integer scalars like `open-pull-requests-limit` |
| `top_level_permissions()` reassembling a block as a string | the parsed `permissions:` mapping |
| `jobs()` slicing the file at two-space indentation | the parsed `jobs:` mapping |
| the three issue-form tests' `form.contains(…)` | `name`, `labels`, the `target` dropdown's own `options:`, and `validations.required` per field |
| `config.contains("blank_issues_enabled: false")` | the parsed boolean, and `contact_links[0].url` |
| ci.yml's fan-in name found by scanning forward | `jobs.required.name` |

Where prose is what matters — "does the form tell a reporter to strip secrets" — the assertion is
now over the flattened scalars of the parsed document rather than over the file's bytes, so a
sentence in a comment no longer satisfies it.

### The `go` substring trap (medium)

`codeql_analyzes_the_languages_this_repository_actually_has` forbade the substring `go` anywhere
in `codeql.yml`. `"cargo build --all-features --locked"` contains `go`, so the spec's own
documented fallback — a `manual` Rust row with that build step, which
`codeql_gives_every_language_an_explicit_build_mode_and_never_autobuilds` explicitly requires when
the row is `manual` — could never satisfy both tests at once. The two were mutually unsatisfiable
for the build mode the spec names, and the GREEN section above recorded the conflict instead of
removing it. Any innocuous prose (`category:`, `logo`, `going`) would have tripped it too, and
reported itself as "the CodeQL matrix analyses `go`".

The loop now runs over the parsed language list, and the list of languages this tree does not hold
grew to `c-cpp`, `csharp` and `swift`. Both halves were demonstrated:

```text
$ # temporarily: the Rust row set to `manual`, with a `cargo build --all-features --locked` step
$ cargo test --test ci_matrix codeql
test codeql_analyzes_the_languages_this_repository_actually_has ... ok
test codeql_gives_every_language_an_explicit_build_mode_and_never_autobuilds ... ok
test codeql_runs_weekly_on_a_slot_of_its_own_plus_push_pull_request_and_dispatch ... ok
test result: ok. 3 passed; 0 failed

$ # temporarily: a real `- language: go` row added to the matrix
$ cargo test --test ci_matrix codeql_analyzes
panicked at tests/ci_matrix.rs:351:5:
assertion `left == right` failed: CodeQL analyses exactly the two languages in this tree — the
Rust crate and the workflows — as `include:` rows, sorted here; it declares:
[("actions", "none"), ("go", "none"), ("rust", "none")]
  left: ["actions", "go", "rust"]
 right: ["actions", "rust"]
```

The workflow itself is unchanged: `build-mode: none` remains the right answer for both rows, for
the reasons in the CodeQL decision above. What changed is that the *other* answer is now
expressible, so a future move to `manual` is a decision rather than a wall.

### The per-job permissions guard accepted a comment (medium)

`every_job_of_every_workflow_declares_its_own_permissions` asked whether the job's text contained
`permissions:` anywhere — steps and comments included. That is the guard that was supposed to pay
for relaxing the top-level rule from a literal `permissions: {}` to "read-only scopes", and it did
not read the job's own block. It now looks up `permissions` as a key of the parsed job mapping and
requires the value to be a mapping. Demonstrated by replacing the CodeQL job's permissions block
with a comment that merely mentions the word — the shape the old guard accepted:

```text
$ # temporarily, in codeql.yml's `analyze` job:
$ #     # TODO: widen permissions: later
$ cargo test --test ci_matrix every_job_of_every_workflow
panicked at tests/ci_matrix.rs:819:5:
every job states the scopes it needs as a mapping of its own, so a widening is a line in the
diff; these do not:
.github/workflows/codeql.yml: job `analyze`
```

Its companion still refuses a writing default, and now prints the block it refused rather than a
`Debug` of the parse tree:

```text
$ # temporarily: top-level `permissions: contents: write` in codeql.yml
$ cargo test --test ci_matrix every_workflow_defaults
panicked at tests/ci_matrix.rs:795:9:
.github/workflows/codeql.yml defaults to `permissions: contents: write`, which grants more than
read; widen per job instead
```

`read-all` and `write-all` are scalars rather than mappings and are refused with the writes: a
scope this repository cannot name per job is a scope it does not want.
