**A — `actionlint` is required of every runner and installed on none.** The two known causes
were both known from `Coverage`; this is the first.

```text
thread 'e1_the_sha256sums_step_read_and_wrote_one_file::actionlint_accepts_every_workflow'
panicked at tests/common/tools.rs:63:17:
`actionlint` is not on PATH and GINARY_REQUIRE_TOOLCHAIN=1 forbids skipping
```

The gate is wrong in kind, not in strength. `GINARY_REQUIRE_TOOLCHAIN` is the claim that the
*toolchain an artifact is built with* is installed — `gleam`, `erl`, `strip` — and `actionlint`
is a lint that has nothing to do with packaging a runtime. The narrow gate the brief prefers is
the one taken: a third variable, `GINARY_REQUIRE_ACTIONLINT`, set by exactly one job, which
installs the tool and **runs the test**. A check moved out of three jobs and into none would be a
check deleted, so that last clause is asserted rather than assumed.

The rule scanned for *this* machine's `$HOME`, which on a runner is `/home/runner` and appears in
every pasted CI transcript. It was therefore unfalsifiable on every machine but one — a
developer's path hard-coded by somebody else passed everywhere except on their own desk, which is
exactly the defect E5 set out to prevent — and on a runner it policed prose.

The replacement is machine-independent: `/home/<name>` and `/Users/<name>` matched whoever runs
the scan, over `src/`, `tests/`, `scripts/` and `.github/` only, never `docs/`; a comment line
inside a scanned file is the same prose as a milestone log and is not policed either; and the
fictional accounts this suite's own unit tests spell — `/home/u`, `/Users/ada`, which appear at
twenty sites — are not people. The reasoning is in `tests/common/homepath.rs`.

It stays non-vacuous in two ways at once. The scanner is calibrated inside the test that uses it,
on a planted buffer assembled at run time (a file spelling `/home/<a person>/` in one piece would
be an offender itself), and the new rule finds exactly one real offender on today's tree:
`tests/regressions/e6_the_toolchain_flag_required_a_cross_stub_nobody_built.rs:64`, which puts
`/home/runner/work/ginary/ginary/target/stubs` in *code* — a synthetic input to a pure function
that could be any absolute directory. The transcript in that file's documentation is prose and
stays exactly as it is. The two E6 sites are therefore split by the new rule, one kept and one
fixed, which is the distinction the old rule could not draw.

Pinned by `tests/regressions/e7_the_home_directory_scan_only_worked_on_one_machine.rs`.

The verifier is right. `setup-beam`'s emulator on `ubuntu-24.04` is linked against `libz.so.1`,
which is not part of a glibc system's own runtime, and reporting it is the whole of the

weakening the gate — it would promise a stranger's machine has zlib — so the expectation is
computed instead from the OTP installation, which is a different file from the artifact the
report was read out of, leaving the assertion two independent sides.

Five of the seven (**D**) are tests that asked the host what platform it was: three passed
`Target::host()` to `runtime_bins` and compared the answer against the unix spelling of a program
name, and three compared a whole launcher message against glibc's `strerror` text. `runtime_bins`
itself is correct — it appends the *target's* suffix, and
`a_windows_build_asks_for_the_programs_by_the_names_the_tree_spells` already pins the `.exe` half
explicitly — and `LauncherError` owns the prefix, the path and the numbered code but not the
words after the colon, which every C library renders in its own. Both are scanned rather than
compiled, the way E6 scanned for `std::os::unix`.

The remaining two (**E**) are one genuine defect in shipped code, and the milestone's most
valuable Windows find. `cache::resolve` implements the XDG base directory specification, which
requires a relative `XDG_CACHE_HOME` to be ignored and defines absolute as a leading `/`. The
check was `Path::new(value).is_absolute()`, which answers for the platform the code was
*compiled* for: on Windows `/xdg` wants a drive letter, so the branch is skipped silently, with
no error and no trace, and the resolver falls through to `HOME`. `cache_dir::resolve` is a
projection of the same function and failed the same way one layer up. The fix is a pure function,
`cache::xdg_base_is_absolute`, that answers the same on every host — which is what makes it
pinnable from Linux.

Both pinned by `tests/regressions/e7_the_unit_tests_asked_the_host_what_platform_it_was.rs` and
`tests/regressions/e7_the_xdg_rule_used_the_hosts_idea_of_an_absolute_path.rs`.

**F — macOS, both arches, one cause: there is no Mach-O emulator reader.**

```text
error: cannot resolve the runtime to bundle
  caused by: the emulator at /Users/runner/work/_temp/.setup-beam/otp/erts-17.0.5/bin/beam.smp
  is not an ELF binary (not an ELF file); a runtime for another target has to be a real
  cross-built tree, not a stand-in
```

E6's removal of the phantom `--erts` flag worked: both jobs got past argument parsing and into
`ginary build` for the first time, and both stopped at the trust anchor.
`erts_source::resolve_with` chooses its reader from the *layout* of `erts-<vsn>/bin` — a Windows
tree spells its emulator `beam.smp.dll` and keeps an `erl.ini` beside it, everything else gets
the ELF reader. That is a complete dichotomy over the two platforms C2 and D2 built for and
wrong the moment a third exists: a macOS tree has the unix layout exactly, and the only
difference a build can observe is that its `beam.smp` is a Mach-O. D3 could not see it — there
was no Mac, and `macho.rs` was proved against fixtures rather than against a toolchain-produced
runtime.

This is the one cause of the six that is reproducible here, and it now is: `FakeOtp::macos()`
writes a unix tree whose emulator is a real thin Mach-O, and the local failure is the runner's
verbatim — `NotAnElfRuntime { reason: "not an ELF file" }`. Whether `codesign --verify --strict`
also has something to say is a question for the next run; it is downstream of a build that has
never completed.

### 17 — E: the XDG specification's own leading slash

### 18 — F: the emulator's own magic chooses the reader

```text
error: cannot resolve the runtime to bundle
  caused by: the emulator at .../erts-17.0.5/bin/beam.smp is not an ELF binary
  (not an ELF file); a runtime for another target has to be a real cross-built tree
```

`emulator_format` classifies four bytes — ELF, Mach-O (thin or fat), PE, or nothing — and
`resolve_with` diverts **only** a Mach-O to a new `resolve_macos`. That "only" is the whole of the
compatibility argument: a tree `assemble::is_windows_erts_bin` recognises still goes to the PE
arm, so assembly and this module cannot disagree about what a tree is; and everything that is not
a Mach-O keeps the ELF reader it has always had, including a file that is no object at all, so the
injected-reader seam every existing test uses is untouched and `inspect` remains the one place
that says what it could not read.

`resolve_macos` is the Windows arm's shape and the same trust anchor: the machine comes off the
emulator's own header, so an x86-64 runtime in an aarch64 build is a `TargetMismatch` here rather
than a loader error on somebody else's machine. Three facts are not read because a macOS runtime
cannot vary in them — one system C library, so the libc is `Libc::None` and there is no version
floor; the emulator resolves at load time, so the linkage is `Dynamic` and NIFs load. Three typed
errors are new, each naming what the developer has to do: `NotAMachoRuntime` (a file that begins
like one and is not), `UniversalRuntime` (a fat emulator, which is more than one runtime and none
of them the one to bundle — the message names `lipo -thin`), and `UnknownMacosRuntimeTarget` (a
`cputype` this crate has no target for). Three tests in `tests/erts_source.rs` cover them, on a
`FakeOtp::macos()` tree.

**ADR 0016 is not contradicted and is not updated.** It is about where a macOS *artifact* carries
its payload and how that artifact is signed; this defect is about reading the *runtime* that goes
into one, which is upstream of every claim the ADR makes. What has to be said instead is that ADR
0016 has still never been exercised on a Mac: both macOS jobs stopped at the runtime resolver, so
section injection, `payload::locate` over a toolchain-produced Mach-O and `codesign --verify
--strict` have not run yet. They are what the next run reaches, and D3's gap stays open until it
does.

**RED.** The planted buffer in `no_tracked_code_file_names_a_persons_home_directory` gained the
attribute line and the site it should report:

```text
thread 'e7_the_home_directory_scan_only_worked_on_one_machine::no_tracked_code_file_names_a_persons_home_directory'
panicked at tests/regressions/e7_the_home_directory_scan_only_worked_on_one_machine.rs:103:5:
assertion `left == right` failed: … `#` opens a Rust attribute, not a comment, so an attribute
naming one machine is code like any other line
  left: [HomePathSite { line: 2, account: "home/jbloggs" }, HomePathSite { line: 6, account: "Users/jbloggs" }]
 right: [HomePathSite { line: 2, account: "home/jbloggs" }, HomePathSite { line: 3, account: "home/jbloggs" }, HomePathSite { line: 6, account: "Users/jbloggs" }]
```

**The fix.** `homepath::Syntax`, chosen from the file's name by `Syntax::of`: `Rust` (`//` opens a
comment, `#` does not), `Hash` for `.yml`, `.yaml`, `.toml`, `.sh` and `.gitignore`, and `Opaque`
for everything else — a `.beam`, a `.snap`, a fixture — where no line is prose. Guessing wrong
towards `Opaque` reports a path that turns out to be in a comment; guessing wrong the other way
hides one that is not, which is the defect. `home_path_sites` takes the syntax, and the tracked
scan passes `Syntax::of(relative)`.

The calibration is now two buffers rather than one, because one scanner reading the same bytes
two ways is the claim being made: the `#` line is prose under `Syntax::Hash` and code under
`Syntax::Rust`, and `Syntax::of` is asserted over one file of each kind. The whole tracked tree
still passes under the stricter reading, so nothing was exempted to make it.
