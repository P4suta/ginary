### 1 — the `kind` column called a stated `e_type` unknown (low)

C4 made `doctor`'s `kind` cell and the verdict cells beside it two halves of one answer: both are
reached from `native::NativeKind`, so a position-independent program reads `executable` in each
rather than `shared object` in one and a static-runtime verdict in the next. The translation was
`native::kind_of_elf`, and it named two `e_type` values and folded every other one into
`NativeKind::Unknown`:

```rust
crate::elf::ElfKind::SharedObject if is_pie => NativeKind::Executable,
crate::elf::ElfKind::SharedObject => NativeKind::SharedObject,
crate::elf::ElfKind::Executable => NativeKind::Executable,
_ => NativeKind::Unknown,
```

`Unknown` already means something precise in this table — a file whose magic says it is an object
and which will not parse, listed with the sentence saying why nobody could read it — and an
`ET_REL` a build system left under `priv` parses perfectly well. A reader who saw `unknown` over
one went looking for a corruption that was not there.

The field's own documentation made it worse rather than better. It justified dropping the raw
number by naming where the number could be had:

```rust
/// cells beside it have to be two halves of one answer. `ginary inspect`
/// is where an ELF's own `e_type` is reported.
```

`ginary inspect` reports the manifest, the payload geometry and the digest of an artifact. It
reads no ELF header at all. The command that does is `ginary elf deps`, whose `--json` output
carries `kind` straight off the header, and `docs/dev/debugging.md` documents it as such. So the
comment pointed at a command that could not answer the question it was excusing.

The review offered either fix and preferred the honest column, which is what was done — the
pointer was corrected as well, since a reader of that field wants to know where the untranslated
value lives.

`NativeKind` gains three variants. `Relocatable` and `Core` are the two shapes the `object` crate
also names, so the PE and Mach-O arm of `describe_object` maps them too rather than leaving one
format more honest than another. `ElfType(u16)` carries a number no standard assigns, because the
number is the whole of what is known about such a file:

```rust
crate::elf::ElfKind::Relocatable => NativeKind::Relocatable,
crate::elf::ElfKind::Core => NativeKind::Core,
// Not [`NativeKind::Unknown`]: the header said what it was, and a
// column that prints `unknown` over a number the file states is a
// report that knows more than it says.
crate::elf::ElfKind::Other(e_type) => NativeKind::ElfType(e_type),
```

`NativeKind::as_str` could not survive the third variant — `e_type 65024` is not a `&'static str`
— so it became a `Display` impl, and `doctor`'s renderer calls `to_string()` where it called
`as_str().to_owned()`. The words the two printing kinds render as are unchanged, so
`tests/snapshots/doctor__doctor_project_native_table.snap` needed no edit, which is the evidence
that nothing a real project's table says has moved.

Nothing downstream decides anything differently. `reconcile`'s static-runtime rule and the
strip-side filter both test `kind == NativeKind::SharedObject`, so a row that changed from
`Unknown` to `Relocatable` changes no verdict; the ELF arm still attaches its
`ObjectDescription::unreadable` sentence to an `e_type` that is neither a program nor a shared
object, so such a file is still reported as one nothing will load.

The regression test is `tests/regressions/d2_the_kind_column_called_a_stated_e_type_unknown.rs`.
It plants an `ET_REL`, an `ET_CORE` and an `ET_LOOS` (`0xfe00`) under a project's shipment and
asserts three things: the `NativeKind` values on the report, the rendered cells (`relocatable`,
`core`, `e_type 65024`, and no `unknown` on any of the three rows), and — the other half, without
which the fix could be "nothing is unknown any more" — that a truncated ELF still describes as
`NativeKind::Unknown` with a reason. Reverting `kind_of_elf` to `_ => NativeKind::Unknown` fails
the first two and leaves the third passing, which is the RED that was watched before the fix went
in.

## RED

The tests, the fixtures and the honest stubs that make them fail on an assertion rather than on a
compile error. No product logic was written: every new function returns an explicit empty value —
an empty path, an empty list, `None`, a zero share mode — carrying a `// RED: replaced in GREEN`
comment that says so, so the crate builds in both flavors and each new test fails on what it
claims rather than on a name that is not there yet.

is a `cross build`.

`windows-sys` is deliberately **not** in `Cargo.toml` yet. Nothing in the RED tree calls a Win32

### Fixtures and helpers

`FakeOtp::windows()` is the one new builder, and it writes `erts-<vsn>/bin/{erl.exe,
beam.smp.dll, erl.ini}` plus whatever `extra_erts_bins` named, as plain files. Plain files rather
than shell stubs because nothing here can execute a PE and every claim a Windows tree is read for
is about *which names are in the directory*. Everything else about the root — the boot file,
`lib`, `releases` — is what the unix flavor writes, which is what makes the launch spec the only
thing that differs. The builder still has no API for an invalid tree: the two refusal tests build
a whole one and `remove_file` the program they are about.

`tests/snapshots/windows__windows_cache_provenance.snap` is written by hand rather than accepted
from a run, because a snapshot is a contract: it holds the provenance table GREEN has to produce,
and the RED run fails against it. It deliberately holds no *paths*. The roots are built with
`Path::join`, so on this machine `%LOCALAPPDATA%\ginary` comes back as
`C:\Users\ada\AppData\Local/ginary`; a snapshot of that would pin the machine that ran the test
rather than the rule, and would fail under wine for a reason that is not a defect. The path
assertions are ordinary `assert_eq!`s against `Path::join`, which agree on either platform.

### What has no RED test, and why

Three things in the D2 scope cannot be stated as a failing test on this machine, and saying so
here is cheaper than discovering it in review.

**The cfg-split itself.** "The crate compiles for `x86_64-pc-windows-gnu`" is a compile-time
claim, and a test that only fails to compile is not RED. Its evidence is the `cross build` GREEN
runs and records — both flavors, both recorded with their sizes — and the `build:windows` task the
scaffolding test does pin. The audit list is unchanged from the spec: `selfexe`, `cache`,
`cache_lock`, `launch`, `launcher`, `process`, `diag`, `payload`'s mode bits, and the
`std::os::unix::ffi` byte access `launch::split_flags` and `heart_command` are written on, which
has a safe wide-string counterpart on Windows (`OsStrExt::encode_wide` and `OsStringExt::from_wide`)
and therefore needs no `unsafe` and no change to `#![forbid(unsafe_code)]`.

**`src/launch_windows.rs`.** Not compiled here at all; see above.

**Anything that runs a Windows binary.** `cross test --target x86_64-pc-windows-gnu` under the
image's wine is an *attempt* GREEN makes and records honestly, and a full `erl.exe` artifact
end-to-end is explicitly out of scope for D2 — it is GitHub Actions territory, and the README and
this log both have to say so rather than implying a coverage that does not exist.

One piece of housekeeping is deliberately left to GREEN: `docs/dev/testing.md`'s "what exists now"
table has no row for `tests/windows.rs` or `tests/windows_build.rs` yet. No test asserts that row,
and adding it while the two targets are red would be recording coverage that does not exist.

### The rules, and where each one lives

| item | file | what it answers |
|---|---|---|
| `cache::resolve_windows` | `src/cache.rs` | `GINARY_CACHE_DIR` verbatim, then `%LOCALAPPDATA%\ginary`, then the fallback; an empty value counts as unset, as it does on unix |
| `cache::windows_fallback_root` | `src/cache.rs` | `%TEMP%`, then `%TMP%`, then `C:\Windows\Temp`, with `ginary-<user>` joined onto it |
| `cache::current_user` | `src/cache.rs` | `%USERNAME%`, or `unknown` when it is unset, empty, `.`/`..`, or holds a separator, a colon or a control character |
| `winpath::long_path_str` | `src/winpath.rs` | the prefix rule on text: slashes rewritten first, `\\?\` idempotent, UNC to `\\?\UNC\`, drive-absolute prefixed, everything else returned as it came |
| `winpath::long_path` | `src/winpath.rs` | the same on a `Path`, owning on Windows and borrowing everywhere else — including on Windows for a path the rule does not touch |
| `cache_lock::windows_share_mode` | `src/cache_lock.rs` | `FILE_SHARE_READ` for a runtime's lock, `0` for a prune's |
| `launch::windows_exit_code` | `src/launch.rs` | the child's code, `u8::MAX` where it does not fit, `NO_EXIT_CODE` for none |
| `Target::launch_program` | `src/target.rs` | `erl.exe` on Windows, `erlexec` elsewhere, off the two constants `bundle::LAUNCH_PROGRAM` and `assemble::WINDOWS_LAUNCH_BINARY` now alias |
| `assemble::windows_required_bins` | `src/assemble.rs` | the directory read back: `erl.exe` and every `*.dll` beside it, sorted, with the two refusals by name |
| `assemble::remove_windows_erl_ini` | `src/assemble.rs` | the size of the `erl.ini` it deleted, or `None` |
| `bundle::check_windows_erts` | `src/bundle.rs` | `dir:` accepted, every other source refused with the sentence naming where a Windows runtime comes from |

None of the eleven is an export nothing calls. `resolve_windows` and `current_user` are what
`cache::resolve_here` dispatches to on Windows, and `prepare_windows` is `prepare_here`'s other
half; `long_path` is applied to the extraction destination in `ensure_extracted`, which is the
one path every `.beam` in a payload is written under; `windows_share_mode` is what
`open_windows_shared` and `open_windows_exclusive` pass to `OpenOptionsExt::share_mode`;
`windows_exit_code` is `launch_windows::run`'s last line; `launch_program` is what
`bundle::manifest_for` writes into `LaunchSpec::program`; `check_windows_erts` runs in
`build_targets` immediately after `erts_spec_for` and before the runtime is fetched; and
`windows_required_bins` and `remove_windows_erl_ini` are both called from `assemble::build`.

The last pair needed a decision the spec left open: how `stage` knows a tree is a Windows one.
It is **read off the tree**, not off the requested target — `is_windows_erts_bin` asks whether
`erl.exe` is in the runtime's `bin`. That is the honest direction of the dependency. The
required-file list is a property of the directory rather than of what the user asked for, and
taking it from the tree means a unix runtime staged for a Windows target is refused by name for
a missing `erl.exe` rather than staged as if the request had been right. It also needed no new
field on `StageOptions`, which nine call sites construct by literal.

`remove_windows_erl_ini` is belt and braces, and says so in its call site's comment: the probe
never contributes `erl.ini` — it is neither the launch program nor a DLL — but
`--extra-bin erl.ini` would put one back, and an `erl.ini` in the artifact points `erl.exe` at
the build machine's `Rootdir`. Its size goes into `junk_removed` whether or not junk removal was
asked for, because it is not junk: it is a file that would have broken the artifact.

### The cfg split

`cargo check --target x86_64-pc-windows-gnu` does not work on this host at all — `zstd-sys` is
C and needs the mingw toolchain that lives only in the cross image — so the whole split was
iterated with `cross check`. Forty-three errors at the start, in nine files.

| file | what Windows does not have | what it does instead |
|---|---|---|
| `selfexe.rs` | `/proc/self/exe` | `current_exe` is the whole answer; the weaker guarantee costs nothing because Windows holds an image section on a running executable |
| `cache.rs` | `getuid`, `syncfs`, mode bits, a directory handle `File::open` can produce, `Errno` | `current_user`, a per-file `fsync` and no directory barrier, `chmod_tree` answering zero, and the four `ERROR_*` numbers named as constants |
| `cache_lock.rs` | `flock`, `FD_CLOEXEC` | `OpenOptionsExt::share_mode` on the open handle, taken and held by the launcher itself |
| `launch.rs` | `OsStrExt::as_bytes`, the execute bit, `ExitStatusExt::signal`, `CommandExt::exec` | a `Unit` type alias — `u8` on unix, `u16` on Windows — under one implementation of the three rules that read code units; existence as the whole of `check_program`; `signal_of` answering `None`; and `exec` compiled only on unix |
| `launcher.rs` | `execve` | `start` is `cfg`-split: `launch::exec` on unix, `launch_windows::run` on Windows, with the lock dropped after the wait rather than before the exec |
| `trailer.rs` | `FileExt::read_exact_at` | `seek_read` in a loop, because the Windows call may answer short |
| `payload.rs`, `manifest.rs`, `assemble.rs` | mode bits | `set_mode` doing nothing, and `mode_of` recording what the `tar` crate itself writes on this platform — 0o755 for a directory, 0o644 otherwise — so the index and the header agree and `verify` has nothing to report |
| `doctor.rs` | the probe's mode | `PROBE_MODE` is `cfg(unix)`; the probe still writes a file and tries to start it |

Two things the split is *not*. It is not a second implementation of anything: `launch::plan`,
`launch::supervise`, `cache::ensure_extracted`, the sweep, the prune and the whole payload
reader are one body of code on both platforms. And it needed no `unsafe` outside
`launch_windows::win32`: `encode_wide`/`from_wide` are safe, and so is `share_mode`.

`rustix` moved to `[target.'cfg(unix)'.dependencies]`, where it belongs — `getuid`, `flock` and
`syncfs` are the three calls it is here for and none exists on Windows.

### `launch_windows.rs`, and the one exception to `forbid(unsafe_code)`

`run` records the plan through `launch::record` — the same function, so the trace has one shape
— installs the console control handler, creates the job object, spawns, assigns, waits, and
exits with `windows_exit_code(status.code())`. The lock is not its business: `launcher::start`
holds it across the call and drops it after.

`SetConsoleCtrlHandler`, `CreateJobObjectW` with `SetInformationJobObject`, and
`AssignProcessToJobObject` are `kernel32` entry points with no safe wrapper anywhere, and
`#![forbid(unsafe_code)]` cannot be lifted for one module. So the crate attribute became
`#![deny(unsafe_code)]` and `launch_windows::win32` carries the only `#[allow(unsafe_code)]` in
the tree: one module, four `unsafe` blocks, each with a `SAFETY` note, every function total and
every failure a `false` or a `None`. `deny` keeps every other file and every other target
exactly as strict as `forbid` was: there is exactly one such attribute in `src/`, on
`launch_windows.rs`'s `mod win32`, and the compiler refuses any `unsafe` outside it.

**This is a deliberate change to a `CLAUDE.md` prohibition and it is flagged as such.** The
alternative was a Windows launcher that orphans its runtime when it is killed and dies under
Ctrl-C, which is what the plan's D3 table exists to prevent; the two facilities are named in the
plan and in the spec, and neither can be written without those calls.
`docs/adr/0015-windows-launcher-stays-resident.md` carries the argument in full. A reviewer who
disagrees can revert the attribute and delete `win32`; nothing else in the crate depends on it.

### The two that cannot fail here

Findings 2 and 6 are Windows-only mechanisms — `CreateFile`'s share modes and the `MAX_PATH`
normalisation — and this machine has neither. Their regression tests are `#![cfg(windows)]`, so
here they compile to nothing and run nowhere, which `cargo test` reports as the empty module it
is. They do not compile for `x86_64-pc-windows-gnu` either, and neither does any other ginary
test target: `tests/common` is unix-only. An earlier draft of this paragraph claimed they did;
see "Finding 3: what the `cfg(windows)` tests actually get" under Fix round 2. What each file
claims is written into its own head rather than left for a reader to discover, and both claims
are on the Actions list below:

- two launchers of one entry both take the shared lock, and a prune is refused while either
  holds it;
- everything one extraction writes hangs off a `\\?\` directory.

Neither file is dead text. Both were type-checked on this machine by lifting their `cfg` for one
compile — `cargo test --test regressions --no-run`, which builds them against the unix halves of
the same names — and put back. What that does not check is the Windows *behaviour*, which is the
point of listing them.

Finding 6 is also a decision, not only a fix. The prefix goes on once, at
`CacheDirs::extraction_dir`, and every path derived from it — the temporary tree, the files the
unpacker creates, the per-file flush that reopens each of them, both ends of the rename — is
verbatim through `Path::join` rather than through a second call somebody has to remember.

**The second half of that decision was wrong and is reversed in Fix round 2.** This round had
`ensure_extracted` *answer* with the ordinary spelling of the same directory, on the argument
that the value becomes `ROOTDIR` and `BINDIR` in an argument vector handed to `erl.exe` and that
a `\\?\` path is a shape that program takes apart rather than one it merely opens. All of that
is true about what `erl.exe` is handed, and none of it is true about the cache-hit check, the
`.lock` open, the manifest probe and `preflight`, which are ginary's own opens and took the same
value. The limit moved one step later instead of going away. See "Finding 2: one spelling for
ginary, one for `erl.exe`" below.

### Decisions worth naming

**`inet_gethost.exe` is required, not optional.** The unix list treats `inet_gethost` as
mandatory because a runtime without it resolves no host name, and a Windows ERTS tree ships the
same port program under that name. It is now one of `assemble::WINDOWS_REQUIRED_BINS`, so a tree
that does not hold it is refused by name at build time rather than shipping an artifact that
fails the first time an application opens a socket. It carries the same risk `beam.smp.dll`
already carried and is recorded with it in the open question below: the names come from the
documentation, not from a zip anybody here has read.

**The prune's share mode gained `FILE_SHARE_DELETE` rather than losing the lock.** Sharing
deletion says nothing about read or write access, so a runtime's shared handle still refuses a
prune and two runtimes still hold one entry together — `tests/windows.rs` asserts both halves
deliberately, with the reason in the message. The alternative, dropping the lock before the
rename, reopens exactly the window the lock exists to close.

**`--extra-bin erl.ini` is allowed and accounted for, not refused.** The file is copied, deleted
and reported in `junk_removed` with the relative path every other entry there carries, and it is
out of the staged set before the excluded list is computed, so no report calls it staged. A
refusal by name was the other option; it would have been an error about a file the build was
going to delete anyway.

### Finding 1: how a Windows tree is read now

Two splits, one flavour test. `assemble::is_windows_erts_bin` — "does `erts-<vsn>/bin` hold
`erl.exe`?" — was already the rule assembly used to choose between the unix and the Windows
required-file lists. It is public now, and it is the *only* place the question is asked:

- `otp::inspect_root` measures a tree it recognises against `assemble::WINDOWS_REQUIRED_BINS`
  (`erl.exe`, `beam.smp.dll`, `inet_gethost.exe`) instead of `REQUIRED_ERTS_BINARIES`, and asks
  for no execute bit. Not because the check is weaker there: a Windows filesystem has no mode
  word, and a zip unpacked on a Linux build machine carries whatever the unzipper chose, which
  is a fact about the unzipper. Everything else about the root — `bin/no_dot_erlang.boot`, one
  `kernel`, one `stdlib`, the release floor — is unchanged, because everything else about a
  Windows runtime *is* the same.
- `erts_source::resolve_with` hands a tree it recognises to `resolve_windows`, which reads
  `erts-<vsn>/bin/beam.smp.dll` — the emulator `erl.exe` loads, the Windows counterpart of the
  `beam.smp` the unix arm reads — and takes the machine off its PE header, straight from
  `object` for the reason `src/stub.rs` already gives: a PE names no interpreter and the machine
  field is the whole question.

The trust anchor is unmoved. The target still comes off the emulator's own header and never off
the spelling that named the tree, so a Windows tree in a Linux build and an aarch64 tree in an
x86-64 build are both `ErtsError::TargetMismatch` at build time. Three facts are *not* read,
because a Windows runtime cannot vary in them: it is a set of DLLs `erl.exe` loads, so the
linkage is `Dynamic` and NIFs load, and Windows has one system C runtime, so the libc is `None`
and there is no version floor to record. Two error variants are new — `NotAPeRuntime` for a file
that is not a PE at all, and `UnknownWindowsRuntimeTarget` for a PE for a machine ginary has no
target for — and both name the file that was read.

`FakeOtp::windows()` changed with them. Every `.exe` and `.dll` it writes is now a real, if
minimal, PE image: a DOS header, a COFF header naming the machine, and a PE32+ optional header
of the size that header declares. `erl.ini` stays text, which is what it is. `FakeOtp::pe_machine`
sets the machine, so the aarch64-runtime-in-an-x86-64-build test changes that one number and
nothing else. This is a fixture that got *more* honest: the tree it writes is now refused and
accepted for the same reasons a real one would be.

### Finding 2: one spelling for ginary, one for `erl.exe`

The rule is one sentence, and it is in `src/winpath.rs`: **ginary opens the verbatim spelling
and hands `erl.exe` the ordinary one.**

`CacheDirs::extraction_dir` is still the one place the prefix goes *on*, and
`ensure_extracted` now answers with it — `writing.join(&key)`, the same value both ends of the
rename use — so the cache-hit check, `cache_lock`'s `.lock`, the manifest probe and
`launch::preflight` all open the directory the extraction created. `launch::plan` is the one
place the prefix comes *off*: `LaunchPlan::program` keeps it, because this process spawns that
file itself, and `ROOTDIR`, `BINDIR`, `HOME` and every path in the argument vector are put back
into the ordinary spelling with `winpath::plain_path`. `launcher::dispatch` walks the prune over
`extraction_dir` too, since the prune renames and removes directories rather than handing them
to anyone.

That corrects a paragraph in "The two that cannot fail here" above, which argued the opposite —
that answering with the ordinary spelling traded a length limit ginary controls for a string
another program has to understand. The trade was real and the conclusion was wrong: the entry
does not have to be *one* spelling, and making it one moved the `MAX_PATH` limit from the
unpacker to the very next line. `plan` is the boundary, and it is the only boundary.

The asymmetry between the two helpers is deliberate and documented. `long_path` *adds* a prefix
and its rule fires on any drive-absolute spelling — including a relative unix path that happens
to be called `C:/x` — so it stays compiled out on unix. `plain_path` *removes* one and fires only
on a path whose first four characters are `\\?\`, which no unix path has, so it is one code path
on every platform and is unit-tested here. `tests/windows.rs` covers both rules and that they
are each other's inverse.

One limit is **not** removed and is stated rather than implied: what `erl.exe` is handed is the
ordinary spelling, so an entry longer than `MAX_PATH` still cannot be *launched* even though it
now extracts, is found, is locked and passes preflight. That limit belongs to `erl.exe`, not to
ginary, and it is on the Actions list.

type-checked **on Linux** by lifting their `cfg` for one compile and putting it back. That
catches a name that does not exist and a signature that does not match; it does not catch
