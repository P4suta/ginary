### 4 — macOS: a validly signed image that jumps into its own load commands

Jobs `100551483194` (macos-14 / aarch64,
<https://github.com/P4suta/ginary/actions/runs/33724862229/job/100551483194>)
and `100551483005` (macos-15-intel / x86_64,
<https://github.com/P4suta/ginary/actions/runs/33724862229/job/100551483005>).
Both reach a *valid* signature and then segfault on exec:

```text
CodeDirectory v=20400 size=69246 flags=0x20002(adhoc,linker-signed) hashes=2161+0 location=embedded
Executable Segment base=0  limit=5029888  flags=0x1
CDHash=416c03e5…  Signature=adhoc
<artifact>: valid on disk
<artifact>: satisfies its Designated Requirement
line 22: 11114 Segmentation fault: 11  "$artifact" 0 hello world
##[error]Process completed with exit code 139
```

**Diagnosis, reproduced on Linux against the real fixture.** `inject_and_sign`
inserts the `__GINARY,__payload` segment where `__LINKEDIT` began and shifts
every following byte of file *content* forward by a whole page
(`file_shift = 0x4000`), growing `__TEXT`'s `filesize`/`vmsize` and pushing each
following segment's `fileoff`/`vmaddr` along with it. It shifts every
file-offset field the `symtab`/`dysymtab`/`dyld_info`/`linkedit_data` commands
carry — but it does **not** shift `LC_MAIN`'s `entryoff`. So the entry point
still names the file offset the entry code used to sit at, which now holds
load-command bytes. A dump of the real fixture through `inject_and_sign` shows
it exactly: the stub's entry is at file offset `0x6c0`, whose first bytes are
arm64 code (`3f 23 03 d5 …`, a `pacibsp` prologue); after injection `entryoff`
is still `0x6c0`, but the injected file's load commands now run to `0x730`, so
byte `0x6c0` is the middle of an `LC_LOAD_DYLIB` name (`2e 64 79 6c 69 62 …`,
`.dylib`). The kernel jumps there and the process faults — a later, different
failure from the pre-E8 `Killed: 9`, and one `codesign --verify` cannot see
because the signature covers those bytes faithfully; they are simply not code.

The `codesign --display` line names a second, separate defect the plan flagged:
`flags=0x20002(adhoc,linker-signed)`. `build_ad_hoc_signature` writes
`CS_ADHOC | CS_LINKER_SIGNED`. ginary rewrote and re-signed this binary; it did
not come out of a linker, so `CS_LINKER_SIGNED` (`0x20000`) asserts a provenance
that is no longer true. Only `CS_ADHOC` may stand.

**The two tests** (`tests/sign_macos.rs`), both reading the output of the real
`inject_and_sign` over the committed `tests/fixtures/macho/` stub:

| test | claim | fails today because |
|---|---|---|
| `an_injected_artifact_runs_the_stubs_own_entry_instructions` | the bytes at the finished artifact's mapped entry equal the stub's own entry instructions | the entry lands in the load commands: `left` is `.dylib` name bytes, `right` is the `pacibsp` prologue |
| `an_injected_artifact_does_not_claim_to_be_linker_signed` | the `CodeDirectory` `flags` carry `CS_ADHOC` and not `CS_LINKER_SIGNED` | `flags & CS_LINKER_SIGNED` is `0x20000`, not `0` (whole word `0x20002`) |

The entry-point invariant is written against the *bytes at the mapped entry*,
not against the `entryoff` field, so it holds whichever way GREEN keeps them
there: shifting `entryoff` by `file_shift` to follow the moved `__TEXT`, or
adopting the append-after-`__LINKEDIT` layout the plan describes (nothing moves,
`entryoff` stays, `__LINKEDIT` grows to cover the payload and signature). GREEN
owns choosing the fix and, if it changes the layout ADR
[0016](../../adr/0016-macho-section-payload-and-adhoc-signing.md) records,
rewriting that ADR to what two real Macs proved.

New test helper: `tests/common/macho.rs` gains `entry_point(bytes, take)`, a
by-hand reader of `LC_MAIN` + `__TEXT` that returns the file offset the entry
resolves to and the bytes there. Segment, signature and `CodeDirectory` reading
is `tests/common/codesign.rs` already, which gains one constant,
`CS_LINKER_SIGNED`.

### 8 — macOS: grow `__LINKEDIT`, do not carve a section

**Diagnosis, carried to its root.** E8 reached a *valid* signature over an image
that segfaults on exec (exit 139), and the RED phase pinned the immediate cause:
`inject_and_sign` shifted every byte of content forward a page to make room for
the new `__GINARY,__payload` section's load command, and never moved `LC_MAIN`'s
`entryoff`, so the kernel jumped into the load commands. GREEN found that
shifting `entryoff` to follow the code is **not** a sufficient fix, and that no
version of the section approach can be: a new section needs a new
`LC_SEGMENT_64`, the linker leaves only forty spare bytes in the load-command
area (a segment-with-section command is a hundred and fifty-two), so the command
cannot be added without sliding the code — and the slide invalidates not only
the entry point but **every `LC_DYLD_CHAINED_FIXUPS` rebase target**, which is
encoded as an offset from the image base. `otool -l` on the committed fixture
confirms the geometry: `__text` begins at file offset `0x6c0`, only forty bytes
past the load commands' end at `0x698`. A validly signed image whose rebases all
point a page short of their data is exactly "verifies and segfaults".

**The fix.** `sign_macos.rs` now moves nothing. It appends the payload — the
packed bytes then the 64-byte trailer — after `__LINKEDIT`'s existing content
(dropping the stale signature bytes), grows `__LINKEDIT`'s `filesize`/`vmsize`
so the segment still ends the file, reuses the `LC_CODE_SIGNATURE` command the
linker already left (repointing `dataoff`/`datasize`; **no** load command is
added or removed for a signed build, so nothing slides), and computes a fresh
ad-hoc `CodeDirectory` over the finished bytes. The entry point, every segment's
`fileoff`/`vmaddr`, and every fixup are byte-for-byte the stub's. This is how
`codesign(1)` itself embeds a signature. `payload::locate` gains
`PayloadVia::MachOAppended`: it reads `LC_CODE_SIGNATURE`'s `dataoff` and parses
the trailer that ends there (`macho::code_signature` is the new reader); an
unsigned build has no signature after the payload, so its trailer is the last 64
bytes and the end-of-file reader finds it (`PayloadVia::EofTrailer`). The
`__GINARY,__payload` section is still *read* (`MachOSection`) for an artifact an
older ginary wrote, but no longer *written*.

- job `100551483194` (macos-14/aarch64), `100551483005` (macos-15-intel/x86_64),
  run `33724862229`; the `Segmentation fault: 11` / exit 139 both reported.
- **fix:** `src/sign_macos.rs` rewritten (append-in-`__LINKEDIT`, `CS_ADHOC`

  `an_injected_artifact_does_not_claim_to_be_linker_signed`) pass; the eleven

  (`d3_macho_section_addr_was_never_shifted`,
  `d3_macho_segment_vmaddr_and_vmsize_were_wrong`,
  `e8_the_injected_segment_broke_page_alignment`,
  `e8_the_ad_hoc_signature_did_not_cover_the_finished_file`) stay green — the new

### 10 — a signed Mach-O whose `dataoff` points past EOF was a read error (payload.rs)

Reviewer finding (low, behavioural): `payload::locate`'s `LC_CODE_SIGNATURE`
branch reads the trailer at `dataoff - TRAILER_LEN` with no check that the read
stays inside the file. `macho::code_signature` reads `dataoff` out of the load
command over the capped `head`, so it cannot validate it against the real file
length; a malformed or truncated signed Mach-O whose `dataoff` runs past EOF
reaches `read_exact_at`, which fails and returns `Err(TrailerError::Io)` —
where the adjacent comment promises the branch "falls through to the section
lookup" for a signature with no ginary trailer.

**RED.** A new targeted test in `tests/payload_locate.rs`,
`a_signed_macho_whose_dataoff_points_past_eof_is_not_a_read_error`, builds a
thin Mach-O with a valid header and an `LC_CODE_SIGNATURE` whose `dataoff` field
is overwritten to `0xffff_ff00` (well past the ~250-byte file), and asserts
`locate` returns `Ok(None)`:

```text
---- a_signed_macho_whose_dataoff_points_past_eof_is_not_a_read_error stdout ----
thread '...' panicked at tests/payload_locate.rs:328:10:
an out-of-range signature dataoff is not a read error; it falls through:
Io(Error { kind: UnexpectedEof, message: "failed to fill whole buffer" })
test result: FAILED. 0 passed; 1 failed; 0 ignored; 0 measured; 11 filtered out
```

**Fix.** `src/payload.rs` range-checks the trailer window against `file_len`
(already read a few lines above) before the read: the `if let` chain gains
`&& trailer_at.checked_add(TRAILER_LEN).is_some_and(|end| end <= file_len)`, so
an out-of-range signature falls through to the section lookup exactly as a
magicless one does. The comment records why `head` cannot make the check itself.

**Test.** The RED test above now passes; the other eleven `payload_locate`
tests stay green, unsigned and no-default-features.

### 11 — `macho::code_signature` parsed non-64-bit-LE magics with 64-bit-LE geometry (macho.rs)

Reviewer finding (low, non-behavioural): `code_signature` guarded
`THIN_MAGICS.contains(&magic)` — which admits `MH_MAGIC` (32-bit, a 28-byte
header) and the byte-swapped `MH_CIGAM`/`MH_CIGAM_64` (big-endian fields) — then
unconditionally read `ncmds` at offset 16 and started the load commands at
offset 32 with little-endian reads. That geometry is correct only for
`MH_MAGIC_64`. No panic (every read is bounds-checked), but the parse is wrong
for the other three magics. ginary writes and signs only 64-bit little-endian
Mach-O.

**Fix (no separate test — a robustness change with nil live impact).**
`src/macho.rs` restricts the guard to `magic != MH_MAGIC_64`, with a comment
recording that the hand walk encodes the 64-bit-LE header layout and only that
one. Every committed and fabricated Mach-O fixture is `MH_MAGIC_64`, so the
existing `macho`/`payload_locate` suites stay green; a differently shaped
Mach-O now reports no signature rather than a misparse.

### 12 — the signed locate round-trip under-asserted the production branch (sign_macos.rs)
