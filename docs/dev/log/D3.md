## Housekeeping

### 1 — a removal walked the ordinary spelling of a verbatim tree (low)

D2 established one sentence: **ginary opens the verbatim spelling and hands `erl.exe` the
ordinary one.** `CacheDirs::extraction_dir` puts the `\\?\` prefix on the directory an extraction
hangs off, `ensure_extracted` *answers* with that spelling, and every read that follows — the
cache-hit check, the `.lock`, the manifest probe, `launch::preflight` — therefore opens the path
that is actually on disk.

The removals were never brought into that sweep. Each of them was handed the ordinary spelling by
its caller and walked it:

| caller | argument | walker |
|---|---|---|
| `GINARY_CMD=uninstall` | `CacheDirs::app_dir` | `cache::uninstall` |
| `ginary cache prune` | `CacheDirs::root` | `cache::prune` → `cache::prune_app` |
| `ginary cache clean` | `CacheDirs::root` | `cache::clean` |
| `cache::ensure_extracted` | the app dir it was given | `cache::discard_incomplete` |
| `cache::sweep` | the app dir it was given | itself |

`launcher::dispatch` was the one exception, and only half of one: D2's fix passed
`extraction_dir(app)` to `prune_siblings` while passing `app_dir(app)` to the crash-dump plan two
lines above, so the module held two spellings of one directory at the call site — which is the
shape the D2 defect had.

What makes this worth a regression test rather than a footnote is that the failure is silent.
`read_dir` on the application directory succeeds even when the entries under it are past
`MAX_PATH`, so a prune finds the entry, reads its age and takes its lock; it is the `rename`
aside that fails on the length. The entry is then reported `kept … (unremovable)` and left on
disk. On exactly the deep `%LOCALAPPDATA%` path the prefix exists for, `GINARY_CMD=uninstall`
would have printed a table saying it had uninstalled nothing, every time, with no error anywhere.

The fix puts the rule in the walker rather than at the call site, which is the only placement that
cannot drift: `sweep`, `discard_incomplete`, `prune_app`, `uninstall`, `prune` and `clean` each
begin by putting the directory they were given into the spelling the extraction wrote. Two private
helpers in `cache.rs` name the two halves:

```rust
fn walked(dir: &Path) -> std::borrow::Cow<'_, Path> {
    crate::winpath::long_path(dir)
}

fn reported(path: &Path) -> PathBuf {
    crate::winpath::plain_path(path).into_owned()
}
```

`walked` is safe to apply on top of a caller that already holds the verbatim spelling, because
`long_path_str` leaves an already-prefixed path alone. That idempotence is what lets the launcher
go back to one spelling: `prune_siblings` is now given the same `crash_dump_dir` the launch plan
is, and the comment above it says why.

`reported` is the other half, and it is not cosmetic. Every path `read_dir` hands back under a
verbatim root inherits the prefix, so without it a `PruneReport`, a `CleanReport` and the path
inside a `LauncherError::Cache` would all have started naming entries `\\?\C:\…`. Those three are
read by a person; the prefix is a fact about how the tree was opened, not part of the path's
identity. It is the same conversion `launch::plan` makes when a cache path stops being ginary's
business, and unlike `walked` it is compiled on every platform, because `plain_path` acts only on
text beginning `\\?\` and no unix path does.

One small refactor came with it. `prune` and `clean` both did `check_app` inside the `Some(app)`
arm of the match that builds their target list; the check now happens once, before the root is put
into the walking spelling, so a refusal names the root the caller asked about rather than a
prefixed one. That is `cache::check_app_of`.

`launcher::repair_once` and the `before-lock` fault point remove trees too, and neither was
touched: both act on the entry `ensure_extracted` answered with, which is the verbatim spelling by
that function's contract.

Two prose claims went stale with the fix and were corrected rather than left to mislead the next
reader. The `winpath` module documentation said `long_path` "is applied at **one** call site" and
`plain_path` "at one call site too"; both are now two, and the module says which and why.
`docs/dev/debugging.md` said the prefix goes on once and comes off once, in the same words. The
one-sentence rule itself is unchanged — ginary opens the verbatim spelling and hands `erl.exe` the
ordinary one — and the removal reports are the case that rule did not previously name: a path that
is shown to a person is neither opened by ginary nor handed to `erl.exe`.

**What this machine proved, and what it did not.** The path rule on both sides is pure syntax and
is asserted here:
`tests/regressions/d2_a_removal_walked_the_ordinary_spelling_of_a_verbatim_tree.rs` checks that
the spelling a removal opens is *not* the one a Windows caller holds, that prefixing an
already-prefixed root is a no-op, that a path found under a verbatim root reports back as the
caller's own spelling, and that a real `uninstall` on this host still names exactly the paths it
was given. Two unit tests in `cache.rs` cover `reported` on the drive-absolute, UNC and unix
shapes and pin `walked` as the borrowing identity off Windows. The `rename` that fails past
`MAX_PATH` is a Windows fact and is not asserted anywhere — same standing as the rest of the D2
Windows surface, which the GitHub Actions milestone owns.

The TDD loop is worth being exact about here, because it was not the usual one. No assertion in
this suite could go red before the fix: `winpath::long_path` is compiled to the borrowing identity
on unix, so on this host a removal handed the ordinary spelling and one handed the verbatim
spelling walk the same bytes and produce the same report. The failing-first step was therefore
taken at the path-string seam — `long_path_str` and `plain_path_str`, which are compiled on every
platform for exactly this reason — where the two spellings of a Windows path are different values
and a test can say so. `tests/windows.rs` has held that seam since D2; what is new is the
statement that a *removal* is one of its call sites. The filesystem test beside it
(`an_uninstall_still_reports_the_paths_the_caller_gave_it`) is a green-stays-green: it is the
guard that routing every walk through two new helpers did not change what a caller reads.

### A design decision the RED tests commit to: payload-section geometry

The plan text describes the section's inner trailer two ways that do not both hold literally at
once: "its first 64 bytes are the same trailer struct" (which puts the trailer at the section's
byte 0), and a validation `offset_rel + len + 64 == section_size` (which, read the way
`Trailer::parse`'s own `payload_offset + payload_len + TRAILER_LEN == file_len` check reads,
would put the trailer at the *end* of a region one trailer-length larger than the section). Both
readings cannot be true of one physical layout, and the spec does not resolve it further.

This RED pass commits to the first reading, because it is the one a hand-rolled format actually
needs no slack for: **the section holds nothing but the 64-byte trailer at its own offset 0,
immediately followed by the payload — `section_size == 64 + payload_len` always — and the
trailer's own `payload_offset` field, read from inside the section, is fixed at 64.**
`payload::locate` converts that to an absolute offset as `section_offset + 64`. The geometry
check that falls out of this is `payload_offset(64) + payload_len == section_size`; every test
in `tests/payload_locate.rs` and `tests/sign_macos.rs` is written against exactly this, and the
long comment at the top of `tests/payload_locate.rs` states the reasoning in place, so GREEN
either confirms this reading (most likely) or has a specific, documented seam to revisit if a
different resolution turns out to be intended. `tests/fixtures/macho/README.md`'s section-offset
numbers and `tests/common/macho.rs::payload_section_body` are both built on this layout.

Two related decisions, smaller: `macho::read` does **not** error on a fat Mach-O — it returns
`Ok(MachoFacts { is_fat: true, cputype: "", target: None, sections: vec![], .. })`, honestly
reporting that none of those three has one answer without choosing an architecture first, and
each *caller* (`payload::locate`, `sign_macos::inject_and_sign`) checks `is_fat` itself and
raises its own typed refusal (`TrailerError::Fat`, `SignMacosError::Fat`). This reads the spec's
"a fat binary is reported is_fat=true ... caller errors" as literally as written, and gives the
`is_fat` field an actual, reachable `true` value rather than one that could never occur because
`read` had already turned it into an `Err`.

different asset-naming scheme entirely) and one object format, taking `impl Fn(&Path) ->
Result<ElfInfo, ElfError>` as its emulator inspector. Making a macOS selector reach that
function at all needs the inspector generalised over ELF and Mach-O — the actual GREEN-phase
architecture work the spec's "catalog repack macos arm" section describes — rather than a RED
stub that would either not compile against `repack_one`'s current signature or would have to
duplicate a large fraction of `repack_one` under a new name to fake exercising it. `docs/dev/log/D3.md`
records that this abstraction change, and the real repack run for `macos-aarch64` it enables, is
GREEN-phase work; RED here is scoped to the two small, pure, independently useful pieces above
(the asset name and the commit guard), both of which GREEN's generalised `repack_one` will call.

### `macho::read`: the `object` crate carries almost all of it

`object` 0.40.0 (already a dependency, `read` + `elf` + `macho` + `pe` + `std`, no new feature
needed) reads a thin Mach-O's architecture and section table through its unified `Object` /
`ObjectSection` traits — the same shape `native.rs`'s `describe_with_object_crate` already uses
for a PE. `cputype` and `target` are spelled by hand for the two architectures this crate
packages (`"x86_64"`, `"arm64"`; the crate's own `Architecture` Debug name would print `Aarch64`,
which is not the spelling `docs/format.md` and every test use), falling back to the crate's
`Debug` name, lower-cased, for anything else. Sections come straight off
`ObjectSection::segment_name`/`name`/`file_range`.

The one fact `object`'s high-level `Object` trait does not surface is whether an
`LC_CODE_SIGNATURE` load command is present — that needs a load-command walk, which
`object::read::macho::MachHeader::load_commands` (reached through the `File::MachO32`/`MachO64`
variants, both sharing one `Endianness` type parameter, so one function serves both widths)
gives directly: `carries_code_signature` just asks whether any command's `cmd()` equals
`object::macho::LC_CODE_SIGNATURE`. A fat header is detected by magic before any of this runs, per
the RED-phase design decision, and never reaches `object::read::File::parse` at all — that
function has no fat-Mach-O variant and would error on one.

All 21 tests in `tests/macho.rs` passed on the first run against this implementation, including
both proptests and the two real-fixture tests (`__TEXT,__text` at offset 1728, size 22324, and
the `LC_CODE_SIGNATURE` erlef's own build already applies).

### `payload::locate`: a bounded read, not the whole file

The RED-phase geometry decision (the section's own first 64 bytes are the trailer, `payload_offset`
fixed at `TRAILER_LEN`, `payload_offset(64) + payload_len + TRAILER_LEN == section_size +
TRAILER_LEN`) is exactly what GREEN implements, reusing `Trailer::parse` itself for that check by
passing `section_size + TRAILER_LEN` in place of a file length — the same equation the EOF case
already checks, applied to a region one trailer length larger than the section. `Trailer::read_from`
is tried first, unconditionally, so every ELF and PE test — every one of them, unedited — keeps
passing; only when that answers `None` and the first four bytes are a Mach-O magic does anything
Mach-O-specific run at all.

One efficiency decision worth recording: `locate` does not read the whole file to look for the
section. The Mach-O header and every load command sit at the front of the file; the payload
itself, which can be gigabytes, sits inside the section they describe. `locate` reads at most
`MACHO_HEAD_CAP` (16 MiB) of the file's front, parses that, and then does two bounded `pread`s —
one for the section's own inner trailer, one is not needed since the payload's own bytes are
never read by `locate` at all, only their offset and length are reported. `pread`, not a seek:
`Trailer::read_from`'s own `read_exact_at` helper (unix `read_exact_at`, Windows `seek_read`
looped to completion) is now `pub(crate)` — mechanically, no behaviour change — and `locate`
reuses it rather than duplicating the two `cfg`-gated implementations.

`test locate_finds_the_eof_trailer_of_a_plain_artifact` failed once, honestly, for a reason that
had nothing to do with the implementation: the test's own stub literal, `b"stub bytes go here,
arbitrary length"`, is 36 bytes, and the test's comment and hardcoded expectation both said 37 —
a miscount made while writing the RED-phase fixture. The fix is in the test, not the production
code: the assertion now reads `stub.len() as u64` instead of a repeated literal, which is both
correct and removes the chance of the same mistake recurring. Every other assertion in the file
was already correct; this is the only test correction `tests/payload_locate.rs` needed.

### `sign_macos::inject_and_sign`: `libsui` read, not depended on — here is why

`libsui` 0.16.4 (`denoland/sui`) is exactly the crate the plan named, its `Macho` type is exactly
the shape the spec describes (`Macho::from(bytes)?.write_section(name, data)?.build(&mut out)?`,
with `build_and_sign` for the signed form), and its source was read in full at implementation
time to decide whether it could be used as a dependency. Two things ruled it out:

1. **The new segment's name is not configurable.** `Macho::write_section`'s arm64 path
   hardcodes the segment it inserts to `pub(crate) const SEGNAME: [u8; 16] = *b"__SUI\0..."`
   — there is no public API to ask for `__GINARY` instead, and every test committed at RED
   phase (`tests/sign_macos.rs`, `tests/stub.rs`'s three darwin cases, and
   `tests/common/macho.rs::with_payload_section`) is written against `__GINARY,__payload`
   specifically, per the spec's own naming. Depending on the crate would have meant either
   asking upstream for a change and waiting, or shipping the wrong section name.
2. **The x86_64 path is a different technique entirely, and needs `target_vendor = "apple"`.**
   Rather than the arm64 path's segment insertion, `Macho::write_section` on x86_64 appends a
   sentinel-marked blob at end-of-file and, on an actual Mac, shells out to the `codesign`
   binary to strip and reapply the platform signature; off Apple, that whole block is compiled
   out and the section is written unsigned with no equivalent of the arm64 geometry at all. A
   build tool that has to run identically on the CI Linux runner that builds every target and
   (eventually) a real Mac cannot depend on a codepath that only does the real work on one of
   them.

So `libsui` was **read, not added to `Cargo.toml`** — no dependency, new or otherwise, was added
in this pass at all. `sign_macos.rs`'s `Writer` (the section-and-signature planner) and
`build_ad_hoc_signature` (the ad-hoc `CodeDirectory` writer, adapted from `libsui`'s own
`apple_codesign::MachoSigner`) are ginary's own code, generalising the technique `libsui`
demonstrates works — write a page-aligned new segment where `__LINKEDIT` used to start, shift
`__LINKEDIT` and every `symtab`/`dysymtab`/`dyld_info`/`linkedit_data` command that points into
it by the same amount, drop whatever `LC_CODE_SIGNATURE` the stub already carried since a
signature over the old bytes says nothing about the new ones, and (when asked) compute a fresh
ad-hoc `CodeDirectory` — one path for both architectures this crate targets, without a
`codesign` subprocess and without `target_vendor` gating anywhere. Every doc comment on
`Writer`, `build_ad_hoc_signature` and the segment-name note on ADR 0016 says this plainly: MIT,
Copyright (c) 2024 Divy Srivastava and the Deno authors, adapted rather than depended on.
`apple-codesign` (`indygreg/apple-platform-rs`, 0.29.0 at RED-phase time) was never reached for:
once the ad-hoc `CodeDirectory` needed to be hand-written anyway (to control the segment name in
the section-insertion half), reusing `libsui`'s much smaller, purpose-built signer as a model was
less surface than pulling in `apple-codesign`'s whole certificate/signing-identity machinery for
a feature (ad-hoc only, no identity) that machinery is not needed for.

Real Mach-O geometry, not a simplification: the header-growth shift (every segment's `fileoff`,
extending the header-containing segment's own `filesize` to still reach its old logical end,
every section's `offset`) is applied uniformly across the *whole* file, not only `__LINKEDIT` —
checked against the committed fixture, whose load-command area has only 40 bytes of padding
before `__TEXT,__text` begins (1728 minus 1688), nowhere near the 136+ bytes this crate's new
segment-and-section command needs. A `__LINKEDIT`-only shift, which is as far as `libsui`'s own
arm64 path goes, would have corrupted `__TEXT` on exactly this fixture. `vmaddr`/`vmsize` are
shifted by the identical rule, on the VM-address axis rather than the file-offset one — see "Fix
round 1" below for the review finding that caught this being missing in the first pass, and the
byte-level fix.

### `catalog.rs`'s two pure functions

### The mechanical refactor: every reader of a trailer now reads through `payload::locate`

The spec's proof condition — "refactor them mechanically so EVERY existing test stays green with
no edit" — held everywhere it was applied. `Trailer` itself is untouched: field names, `to_bytes`,
`cache_key`, `Trailer::read_from` for the EOF case. What changed is *how* the four places named
in the spec first obtain one:

- **`launcher::mode`** — the one function `main()` calls to decide CLI or launcher mode at all —
  now calls `payload::locate` and rebuilds a `Trailer` from whichever container answered
  (`PayloadLoc { offset, len, sha256, .. }` maps straight onto `payload_offset`, `payload_len`,
  `payload_sha256`). Every step downstream of `mode` — `dispatch`, `ensure_extracted`,
  `extract_into`, the crash-dump plan, `prune_siblings` — still takes a plain `&Trailer` exactly
  as it always did and does not know or care which container the trailer came from. This is the
  one launcher-path change in this pass, and it is why a real darwin build of this launcher
  would recognise its own `__GINARY,__payload` section as a payload at all, not just a claim
  that it structurally could.
- **`inspect::open`** (and therefore `verify::run`, which is built entirely on
  `inspect::open`'s `ArtifactInfo`) makes the identical swap. `ginary inspect` and `ginary
  verify` can now open a Mach-O artifact exactly as they open an ELF or PE one.
- **`bundle::check_stub`** makes the same swap, so a Mach-O file that already carries the
  `__GINARY,__payload` section is refused as `BundleError::BundledStub` the same way an
  EOF-trailered ELF or PE stub is, rather than only being caught later by `stub::verify`'s own
  `StubError::Sectioned`.

`cache::ensure_extracted` itself needed no change at all: it already took `trailer: &Trailer` by
value from its caller rather than reading one itself, so once `launcher::mode` supplies a
correctly-populated `Trailer` regardless of source, every function downstream of it was already
container-agnostic by construction — the "one abstraction everything downstream reads through"
the spec asks for turned out to already be true of `cache.rs`'s own design, and needed no edit to
prove it.

Every existing test in `tests/cli.rs`, `tests/smoke_cli.rs`, `tests/regressions.rs`,
`tests/windows.rs`, `tests/cache.rs`, `tests/cache_lock.rs`, `tests/launcher.rs`,
`tests/launch.rs`, `tests/inspect.rs`, `tests/verify.rs` and `tests/bundle.rs` passed unedited
after this refactor — the full-suite run below is that proof.

### `bundle.rs`'s darwin arm

`write_artifact` now branches on `target.os`: an ELF or PE target is unchanged, byte for byte,
from before this milestone. A macOS target calls the new `write_macos_artifact`, which packs the
payload into memory (rather than streaming it to a file the way the EOF path does — a macOS
artifact's payload has to be a byte slice for `sign_macos::inject_and_sign` regardless), builds

calls `inject_and_sign` with `CodeSign::Adhoc`. One honestly-recorded gap: unlike the ELF/PE

`sign_macos::inject_and_sign` writes its output path directly. There is no darwin toolchain here
to build a stub with, so this arm has no way to be exercised end to end on this host regardless
of how it is written, and making it crash-safe the way the ELF/PE path is belongs with the
milestone that can actually run a macOS build to completion; the doc comment on
`write_macos_artifact` says so.

`tests/bundle.rs` gained one new test,
`a_macos_build_with_no_darwin_stub_gets_the_honest_stub_search_error`: with no `--stub` and no

state a darwin build reaches on this machine, exactly as the spec predicted, and it is now
asserted rather than only described.

### What was deliberately scoped out of this pass, and why

Two pieces of the spec text are not implemented in this pass. Neither had a RED-phase test
forcing it — the RED report named both explicitly as GREEN-phase architecture work — and neither
is silently dropped: both are recorded here, in the ADR (0016's last consequence bullet) and in
`docs/format.md`, so the gap is a stated decision rather than a discovered one.

- **The real `macos-aarch64` catalog repack was not run.** `catalog::repack_one` is built
  entirely around one upstream (`gleam-community/erlang-linux-builds`) and one object format,
  taking `impl Fn(&Path) -> Result<ElfInfo, ElfError>` as its emulator inspector — reaching
  `erlef/otp_builds` and a Mach-O `beam.smp` needs that inspector generalised over both formats,
  which is a real architecture change to a pipeline `tests/catalog.rs` and `tests/otp_repack.rs`
  already hold to a lot of existing behaviour. Doing that hastily, under this milestone's time
  budget, risked regressing a pipeline the Linux side of this crate depends on, for a repack this
  host cannot even prove ran a real macOS binary once it finished (there is no way to execute the
  result here either way). A second, smaller gap compounds it: this crate has no Mach-O stripper
  — `strip.rs` is `strip` on ELF and `beam_lib:strip_files` on `.beam`, and a macOS repack would
  need a third answer for `beam.smp` and every native object in the tree, which does not exist
  yet. `erlef_upstream_asset` and `macos_catalog_admissible` — the two pieces of this the spec
  calls independently useful and RED already scoped narrowly — are real and tested; the pipeline
  that would call them for a genuine repack is not built yet. `dist/otp/catalog.json` carries no
  macOS entry, which is the correct, honest state either way: even a successful repack would only
  become committable once `macos_catalog_admissible(29, 29)` says so, and nothing here claims a
  runtime this repository cannot prove works.
- **`ginary verify`'s native-object scan is not Mach-O-aware.** `macho.rs` can already answer
  `cputype`/target/code-signature questions about an object found inside a payload exactly the
  way it answers them about the artifact itself; `verify.rs`'s scan (`native_issues` and what
  feeds it) is built entirely around `elf::inspect_bytes` and a `DT_NEEDED` allowlist that is
  Linux-specific by construction (`NEEDED_ALLOWLIST`, `LOADER_PREFIX` — glibc sonames have no
  macOS analogue). Wiring `macho::is_macho`/`macho::read` into that scan as a second recognised
  format, with its own (much shorter, since macOS names no `DT_NEEDED`-equivalent runtime
  dependency the way ELF does) rule for what an inner Mach-O is allowed to need, is real,
  separate design work this pass did not reach. No test in RED asked for it, and both
  `docs/adr/0016-macho-section-payload-and-adhoc-signing.md` and `docs/format.md` say this
  plainly rather than implying `ginary verify` already understands an embedded Mach-O the way it
  understands an embedded ELF.

## Fix round 1

An adversarial review of the D3 diff (still uncommitted at review time) found five issues: two
high-severity defects in `sign_macos.rs`'s segment geometry and in `write_macos_artifact`'s
robustness, one medium (also `write_macos_artifact`), and two low (a documentation gap and an
under-enforced invariant in `payload::locate`). Every behavioural one got a regression test,
watched RED, before the fix. In finding order:

### 1 — `Writer` never shifted a segment's `vmaddr`/`vmsize` (high, behavioural)

**The claim.** `Writer::plan` shifted every segment's `fileoff` (and the offsets a
`symtab`/`dysymtab`/`dyld_info`/`linkedit_data` command points into `__LINKEDIT` with) by the
header growth, and `__LINKEDIT`'s own `fileoff` further by the payload segment's size — but never
touched `vmaddr` or `vmsize` at all, and reused `__LINKEDIT`'s *original* `vmaddr` verbatim for
the new `__GINARY` segment. Two concrete consequences: the new segment and the relocated
`__LINKEDIT` declared the identical `vmaddr` (an invalid Mach-O outright), and `__TEXT`'s
`filesize` grew to cover the longer load-command area while its `vmsize` did not, so `filesize`
ended up larger than `vmsize` — itself invalid, since a segment may not claim more file-backed
bytes than its own VM region holds. The reviewer decoded the committed fixture by hand to confirm
both numbers; this pass wrote that same decode as a test rather than trusting the hand check.

**RED.** `tests/regressions/d3_macho_segment_vmaddr_and_vmsize_were_wrong.rs`, over the real
fixture, both unsigned and ad-hoc-signed:

```
$ cargo test --features cli --test regressions d3_macho_segment
running 2 tests
test d3_macho_segment_vmaddr_and_vmsize_were_wrong::inject_and_sign_produces_distinct_non_overlapping_segments_unsigned ... FAILED
test d3_macho_segment_vmaddr_and_vmsize_were_wrong::inject_and_sign_produces_distinct_non_overlapping_segments_signed ... FAILED

---- ...unsigned stdout ----
thread '...' panicked at tests/regressions/d3_macho_segment_vmaddr_and_vmsize_were_wrong.rs:80:9:
__TEXT: filesize 32904 exceeds vmsize 32768 -- a segment may not claim more file-backed bytes
than its own VM region

---- ...signed stdout ----
thread '...' panicked at tests/regressions/d3_macho_segment_vmaddr_and_vmsize_were_wrong.rs:80:9:
__TEXT: filesize 32920 exceeds vmsize 32768 -- a segment may not claim more file-backed bytes
than its own VM region

test result: FAILED. 0 passed; 2 failed
```

32904 = 32768 + 136 (the unsigned header growth: 152 bytes added for the new segment-and-section
command, minus the 16-byte `LC_CODE_SIGNATURE` the fixture already carried and this pass drops);
32920 = 32768 + 152 (the signed growth, which also adds a fresh 16-byte `LC_CODE_SIGNATURE`,
netting the same 152 the segment-and-section command alone costs). Both match the reviewer's own
hand decode exactly, and neither test reached the `vmaddr` collision assertion at all — the
`filesize > vmsize` check runs first for `__TEXT` and failed before the loop got to a pair of
segments to compare.

**The fix.** `shift_segment` now takes `old_linkedit_vmaddr` alongside `old_linkedit_fileoff` and
shifts `vmaddr` by the identical rule `fileoff` already followed: unconditionally by
`header_growth` (growing the header-containing segment's load-command area pushes every
following segment's VM address forward the same way it pushes every following segment's file
offset forward), plus the payload segment's own aligned size once `vmaddr` reaches
`old_linkedit_vmaddr` — mirroring the `fileoff`/`old_linkedit_fileoff` rule exactly, which is
what keeps the new `__GINARY` segment and the relocated `__LINKEDIT` from landing on the same
address. The `fileoff == 0` branch (the segment mapping the header itself) now grows `vmsize`
alongside `filesize`, by the same `header_growth`, so the two stay equal the way they started.
The new segment's own `vmaddr` and its section's `addr` are computed as
`old_linkedit_vmaddr + header_growth` — the VM-space twin of `section_fileoff`, already computed
that way on the file-offset axis.

**GREEN.**

```
$ cargo test --features cli --test regressions d3_macho_segment
test d3_macho_segment_vmaddr_and_vmsize_were_wrong::inject_and_sign_produces_distinct_non_overlapping_segments_unsigned ... ok
test d3_macho_segment_vmaddr_and_vmsize_were_wrong::inject_and_sign_produces_distinct_non_overlapping_segments_signed ... ok
test result: ok. 2 passed; 0 failed
```

`tests/macho.rs`, `tests/payload_locate.rs` and `tests/sign_macos.rs` (39 tests together) were
re-run after the fix and stayed green, unchanged.

This still is not proof a real kernel accepts the file — that needs a Mac, unchanged from the
rest of this document's scope note — but the two structural defects the review actually
demonstrated (a `vmaddr` collision, `filesize > vmsize`) are now checked on every run rather than
merely disclaimed as "not verified here".

### 2 — `write_macos_artifact` never created its output directory (high, behavioural)

**The claim.** `write_artifact`'s ELF/PE arm calls `std::fs::create_dir_all` on `out`'s parent
before writing anything; the darwin arm went straight to `inject_and_sign`, whose only write is
`std::fs::write(out, &body)` — a raw `NotFound` IO error when the output directory (the ordinary
case for a first build) does not exist yet.

**RED.** `bundle::tests::write_macos_artifact_creates_the_output_directory_when_it_does_not_exist`,
a unit test (the function is private, so this could not be an integration test) against a fresh
staging tree and the committed Mach-O fixture standing in for a stub:

```
$ cargo test --features cli --lib bundle::tests::write_macos_artifact
thread 'bundle::tests::write_macos_artifact_creates_the_output_directory_when_it_does_not_exist' panicked at src/bundle.rs:2246:9:
expected the output directory to be created, got Some(MacSign(Io { path: "/tmp/.tmpThWSeO/build/output/not/yet/created/hello", source: Os { code: 2, kind: NotFound, message: "No such file or directory" } }))
```

**The fix.** `write_macos_artifact` now creates `out`'s parent directory before calling
`inject_and_sign`, the same call the ELF/PE arm already makes.

### 5 — `payload::locate` did not enforce the fixed `payload_offset` (low, behavioural)

**The claim.** `docs/format.md` fixes the inner trailer's `payload_offset` at exactly
`TRAILER_LEN`: the payload immediately follows the trailer and nothing else is in the section.
`locate` reused `Trailer::parse` purely for its `payload_offset + payload_len + TRAILER_LEN ==
region_len` equation and never checked `payload_offset` itself against `TRAILER_LEN` — a section
whose trailer instead read `payload_offset = 0, payload_len = section_size` also balances that
equation, and `locate` would silently accept it, pointing `PayloadLoc::offset` at the trailer's
own bytes rather than skipping past them.

**RED.** `tests/payload_locate.rs::locate_reports_a_typed_error_for_a_section_whose_trailer_offset_is_not_the_fixed_one`,
a section built exactly to that other solution:

a payload_offset other than TRAILER_LEN must not locate successfully: Some(PayloadLoc { offset: 184, len: 69, sha256: [...], via: MachOSection })

`offset: 184` is exactly `section_offset + 0` — the trailer's own bytes, not the payload past it —

**The fix.** `locate` now checks `inner_trailer.payload_offset == TRAILER_LEN` explicitly after

An independent external harness called `inject_and_sign` on the committed real fixture and

### 1 — `shift_segment` never shifted a section's `addr` (high, behavioural)

**The claim.** `shift_segment`'s section loop shifts `section_64::offset` (the file offset, at
byte 48 of the 80-byte `section_64` record) by exactly the same rule the containing segment's own
`fileoff` is shifted by. It never touches `section_64::addr` (the section's VM address, at byte
32) at all, in either the `fileoff == 0` branch or the `else` branch, for any segment. Fix round
1 made every segment's own `vmaddr` shift correctly (finding 1 there), but every *section inside*
a segment whose `vmaddr` moved — every segment other than the one mapping the header, since that
one's `vmaddr` does not move, only its `filesize`/`vmsize` grow — kept its original `addr`, now
sitting before the segment's new `vmaddr`: outside that segment's own `[vmaddr, vmaddr +
vmsize)` range. An invalid Mach-O, regardless of any live kernel, and invisible to fix round 1's
regression test, which decodes `LC_SEGMENT_64` fields only and never reads a `section_64`.

**RED.** New test file `tests/regressions/d3_macho_section_addr_was_never_shifted.rs`, decoding
every section inside every `LC_SEGMENT_64` and asserting each section's `addr` falls within its
own segment's `[vmaddr, vmaddr + vmsize)`:
