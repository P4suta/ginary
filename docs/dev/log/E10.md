### 7 — macOS x86_64: the stub carries no `LC_CODE_SIGNATURE` to reuse

**Job.** `macOS (macos-15-intel, macos-x86_64)`, job
[`100597889308`](https://github.com/P4suta/ginary/actions/runs/33739517757/job/100597889308).
Steps 1 through 6 pass; step 7, `Package, run and verify a hello_ffi artifact`,
fails at the packaging command:

```text
error: cannot write the macOS payload section
  caused by: the stub is not a Mach-O this ginary can read: cannot parse the Mach-O file:
             cannot ad-hoc sign a Mach-O with no LC_CODE_SIGNATURE to reuse; its
             load-command area cannot grow without relocating code
##[error]Process completed with exit code 1.
```

**Diagnosis.** E9's writer moves nothing: it appends the payload inside
`__LINKEDIT`, grows that segment, and points the stub's *existing*
`LC_CODE_SIGNATURE` at the fresh signature. The arm64 twin of this job passes on
the same code because the platform linker ad-hoc signs every arm64 Mach-O it
produces, so an arm64 stub always arrives with a command to reuse. An x86_64
stub often does not, and `Writer::plan` refuses rather than corrupting the
image. The refusal is honest and the gap is real.

**The measurement the fix rests on.** Three numbers, and E10 takes all three
from the code rather than quoting E9:

| quantity | bytes |
| --- | --- |
| `LC_CODE_SIGNATURE` (a `linkedit_data_command`) | 16 |
| `LC_SEGMENT_64` plus one `section_64` (what a payload section needed) | 152 |
| slack before the first section, committed arm64 fixture | 40 |

The committed fixture's load commands end at 1688 (`32 + sizeofcmds`, where
`sizeofcmds` is 1656) and its first section begins at 1728. Sixteen fits in
forty; a hundred and fifty-two does not, which is the whole of why E9 could not
add a segment and E10 can add a signature command. `sign_macos::load_command_slack`
is that measurement as a function, so a stub whose slack is unknown can be
asked rather than assumed.

**The shape of the fix (GREEN).** When the stub carries no
`LC_CODE_SIGNATURE`, append a sixteen-byte one immediately after the commands
that are already there, into the slack, and raise `ncmds` by one and
`sizeofcmds` by sixteen. The bytes it is written into belong to no load command
and no section, so every file offset in the image stays exactly where the
linker put it: the entry point, every segment, every `LC_DYLD_CHAINED_FIXUPS`
target. When the slack is smaller than sixteen bytes, keep the honest refusal
and name both numbers.

### 9 — the Windows rules pinned as pure functions here

Cause G is a defect in `src/`, and the other three rows above are rules the
suite itself gets wrong. Each is expressed as a function of its arguments and
tested on this host against the spellings only Windows produces, which is the
technique `platform::erl_program`, `winpath::plain_path_str` and
`cache::xdg_base_is_absolute` already use.

**Cause G — the needle halves were stored side by side.** `stubid` never
stores the needle whole: it stores `GINARY-STUB` and `-ID\0` and joins them at
run time, precisely so that a scanner does not match itself. But the two halves
are two constants, and a linker is free to lay two constants out adjacently —
and then the file holds `GINARY-STUB-ID\0` contiguously at an address no code
in this crate chose. That is the second marker: one record, and one accident of
layout. On this host the two hits collapse (every Linux and cross-built Windows
stub in `target/stubs` holds the needle exactly once, inside its marker); on
the MSVC runner they do not. Both halves of the defect are pinned:

- no two of the byte images a build stores may be joinable into the needle, in
  any order — `stubid::needle_fragments` makes that checkable, and the same
  claim is made of the test suite's own halves, which are linked into every
  test binary;
- a scan counts **records** — 128 whole bytes, terminated, zero-padded, naming
  the four fields — rather than needle hits, so a file with one record and one
  stray hit is a stub and only two whole records are an ambiguity.
  `stubid::candidates` and `stubid::records` are the two questions, told apart.

Tests: `a_needle_that_is_not_a_whole_record_is_not_an_identity`,
`records_and_candidates_tell_a_whole_record_from_a_stray_needle`,
`two_whole_records_are_ambiguous_and_the_count_is_of_records`,
`the_needle_halves_this_build_stores_cannot_be_joined_into_the_needle`,
`the_test_suites_own_needle_halves_cannot_be_joined_into_the_needle_either`
(`tests/stubid.rs`) and the three in
`tests/regressions/e10_the_needle_halves_were_stored_side_by_side.rs`.

**Cause B — a shebang is not a program on Windows.** `src/strip.rs` already
looks for `bin/<platform::erl_program>`, which E8 got right; the fixture writes
a `/bin/sh` file called `erl`. Renaming it does not help and a `.cmd` is not a
program either: `CreateProcess` starts a program by reading its image header.
So the fixture asks the platform what a program looks like —
`common::script::shim_form` and `common::script::shim_file_name` — and nothing

`tests/regressions/e10_a_fake_otp_wrote_an_erl_windows_cannot_start.rs`.

### 12 — macOS x86_64: the command that was missing is added into the slack

**Job.** `macOS (macos-15-intel, macos-x86_64)`, job
[`100597889308`](https://github.com/P4suta/ginary/actions/runs/33739517757/job/100597889308).

**Log excerpt.**

```text
error: cannot write the macOS payload section
  caused by: cannot ad-hoc sign a Mach-O with no LC_CODE_SIGNATURE to reuse; its
             load-command area cannot grow without relocating code
```

**Diagnosis.** E9's writer reuses the `LC_CODE_SIGNATURE` the platform linker
left. It ad-hoc signs every arm64 image and does not always sign an x86_64 one,
so the arm64 twin of this job passes on the same code and this one refuses.

**Fix.** `src/sign_macos.rs`. `Writer::plan` no longer refuses when there is no
command to reuse: it measures the slack between the end of the load commands and
the first section's file offset and, when at least `CODE_SIGNATURE_COMMAND_LEN`
(16) bytes are free, appends a fresh `linkedit_data_command` with `dataoff` and
`datasize` left for `Writer::build` to patch. `ncmds` grows by one and
`sizeofcmds` by sixteen; the padding arithmetic that used to assume the command
area only ever shrinks now takes the stub's own content from
`max(old_lc_end, new_lc_end)` instead, so the sixteen bytes the command occupies
are slack that is consumed rather than content that is pushed along. Nothing
before `__LINKEDIT` moves — the entry point, every segment's `fileoff`, every
`LC_DYLD_CHAINED_FIXUPS` target keep the offsets the linker gave them, which is
the property the section approach could not have and the whole reason 16 fits
where 152 did not. When the slack is genuinely too small the refusal stays and
names both numbers:

```text
cannot ad-hoc sign a Mach-O with no LC_CODE_SIGNATURE to reuse: adding one needs 16 bytes of
load command and only 8 are free before the first section, and the load-command area cannot
grow without relocating code
```

`load_command_slack` is that measurement as a public function, built on a new
private `command_geometry` walk so a caller measuring a stub does not have to
plan a write of it; `InjectReport::code_signature` says which of
`CodeSignatureSlot::Reused` and `CodeSignatureSlot::Added` happened, because the
two are correct in different circumstances and a caller should not have to infer
it from the bytes.

The measurement, re-taken by the code rather than quoted from E9:

| quantity | committed arm64 fixture |
| --- | --- |
| `commands_end` (`32 + sizeofcmds`) | 1688 |
| `first_content_offset` (lowest section `offset`) | 1728 |
| `free` | 40 |
| `LC_CODE_SIGNATURE` | 16 |

cross-check against the header and the section table; the derived

### 13 — Windows cause G: the needle is masked, and a scan counts records

**Job.** `Windows build and exit-code propagation`, job
[`100597889388`](https://github.com/P4suta/ginary/actions/runs/33739517757/job/100597889388).

**Log excerpt.**

```text
---- the_binary_this_test_run_built_carries_exactly_one_marker stdout ----
a ginary binary carries one identity marker, at one offset: [10961490, 10971432]

---- scanning_this_builds_own_binary_reports_its_identity stdout ----
the ginary binary is a stub: Ambiguous { count: 2 }
```

**Diagnosis.** The file carries one identity. It also carried the fifteen-byte
needle a second time, 9942 bytes from the first, because `stubid` stored the
record's name as two constants — `NEEDLE_HEAD` and `NEEDLE_TAIL` — and joined
them at run time. Splitting a constant keeps the needle out of any single
object and does nothing about the linker: two constants are two objects, and the
MSVC link of `ginary.exe` laid these two side by side, so the image held
`GINARY-STUB` immediately followed by `-ID\0` at an address no code in this crate
chose. That accounts for exactly two hits and no third, which is what the log
shows.

**Fix, both halves, because either alone leaves the mechanism at the mercy of the
next linker.** In `src/stubid.rs`:

1. **Nothing spells the needle.** The two constants are gone. What the build
   stores is one `static NEEDLE_IMAGE: [u8; 15]`, every byte exclusive-ored with
   `NEEDLE_MASK`, and `needle()` unmasks it at run time through
   `std::hint::black_box` so the optimiser may not fold the loop back into a
   plain fifteen-byte constant. The plaintext is a `const fn` written byte by
   byte rather than a string literal, and its only callers are constant
   evaluations — the image's initialiser and `marker()` — so the one plaintext
   image in the binary is `GINARY_STUB_ID` itself, where it belongs.
   `needle_fragments()` returns the stored images so the invariant is checkable
   rather than argued.
2. **A scan counts records.** `candidates` is every offset the needle appears at;
   `records` is every offset a whole 128-byte, terminated, UTF-8, zero-padded,
   four-field record begins at. `scan` counts the second: one record is a stub,
   two are `Ambiguous { count: 2 }` however many stray hits there are beside
   them, and no record with at least one candidate reports why the *first*
   candidate is not one — so a truncated, mistyped or badly padded marker still
   answers with its own typed error rather than a bare `NotAStub`.

`tests/common/stubfile.rs` is masked the same way, for the same reason: the
helper is linked into every test binary and `tests/stub.rs` scans real files
built from them.

**Evidence on this host.** `target/debug/ginary` now holds the needle at exactly
one offset and the masked image at one other:

```console
needle hits in target/debug/ginary: [1814387]
masked image hits: [1814372]
```

**Tests.** The five of `tests/stubid.rs` and the three of
`tests/regressions/e10_the_needle_halves_were_stored_side_by_side.rs`, all green,
plus the twenty pre-existing `stubid` tests unchanged — including every typed
field error, which is what pins that counting records did not swallow the reason
a single malformed marker is malformed.

### 19 — GREEN / test corrections

Two, and both are corrections to an *expectation*, not to a claim.

1. **`nothing_before_linkedit_moves_when_a_code_signature_is_added`**
   (`tests/sign_macos.rs`). As written, the test built its expected prefix from

   implementation, because `__LINKEDIT`'s `segment_command_64` sits in that

   is that rounded up to the 0x4000 page. The claim under test — that no *byte*
   moves — is unchanged and still compared over the whole prefix; what changed is
   that the expectation now describes the three fields the design changes instead
   of two of them.
